## 1. Cursor Projects: 멀티파일 코딩 에이전트 세팅

**Cursor**가 새로 공개한 **Projects**는 하나의 “작업 단위”에 파일, 터미널, 에이전트를 묶는 워크스페이스 기능입니다. 코드를 여러 파일에 걸쳐 수정하고, 터미널에서 명령을 치고, 같은 문맥을 에이전트가 계속 기억하게 하는 구조입니다. [출처](https://tldr.tech/ai/2026-09-14)

**어떻게 쓰는가**

1. **프로젝트 생성**
   - Cursor를 열고 왼쪽 사이드바에서 **Projects → New Project**를 선택합니다.  
   - Git 리포지터리를 이미 열었다면, 해당 폴더 기준으로 프로젝트를 생성합니다.  
   - “Backend API 리팩터링”, “LLM 실험 환경 셋업”처럼 **작업 단위로 이름**을 붙이는 것이 좋습니다.

2. **파일과 터미널 묶기**
   - 프로젝트 안에서 필요한 폴더와 파일만 **즐겨찾기처럼 핀(Pin)** 해둡니다.  
   - **Integrated Terminal**을 열어, 이 프로젝트 전용 터미널 탭을 띄웁니다. 빌드, 테스트, 로그 tail 명령을 이 안에서만 실행합니다.  
   - 강의에서는 “오늘 실습용 프로젝트”를 하나 만들어, 수강생에게 동일한 폴더 구조와 명령을 안내하면 됩니다.

3. **에이전트 연결과 컨텍스트 유지**
   - 프로젝트 창에서 **Chat / Code 에이전트**를 열면, 해당 프로젝트의 파일과 터미널 기록이 기본 컨텍스트로 붙습니다.  
   - 프롬프트 예:
     - “이 프로젝트에서 `orders` 관련 코드만 모두 살펴보고, 중복 비즈니스 로직을 찾고 리팩터링 계획을 세워 주세요.”
     - “방금 터미널에서 실패한 테스트 로그를 읽고, 관련된 파일을 열어 수정 제안 코드를 작성해 주세요.”
   - 에이전트가 파일을 넘나들며 기억해야 하는 작업은, **반드시 같은 Project 안에서만** 진행하는 것이 좋습니다.

**실전 팁 / 베스트 프랙티스**

- **작업 단위로 쪼개기**  
  “모놀리식 프로젝트 1개” 대신, 기능 단위나 실험 단위로 여러 Projects를 만듭니다.  
  예: `feature/user-onboarding`, `infra/ci-migration`, `study/llm-rag-poc`.

- **프롬프트에 “이 프로젝트 범위만”을 명시**  
  `이 Project 안의 파일만 고려해서…` 를 매번 붙이면, 무관한 디렉터리로 튀는 답변을 줄일 수 있습니다.

- **강의용 템플릿으로 활용**  
  사전에 **“강의용 Project 템플릿”**을 만들어 깃헙에 올려두고, 수강생에게 Cursor에서 그 폴더로 Project를 만들게 하면,  
  실습 중 에이전트가 “강의 전체 문맥”을 공유하므로 실습 지원에 유용합니다.

## 2. GPT-5.6 Luna vs GPT-6 Astra: 코드리뷰 이원화 전략

entelligence.ai가 **GPT-5.6 “Luna”와 GPT-6 “Astra”**를 코드리뷰 성능과 비용 측면에서 비교했습니다. **Luna는 저렴한 가격(약 1.20달러 / k 토큰 수준)으로 일상적인 코드리뷰에 충분**했고, **Astra는 깊은 설계 리뷰와 복잡한 리팩터링에서 우위**를 보였습니다. [출처](https://entelligence.ai/blogs/gpt-5.6-luna-vs-gpt-6-astra-is-a-1.20-model-good-enough-for-code-review)

**어떻게 쓰는가**

1. **CI에 Luna를 “1차 자동 리뷰어”로 붙이기**
   - PR이 생성되면, 변경된 파일 diff를 Luna에 전달합니다.  
   - 프롬프트 예:
     - “아래 diff를 기준으로 잠재 버그, 경계 케이스, 스타일 위반, 빠진 테스트를 목록으로 정리해 주세요. 파일별로 나누고, 줄 번호를 붙여 주세요.”
   - 결과를 **PR 코멘트나 체크리스트 파일**로 저장합니다.

2. **사람 + Astra를 “2차 심화 리뷰어”로 사용**
   - 다음 중 하나 이상에 해당하면 Astra를 호출합니다.
     - 여러 모듈을 동시에 건드린 PR
     - 아키텍처 변경, 보안 관련 수정
     - 성능 최적화, 동시성 제어
   - 프롬프트 예:
     - “아래 PR 전체를 읽고, 설계 상의 구조적 문제, 경합 가능성, 트랜잭션 경계 문제를 중심으로 리뷰해 주세요. 심각도 순으로 정리해 주세요.”
     - “이 변경이 기존 모듈 경계와 레이어드 아키텍처 원칙을 깨는 부분이 있는지 검토해 주세요.”

3. **강의/워크숍에서의 활용**
   - 같은 PR을 두 모델에 각각 리뷰시키고,  
     강의 시간에 “어느 지적이 실제로 의미 있었는지”를 수강생과 함께 평가합니다.  
   - 이를 통해 “모델 조합 설계” 수업을 할 수 있습니다.

**실전 팁 / 베스트 프랙티스**

- **Luna로는 “표면 검사”, Astra로는 “설계 검사”**라는 역할을 명확히 합니다.  
  프롬프트 설명에도 이 역할을 그대로 박아 넣는 것이 좋습니다.

- **PR 템플릿에 모델 호출 조건을 명문화**  
  예: “다음에 해당하면 Astra 리뷰 필수: DB 스키마 변경, 인증/인가, 캐시 전략 변경”.

- **비용 모니터링 대시보드**  
  Luna와 Astra 호출량을 분리해서 대시보드에 그립니다.  
  “PR당 평균 토큰, 모델별 비용”을 보여주면, 경영진 설득이나 강의 사례로도 활용 가능합니다.

## 3. OpenAI 연구 에이전트: 실험 파이프라인 자동화

OpenAI가 내부에서 사용하는 **코딩 에이전트 기반 연구 가속** 사례를 공개했습니다. 에이전트가 코드 작성, 실행, 결과 검증까지 맡으면서, **실험 속도와 복잡한 멀티스텝 작업 처리 능력이 실제로 올라갔다**는 내용입니다. [출처](https://openai.com/index/research-acceleration-view-inside-openai)

**어떻게 쓰는가**

1. **실험을 “모듈형 작업”으로 쪼개기**
   - 예: “데이터 전처리 코드 작성 → 실험 스크립트 생성 → 러닝 실행 → 메트릭 수집 → 후속 실험 제안”.  
   - 각 단계마다 **입력, 출력, 성공 기준**을 문서로 정리합니다.
   - 이 모듈들을 에이전트에게 “태스크 그래프”로 설명합니다.

2. **에이전트에게 “끝까지 맡기는” 프롬프트 작성**
   - 예시 워크플로:
     1. “dataset.csv로부터 피처를 생성하는 파이프라인 코드를 작성해, `src/preprocess.py`로 저장해 주세요.”
     2. “해당 파일을 사용해 3가지 모델(Logistic, RandomForest, XGBoost)을 비교하는 `run_experiments.py`를 작성하고, k=5 교차검증 결과를 표로 출력해 주세요.”
     3. “스크립트를 실행하고, 결과를 `results/summary.json`에 저장해 주세요.”
     4. “결과를 분석해, 성능 개선을 위한 추가 실험 3가지를 제안하고, 각 실험용 설정 파일을 생성해 주세요.”
   - 이 일련의 단계 전체를 하나의 “에이전트 루프”로 구성합니다.

3. **검증 가능한 산출물을 강제**
   - 각 단계는 항상 **파일, 로그, 메트릭**처럼 “눈으로 확인 가능한 결과물”을 반환하게 설계합니다.  
   - CI나 노트북에서 자동 체크:
     - 해당 파일이 존재하는지
     - 메트릭 JSON이 파싱 가능한지
     - 실행 로그에 에러가 없는지

**실전 팁 / 베스트 프랙티스**

- **“한 번에 모든 걸 바꾸는” 대신 “작은 루프를 반복”**  
  먼저 작은 데이터셋, 간단한 모델로 루프를 돌려 검증하고, 이후에 전체 데이터로 확장합니다.

- **실험 ID와 설정을 강제 기록**  
  에이전트가 실행하는 모든 실험에 `experiment_id`, `config`, `git commit hash`를 남기게 합니다.  
  재현성 문제를 줄이고, 강의에서 “에이전트 실험 재현하기” 과제를 줄 수 있습니다.

- **강의에서는 “사람 vs 에이전트” 속도 비교**  
  같은 실험을 수강생이 직접 짜게 하고, 에이전트 버전과 소요 시간, 버그 발생률을 비교하면  
  에이전트 활용 설계의 필요성을 직관적으로 보여줄 수 있습니다.

## 4. OpenArch: LLM 아키텍처 강의와 실험 레포

**OpenArch**는 Llama, Qwen, DeepSeek 등 여러 **LLM 아키텍처를 모델별로 한 파일에 구현한 PyTorch 레포지터리**입니다. 각 모델이 단일, 읽기 쉬운 `.py` 파일에 들어 있어, 구조를 비교하며 읽고 바로 수정해볼 수 있습니다. [출처](https://news.hada.io/topic?id=33700)

**어떻게 쓰는가**

1. **레포 구조 파악과 모델 선택**
   - 깃허브에서 OpenArch를 클론합니다.  
   - `llama.py`, `qwen.py` 같은 식으로 모델별 파일이 있습니다.  
   - 강의나 스터디에서는 1~2개만 선택해 집중적으로 다루는 것이 좋습니다.

2. **코드 읽기와 간단한 포워드 패스**
   - 각 파일 상단의 `Config`와 `Model` 클래스를 확인합니다.  
   - 예시 코드:
     ```python
     from llama import LlamaConfig, LlamaModel
     import torch

     config = LlamaConfig(
         vocab_size=32000,
         dim=512,
         n_layers=4,
         n_heads=8,
     )
     model = LlamaModel(config)
     x = torch.randint(0, config.vocab_size, (1, 16))
     y = model(x)
     print(y.shape)
     ```
   - 이 정도만 실행해도 “토이 LLM이 실제로 돌아간다”는 감각을 줄 수 있습니다.

3. **구성요소 스왑 실험**
   - 한 곳씩만 바꿔보는 것이 핵심입니다.
     - 어텐션 구현을 다른 파일에서 가져와 교체
     - LayerNorm 위치를 Pre-LN, Post-LN으로 바꾸기
     - RoPE, ALiBi 등 위치 인코딩 교체
   - 변경 전후로 **동일 입력에 대한 속도와 메모리 사용량, 출력 모양**을 비교합니다.

**실전 팁 / 베스트 프랙티스**

- **“최적화” 대신 “가독성”에 집중**  
  레포 자체가 성능 최적화보다 구조 이해에 초점을 두고 있으므로,  
  강의에서도 “왜 이렇게 나눴는지”를 설명하는 쪽이 좋습니다.

- **과제 설계 예시**
  - 과제 1: “Llama 구조에 MoE 레이어 1개를 추가해 포워드 패스를 통과시키기”.
  - 과제 2: “Qwen의 어텐션을 Llama 스타일로 교체하고, 성능 차이를 간단 벤치마크로 측정하기”.

- **연구 프로토타입용으로 활용**
  - 새로운 아이디어를 거대한 프레임워크에 붙이기 전에,  
    OpenArch에서 먼저 검증한 뒤, 실제 프로덕션 코드베이스로 옮기는 흐름이 안전합니다.

## 5. Sunk Cost 계산기와 NVLink: 로컬 LLM 인프라 의사결정

**Sunk Cost**는 “로컬 LLM 장비를 사서 돌릴지, 토큰을 빌려 쓸지”의 손익분기점을 계산해 주는 웹 계산기입니다. GPU 사양, 모델, 일일 토큰 사용량을 입력하면 **하드웨어 감가상각 vs 임대 토큰 비용**을 비교해 줍니다. 한편, **엔비디아와 미디어텍의 35억 달러 투자와 NVLink Fusion 라이선스**는 클라우드와 대형 인프라 쪽에서 “엔비디아와 직접 호환되는 SoC 생태계”를 키우려는 신호입니다. [Sunk Cost 출처](https://sunkcost.ai/) / [엔비디아 출처](https://www.itworld.co.kr/article/4221572/%ec%97%94%eb%b9%84%eb%94%94%ec%95%84-%eb%af%b8%eb%94%94%ec%96%b4%ed%85%8d%ec%97%90-35%ec%96%b5-%eb%8b%ac%eb%9f%ac-%ed%88%ac%ec%9e%90%eb%a1%9c-ai-%ec%9d%b8%ed%94%84%eb%9d%bc-%ec%a3%bc%eb%8f%84.html)

**어떻게 쓰는가 (Sunk Cost)**

1. **현실적인 사용량부터 정하기**
   - 팀 혹은 강의에서 하루에 실제로 소비하는 토큰 수를 추산합니다.  
   - 예: “개발팀 10명, 1인당 하루 5만 토큰 사용”이면, 하루 50만 토큰입니다.

2. **계산기에 입력**
   - GPU 모델, 대략적인 장비 가격, 예상 수명(예: 2~3년), 전력 비용을 넣습니다.  
   - 사용하는 모델과 예상 토큰당 비용(클라우드 API 가격)을 설정합니다.  
   - 결과로 **손익분기까지 걸리는 일수 또는 개월 수**가 나옵니다.

3. **의사결정 기준 만들기**
   - 예: “손익분기까지 18개월 이하면 장비 구매 고려, 그 이상이면 클라우드 유지”.  
   - 강의에서는 여러 케이스를 비교해, 수강생에게 “자기 조직 기준”을 스스로 계산하게 할 수 있습니다.

**NVLink Fusion 시그널은 어떻게 활용할까**

- NVLink Fusion으로 **서드파티 SoC와 엔비디아 GPU가 직접 연결**되면,  
  대형 사업자 입장에서는 “엔비디아 생태계 안에서 커스텀 칩을 쓰기 쉬워지는” 구조가 됩니다.
- 개발자와 강사는 다음을 가정하고 설계하는 것이 안전합니다.
  - 대규모 인프라는 NVLink 호환 클러스터로 더 표준화될 가능성이 높습니다.
  - 자체 GPU 센터를 설계하는 조직은, **향후 NVLink Fusion 호환 여부**를 체크리스트에 넣어야 합니다.

**실전 팁 / 베스트 프랙티스**

- **로컬 vs 클라우드 vs NVLink 클러스터를 구분해 설명**  
  강의에서는 세 가지를 별도 축으로 나눕니다.
  - “개인/소규모 팀: Sunk Cost로 손익분기 계산 후, 로컬 vs API 선택”
  - “중대형 조직: NVLink 호환 클러스터나 메이저 클라우드의 GPU 팜 활용”
  - “규제·데이터 보안 요구가 강한 조직: 폐쇄망 + 로컬 장비의 비용을 별도로 시뮬레이션”

- **Sunk Cost 결과를 “조달 문서” 초안으로 사용**  
  장비 구매 제안서에 계산 스크린샷과 가정을 첨부하면,  
  경영진과 인프라 팀 설득에 활용할 수 있고, 교육에서는 “데이터 기반 의사결정” 사례로 쓸 수 있습니다.

- **오늘 흐름 정리**  
  프런티어 모델을 둘러싼 규제와 인프라 투자는 점점 거대해지고 있습니다.  
  그 사이에서 실무자는 Cursor Projects, Luna+Astra 조합, OpenArch, Sunk Cost 같은 “현장에서 바로 쓰는 도구”로,  
  **코드는 에이전트에 더 맡기고, 비용과 리스크는 숫자와 구조로 설명하는 역할**을 키우는 쪽으로 움직이는 흐름입니다.
