## 1. Hy4 초장문맥 LLM: 오픈 가중치·추론 제어

텐센트 **Hy4 프리뷰**가 공개되었습니다.  
구조는 총 **770B 파라미터(49B 활성)**, 컨텍스트 윈도는 **100만 토큰급**, 가중치는 허깅페이스에 약 **1.56TB** 규모로 올라와 있습니다. [출처](https://simonwillison.net/2026/Aug/29/hy4)

### 어떻게 돌리는가

두 갈래입니다.

1) 로컬·서버에서 직접 추론  
- 허깅페이스에서 Hy4 체크포인트를 받습니다.  
- 제공된 토크나이저와 추론 스크립트를 그대로 사용해 스트리밍 입력을 붙입니다.  
- 컨텍스트가 길기 때문에, 코드·논문은 **토크나이저 기준 슬라이딩 윈도**로 잘라 넣는 것이 좋습니다.

2) OpenRouter 등 API 경유  
- OpenRouter에서 Hy4 엔드포인트를 선택합니다.  
- 제공된 **`chat_template.jinja`**를 그대로 적용합니다.  
- 메시지 구성 시 `reasoning_effort` 파라미터를 함께 넘깁니다.  
  - `"high"`: 디폴트, 내부 추론을 길게 써 줌(CoT 스타일).  
  - `"no_think"`: 추론 과정을 최대한 숨기고 결과 위주로 응답.

### 실전 팁

- **디버깅·강의·리뷰**에는 `reasoning_effort="high"`  
  - 예: “이 코드 리팩터링 과정을 단계별로 설명하라”  
  - 내부 추론이 드러나야, 수업·코드리뷰에 설명 자료로 재사용 가능합니다.

- **프롬프트·에이전트 응답 최적화**에는 `reasoning_effort="no_think"`  
  - 체인 오브 소트가 길어져 UI를 어지럽히거나, 모델 간 내부 추론을 노출하고 싶지 않을 때 사용합니다.  
  - 같은 프롬프트에서, “사용자에게 보이는 답”과 “내부 로그용 추론”을 분리해 설계할 수 있습니다.

- 100만 토큰 컨텍스트 활용 패턴  
  - 대규모 코드베이스 리뷰:  
    - **폴더 단위**로 토큰 수를 계산하고, 빌드·실행과 직접 관련된 경로만 한 번에 넣습니다.  
    - “이 프로젝트의 의존성 그래프와 빌드 순서를 텍스트로만 요약하라”처럼 **메타 구조**를 먼저 뽑고, 이후 세부 파일에 슬라이딩 윈도 접근을 붙입니다.  
  - 논문·리포트 번들 강의:  
    - 10~20편 논문을 한 번에 넣고,  
    - “대학원 수업용 3회차 커리큘럼과 실습 아이디어를 만들어라”처럼 상위 설계부터 받습니다.

Hy4는 “전체 코드·자료를 거의 통째로 넣고, 추론 양까지 제어”하는 강의·리뷰용 실험 장비로 쓸 만합니다. 실무에선 OpenRouter로 빠르게 붙이고, 이후 GPU 예산이 맞으면 허깅페이스 가중치로 자체 호스팅을 검토할 수 있습니다.

## 2. Lovable Capabilities: 에이전트가 쓰는 SaaS 설계법

**Lovable**가 MCP 호환 **Capabilities**를 공개했습니다.  
핵심은 “에이전트가 클릭 대신 API로 웹앱을 쓴다”는 가정에서, 앱 기능을 **에이전트 호출용 액션 단위**로 재정의하는 것입니다. [출처](https://www.latent.space/p/lovable-future-of-saas)

### 어떻게 붙이는가

1. **Capability 매니페스트 정의**  
   - 액션 이름과 설명  
   - 입력/출력 스키마(JSON Schema 스타일)  
   - 인증 스코프(어떤 리소스를 어느 수준으로 다루는지)

   예시 구조(개념적):

   ```json
   {
     "name": "create_issue",
     "description": "프로젝트에 신규 이슈 생성",
     "input_schema": {
       "type": "object",
       "properties": {
         "project_id": {"type": "string"},
         "title": {"type": "string"},
         "body": {"type": "string"}
       },
       "required": ["project_id", "title"]
     },
     "output_schema": {
       "type": "object",
       "properties": {
         "issue_id": {"type": "string"},
         "url": {"type": "string"}
       },
       "required": ["issue_id"]
     },
     "auth_scopes": ["project:write"]
   }
   ```

2. **Lovable MCP 게이트웨이에 등록**  
   - 매니페스트를 게이트웨이에 등록하면,  
   - 에이전트가 **표준 Capability API**를 통해 이 액션을 검색·호출할 수 있습니다.

3. **에이전트에서 사용**  
   - 에이전트는 “이슈를 생성해야겠다”라고 판단하면,  
   - `create_issue` 액션을 매니페스트 정의대로 호출합니다.  
   - 응답은 항상 `output_schema`에 맞으므로, 후속 프롬프트·툴 호출이 단순해집니다.

### 실전 설계 팁

- **작고 멱등(idempotent)한 액션**으로 쪼개기  
  - `create_or_update_and_notify_issue` 같은 복합 액션은 피하는 것이 좋습니다.  
  - `create_issue`, `update_issue`, `send_notification`처럼 나누고,  
    - 재호출해도 같은 결과가 보장되는 액션부터 설계합니다.

- **입·출력 스키마를 ‘설명서’로 쓰기**  
  - 설명(prompt)보다 스키마가 정확합니다.  
  - “이 필드는 enum, 이 조합은 금지” 같은 제약을 스키마에 녹이면,  
    - 에이전트가 잘못된 파라미터를 덜 생성합니다.

- **Auth 스코프를 최대한 좁게**  
  - 에이전트는 실수합니다.  
  - `project:read`, `project:write:own`, `billing:read`처럼 목적별로 세분화하고,  
  - 초기 실험 단계에서는 `read` 중심 권한만 허용해도 충분한 경우가 많습니다.

- **에러 응답을 표준화**  
  - 에이전트는 `"error_code"`, `"retryable"`, `"user_message"` 같은 구조화된 에러에 강합니다.  
  - 이를 스키마에 포함해 두면, **재시도·사용자 안내**를 프롬프트에서 일괄 처리할 수 있습니다.

강의·워크샵에서는 “기존 REST API를 에이전트용 Capability로 리팩터링해 보기” 과제를 주면 좋습니다. 실제 제품팀은 이 설계를 표준화해 두면, 에이전트 플랫폼(Claude, OpenAI, Lovable 등)이 바뀌어도 백엔드 액션은 재사용 가능해집니다.

## 3. memnest·Lemmalog: 코딩 에이전트용 장기 메모리

국내에서 **memnest**가, 해외 커뮤니티에서는 **Lemmalog**가 모두 “에이전트용 메모리”를 다루지만 접근 방식이 다릅니다.  
공통 화두는 “세션이 끊겨도, 에이전트가 프로젝트 맥락을 잊지 않게 하는 것”입니다. [memnest](https://news.hada.io/topic?id=33025) / [Lemmalog](https://news.hada.io/topic?id=33015)

### memnest: 로컬 노트 저장소 패턴

- 로컬에서 서비스 하나를 띄웁니다.  
  - 기본은 HTTP 서버, 포트는 설정 가능.  
- 코딩 에이전트(예: Claude Code, 자작 IDE 플러그인)가  
  - **요약·결정·이슈**를 memnest API로 저장합니다.  
  - 이후 새 세션에서 같은 리포지토리·프로젝트를 열면 memnest에서 다시 불러옵니다.

실전 사용 패턴:

- 저장할 내용은 “재사용 가능한 단위”만  
  - “왜 이 라이브러리를 골랐는지”  
  - “이 버그의 원인과 최종 패치 커밋”  
  - “이 포트·토큰이 어떤 환경에서 쓰이는지”  
- 형식은 짧은 구조화 JSON 추천  

```json
{
  "project": "my-service",
  "type": "decision",
  "topic": "db_migration",
  "summary": "SQLite에서 Postgres로 이전, 이유: 동시성·백업 전략",
  "commit": "abc1234"
}
```

이렇게 저장하면, 새 세션의 에이전트에게는  
“이 프로젝트의 과거 결정들을 불러와라” 한 줄로 충분합니다.

### Lemmalog: Datalog 기반 “사실·규칙” 엔진

**Lemmalog**는 Datalog로 상태를 표현합니다.  
대화 기록을 재전달하는 대신, 현재 참인 사실과 규칙만 저장·추론합니다.

사용 흐름:

- 사실(Fact)과 규칙(Rule)을 Datalog 형태로 저장  
  - 사실 예: `uses_lib(projectA, "fastapi").`  
  - 규칙 예: `requires_review(File) :- touches_security(File).`
- 쿼리 시점에는 “지금 시점에서 무엇이 참인가”만 질문  
  - 예: `? - requires_review(File).`

실전 팁:

- **가설은 규칙, 검증된 정보는 사실**로 구분  
  - 취약점 조사 중 가설은 규칙으로 두고,  
  - 재현·패치 후에야 사실로 승격합니다.  
- 이렇게 하면,  
  - “이미 틀린 것으로 판명된 가설”이 다시 등장하지 않습니다.  
  - 장기적인 취약점 분석, 인시던트 리뷰에 유용합니다.

강의에서는 memnest를 “실용 메모리 API” 예제로, Lemmalog를 “프로그램 분석·추론 엔진” 예제로 대비해 소개하면 좋습니다. 실무에서는 둘 다 “프롬프트에 과거를 계속 덕지덕지 붙이지 않아도 되는 구조”를 주는 점이 핵심입니다.

## 4. Tempo WFI: AI 도구 비용을 이슈 단위로 귀속

**Tempo의 워크포스 인텔리전스(WFI)**가 지라(Jira)용 앱으로 공개되었습니다.  
핵심 기능은 **Codex, Copilot, Claude Code 등 AI 도구 사용 로그와 비용을 지라 이슈·에픽 단위로 자동 매핑**하는 것입니다. [출처](https://www.itworld.co.kr/article/4213924)

### 어떻게 쓰는가

1. 지라 클라우드에 **WFI 앱 설치**  
   - Atlassian 마켓플레이스에서 설치 후,  
   - 조직의 AI 도구(예: OpenAI, GitHub Copilot, Anthropic)의 텔레메트리·라이선스를 연결합니다.

2. AI 사용량·비용을 지라 이슈에 귀속  
   - 앱이 최대 **과거 90일**까지 데이터를 수집·매핑합니다.  
   - 각 이슈/에픽에서  
     - “무슨 AI 도구를 얼마나 호출했는지”  
     - “토큰·라이선스 비용이 얼마인지”를 보여 줍니다.

3. 인건비와 함께 비교  
   - Tempo 자체의 시간 추적·코스트 기능과 합쳐  
   - “이 이슈에 투입된 사람 시간 + AI 비용”을 한 화면에서 확인할 수 있습니다.

### 실전 활용 팁

- **팀별 AI ROI 대시보드**  
  - 팀·이니셔티브별로  
    - 총 AI 비용 vs 총 인건비 vs 산출물(스토리 포인트·배포 수)을 비교합니다.  
  - “AI 비용은 높은데 산출물 개선이 없는” 팀·프로젝트를 빠르게 찾을 수 있습니다.

- **도구·플랜 실험의 A/B 검증**  
  - 예: Copilot Business vs Enterprise, Claude Code 플랜 변경 등.  
  - 플랜 변경 전후를 같은 이니셔티브 기준으로 비교해  
    - “한 이슈를 끝내는 총 ‘현금 비용’(사람+AI)이 줄었는지”를 확인합니다.

- **교육·강의용 사례 만들기**  
  - 수강생 실습 프로젝트를 지라 이슈에 묶고,  
  - 각 조가 사용한 AI 도구와 비용을 보여 주면  
    - “AI를 잘 쓰면 얼마를 아끼는지”를 수치로 보여 줄 수 있습니다.

이제 “AI가 생산성을 올린 것 같다” 수준이 아니라,  
“이 에픽에서 AI 도구가 없었으면 비용이 얼마 더 들었을지”를 추정할 수 있는 재무·교육 설계가 가능해집니다.

## 5. 자기개선 에이전트 vs 보안·거버넌스: 오늘의 균형점

**Warp**는 Claude 기반으로 “자기개선 에이전트”를 운영합니다.  
에이전트가 스스로 코드를 수정하고, 테스트를 돌리고, 다시 프롬프트를 개선합니다. [출처](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)

### Warp식 자기개선 루프 요약

- Claude를 백엔드로 설정하고,  
- 에이전트의 “목표·작업·테스트·피드백 루프”를 정의합니다.  
- 에이전트는  
  - 코드를 작성·수정  
  - unit-style 테스트를 실행  
  - 실패 시 원인 분석 후 다시 개선  
  - 테스트 통과 전에는 배포하지 않도록 제한합니다.

이 구조는 “프롬프트·코드가 시간이 갈수록 좋아지는” 시스템을 가능하게 합니다.  
하지만 동시에, 공격 면도 커지고 있습니다.

### 오늘 같이 봐야 할 보안·거버넌스 신호

- **Hugging Face 사고와 OpenAI의 권고**  
  - 모델 가중치·서드파티 모델의 출처 검증,  
  - 무결성 해시·서명,  
  - 런타임 이상 징후 모니터링이 요구되고 있습니다. [출처](https://openai.com/index/hugging-face-incident-and-the-road-ahead)

- **EASM(External Attack Surface Management)**  
  - AI 도입 속도가 빨라질수록,  
    - 하드코딩된 키,  
    - 잘못 공개된 리포지토리,  
    - 에이전트가 만들어 둔 테스트 서버 등이 외부 공격 표면을 키웁니다.  
  - Palo Alto, CrowdStrike, Tenable, Rapid7, Wiz 등의 EASM 도구로  
    - 공개 자산·코드·클라우드 설정을 주기적으로 스캔해야 합니다. [출처](https://www.itworld.co.kr/article/4214531)

- **Debian의 LLM 사용 방침**  
  - “AI를 써도 되지만, 품질·법적 책임은 인간이 진다”는 입장입니다.  
  - AI 생성 코드는  
    - 작성자가 이해·리뷰·테스트를 마쳐야 하며,  
    - 라이선스·컴플라이언스는 기존 기준 그대로 적용합니다. [출처](https://news.hada.io/topic?id=33020)

### 실전 체크리스트

자기개선·장기 실행 에이전트를 도입할 때, 다음 네 가지를 기본선으로 두는 것이 안전합니다.

1. **테스트 없는 자동 수정 금지**  
   - Warp 사례처럼, “테스트 통과 전에는 병합·배포 불가”를 시스템 차원에서 강제합니다.

2. **권한 최소화·토큰 분리**  
   - 에이전트용 액세스 키는  
     - 읽기 범위가 좁고,  
     - 쓰기가 필요하면 프로젝트·환경 단위로 분리합니다.

3. **EASM + 시크릿 스캐닝 상시 가동**  
   - 공용 리포지토리·SaaS 계정 전체를 대상으로  
   - 시크릿·노출 자산 스캔을 주기적으로 돌립니다.

4. **AI 사용 내역·출처 기록**  
   - 어떤 코드·문서가 어떤 모델 도움을 받았는지,  
   - 최소한 커밋 메시지·MR 템플릿에 남깁니다.  
   - 나중에 라이선스·품질 문제를 추적하기가 훨씬 수월합니다.

오늘 신호를 묶어 보면, “Hy4 같은 거대 모델과 자기개선 에이전트로 공격적으로 자동화를 밀어붙이는 흐름”과 동시에, “비용·보안·책임을 수치와 정책으로 묶어 두려는 흐름”이 맞부딪칩니다. 개발자와 강사는 이제 “무엇을 자동화할지” 뿐 아니라 “어디까지 자동화하고, 그 결과를 어떻게 검증·기록할지”를 함께 설계해야 하는 시점입니다.
