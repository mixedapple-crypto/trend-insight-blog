## 1. Claude Code + Playwright: 캔버스 애니메이션 영상화

**26일자 Simon Willison의 글**에서 **Claude Code**를 **Playwright**와 묶어 HTML5 캔버스 애니메이션을 브라우저에서 직접 재생, 클릭, 녹화해 동영상으로 뽑는 예제가 공개되었습니다. [출처](https://simonwillison.net/2026/Sep/26/kakapo-party)

**사용 흐름은 단순합니다.**

1. **로컬 HTML 열기 지시**
   - Claude Code에 파일 URL을 그대로 줍니다.  
     예:  
     `file:///Users/you/projects/kakapo-party.html`
   - “Playwright로 이 페이지를 열고, 60fps로 20초간 녹화해 mp4로 저장하라”처럼 목표를 명시합니다.

2. **타이밍·클릭 시나리오 정의**
   - 프롬프트에 다음을 구체적으로 적습니다.
     - 녹화 시작 전 **워밍업 대기 시간**  
       예: “페이지 로드 후 3초 기다린 뒤 녹화 시작”
     - **클릭 지점과 타이밍**  
       예:  
       - 2초 시점에 x=300, y=250 클릭  
       - 5초 시점에 x=500, y=260 더블클릭
     - **총 녹화 길이**  
       예: “총 15초간 녹화 후 브라우저 종료”

3. **Claude Code가 만드는 Playwright 스크립트 예시**
   - Claude Code가 대략 이런 스크립트를 생성합니다.
   - 요지:
     - `page.goto("file:///…/kakapo-party.html")`
     - `await page.waitForTimeout(3000)`  // 워밍업
     - `browser.startTracing` 또는 녹화용 API 호출
     - `setTimeout`으로 특정 시점에 `page.mouse.click(300, 250)` 실행
     - 15초 후 녹화 중단, 영상 파일 저장

4. **실행**
   - Claude Code가 생성한 스크립트를 로컬에 저장합니다.  
     예: `record-kakapo.ts`
   - `npx playwright codegen` 류 명령이 아닌, `npx ts-node record-kakapo.ts`처럼 직접 실행합니다.

**실전 팁**

- **워밍업 딜레이는 넉넉히**  
  캔버스 초기화, 이벤트 핸들러 등록, 리소스 로드를 고려해 최소 2~3초 이상을 권장합니다.
- **좌표는 개발자 도구로 먼저 확인**  
  브라우저에서 `document.addEventListener('click', e => console.log(e.clientX, e.clientY));`를 잠시 붙여 좌표를 로그로 받은 뒤, 그 값을 Playwright 클릭 좌표로 사용하면 재현성이 높아집니다.
- **시나리오는 “타임라인”으로 서술**  
  “0~3초: 워밍업, 3~18초: 녹화, 5초·10초에 각각 클릭”처럼 타임라인 서술을 하면 Claude Code가 구조를 잘 잡습니다.

강의나 실습에서는 이 워크플로를 사용해 **수업용 캔버스 데모를 표준화된 동영상 자산으로 바꾸는 과정**을 보여줄 수 있습니다. 프론트엔드 튜토리얼, 시뮬레이션, 인터랙티브 데이터 시각화 결과물을 재현 가능한 영상으로 남길 때 특히 유용합니다.

## 2. Atlas: 에이전트 작업 전체를 Git 히스토리로 남기기

**Atlas**는 코딩 에이전트를 위한 **데스크톱 소스 관리 도구**로, Git 커밋만이 아니라 에이전트가 받은 요청, 사용한 도구, 작업 컨텍스트까지 한 번에 기록합니다. [출처](https://news.hada.io/topic?id=34344)

**기본 사용 흐름**

1. **Atlas 데스크톱 앱 실행**
   - Atlas를 설치 후 실행합니다.
   - 작업할 로컬 리포지터리를 Atlas에 연결합니다.

2. **에이전트 연결**
   - 지원 에이전트:
     - **Claude Code**
     - OpenAI Codex 계열
     - 자체 호스팅 에이전트
     - **ACP 호환 에이전트**
   - 에이전트 설정에서 Atlas의 API 엔드포인트나 토큰을 등록합니다.  
     에이전트가 코드 변경을 할 때 Atlas로 이벤트를 보내도록 합니다.

3. **작업 시나리오**
   - VS Code에서 Claude Code나 다른 에이전트로 “이 모듈에 캐싱 레이어 추가” 같은 작업을 실행합니다.
   - 에이전트가 파일을 수정하고, 테스트를 돌리고, 커밋을 남깁니다.
   - Atlas는 이 흐름을 모두 캡처합니다.
     - 각 커밋에 대응하는 **프롬프트, 응답, 사용한 도구, 중간 결정**이 함께 저장됩니다.

4. **Atlas에서 히스토리 확인**
   - 특정 커밋을 클릭하면:
     - 그 커밋을 만든 에이전트의 대화 내용
     - 코드 변화 diff
     - 관련된 다른 에이전트 세션
   - 을 한 화면에서 볼 수 있습니다.

**멀티 에이전트 실전 팁**

- **병렬 세션 + 공유 컨텍스트 활성화**
  - Atlas에 있는 **병렬 세션**과 **공유 컨텍스트 동기화** 기능을 켭니다.
  - 예:
    - 에이전트 A: 기능 구현 담당
    - 에이전트 B: 테스트 케이스 생성 담당
    - 에이전트 C: 리팩터링 담당
  - 각 에이전트가 Atlas를 통해 서로의 작업 요약과 커밋 사유를 볼 수 있게 합니다.

- **재현·감사·디버깅이 쉬운 구조 만들기**
  - “어떤 프롬프트로 이런 커밋이 나왔는지”를 언제든 재현 가능하게 두면:
    - 강의 시 “이 프롬프트를 이렇게 바꾸면 커밋이 어떻게 달라지나”를 실험적으로 보여줄 수 있습니다.
    - 팀에서는 “문제가 된 버그 커밋을 어떤 에이전트 결정이 만들었는지”를 추적할 수 있습니다.

강사 입장에서는 Atlas를 통해 **“에이전트 주도 개발”의 전체 타임라인**을 시각화하면서, 사람과 에이전트의 역할 분담과 책임 범위를 구체적으로 설명하는 데 활용할 수 있습니다. 실무에서는 에이전트 도입 시 필수에 가까운 **프로비넌스(provenance) 기록 계층**으로 사용할 수 있습니다.

## 3. Codex 폭주 사고와 OpenAI 훈련 중단: 에이전트 거버넌스 체크리스트

한 개발자가 **VS Code에서 OpenAI Codex 에이전트를 돌리다 7만 8천 달러 상당의 토큰이 소모된 사례**를 보고했습니다. 하나의 작업이 수백 개의 자식 태스크(총 826개, 그 중 104개는 동일 복제본)를 자율적으로 생성했고, 각 태스크가 서로 다른 모델 이름과 큰 로컬 토큰 카운터를 기록했습니다. [출처](https://news.ycombinator.com/item?id=49861047)

동시에, **OpenAI는 “가장 능력 있는 모델들의 추가 훈련을 일시 중단”**한다고 발표했습니다. 성숙한 거버넌스와 안전 장치가 확보될 때까지 고성능 모델의 스케일업을 멈추겠다는 입장입니다. [출처](https://www.theverge.com/ai-artificial-intelligence/1001049/openai-training-pause)

**이 두 신호에서 바로 적용할 수 있는 통제 체크리스트는 다음과 같습니다.**

1. **에이전트 생성·병렬성 제한**
   - “에이전트가 에이전트를 만든다” 구조에는 반드시 하드 리밋을 둡니다.
     - 한 세션당 자식 에이전트 수 상한
     - 전체 동시 실행 에이전트 수 상한
   - VS Code, 서버, 오케스트레이터 레벨 모두에서 동시성 제한을 중첩해 두는 것이 안전합니다.

2. **명시적 승인 워크플로**
   - 멀티 에이전트 워크플로는 기본값을 “자동 실행”이 아니라 **“사전 승인 필요”**로 둡니다.
   - 예:
     - 3개 이상의 자식 태스크 생성 시 팝업으로 확인
     - 예상 토큰 사용량이 일정 기준(예: 5만 토큰) 이상이면 사용자에게 재확인

3. **서버 측 비용·활동 로그 필수화**
   - 단일 클라이언트(예: VS Code 확장) 로그에만 의존하지 말고:
     - 서버에서 **에이전트 ID, 부모-자식 관계, 모델 버전, 토큰 사용량**을 모두 저장합니다.
     - 청구·포렌식이 가능하도록 월 단위가 아닌, 세션 단위로 조회할 수 있게 합니다.
   - 강의 현장에서는 이 로그를 활용해 “폭주 시나리오”를 재현용 샌드박스에서 시뮬레이션하고, 어디서 차단해야 하는지 보여줄 수 있습니다.

4. **모델 업그레이드 추격 대신 시스템 설계에 집중**
   - OpenAI의 훈련 중단 신호는, 당분간 “더 큰 모델”이 아니라 **“더 안전한 시스템”**으로 무게 중심을 옮기라는 의미로 읽을 수 있습니다.
   - 실무에서 바로 할 수 있는 일:
     - 평가 세트와 회귀 테스트를 만들어, 에이전트 변경 시 항상 돌리기
     - 모델 + 검색(RAG) + 정책 레이어(허용·차단 규칙) 구조를 모듈화
     - 위험한 액션(결제, 배포, 대규모 리포 수정)은 별도 승인 플로우 강제

Codex 사고와 OpenAI의 훈련 중단은, “단일 모델 성능 향상”보다 **거버넌스, 로그, 승인 흐름 설계가 먼저**라는 점을 다시 상기시킵니다. 강의나 컨설팅에서는 이 사례를 에이전트 도입 전 “필수 점검 목록”으로 제시하는 것이 효과적입니다.

## 4. LLM을 설계·리뷰·평가 도구로 쓰는 법 + Jev 래퍼

**“LLM 시대에도 프로그래밍을 계속 즐기는 법”**이라는 글은 LLM을 전체 구현자가 아닌 **설계, 조사, 리뷰, 테스트 도우미**로 사용하는 방식을 제안합니다. [출처](https://news.hada.io/topic?id=34336)

**실전 활용 프롬프트 예**

1. **설계·계획용**
   - “다음 기능을 추가하려 한다. 단계별 구현 계획과 각 단계의 트레이드오프를 정리해 달라.”
   - “이 API 설계에서 누락된 에러 케이스와 고려할 점을 리스트업해 달라.”

2. **테스트·엣지 케이스**
   - “이 함수에 대한 엣지 케이스와 단위 테스트 목록을 만들어 달라.”
   - “아래 입력 형식에서 보안 취약점이 될 수 있는 패턴을 찾아 달라.”

3. **리뷰·리팩터링 논의**
   - “다음 코드에서 버그 가능성이 높은 부분을 지적하고 이유를 설명해 달라.”
   - “동일 기능을 유지하면서 가독성을 높이는 리팩터링 방향을 제안해 달라.”

핵심은 **핵심 구현은 직접 작성**하고, LLM은 주변 작업에 집중시키는 것입니다. 이렇게 하면 코드베이스에 대한 이해를 유지하면서도, 설계 품질과 커버리지를 끌어올릴 수 있습니다.

여기에 **Jev 스타일 LLM 래퍼**가 더해지면, LLM을 “평가기”와 “분류기”로 안정적으로 활용할 수 있습니다. 이 래퍼는 **비전 모델까지 지원**하며, 자유 텍스트 대신 **선택지 확률**을 돌려줍니다. [출처](https://news.hada.io/topic?id=34327)

**Jev 래퍼 사용 흐름**

1. **score 함수 호출**
   - 인터페이스 예:
     ```python
     score(
       question="이 코드 변경이 기존 테스트를 깨뜨릴 가능성?",
       choices=["A", "B", "C"],  # 예: A=낮음, B=중간, C=높음
       model="gpt-vision-x"
     )
     ```
   - 프롬프트에서는 “반드시 A, B, C 중 하나만 출력하라”라고 강하게 명시합니다.

2. **단일 토큰 출력 강제**
   - 출력이 한 글자(A/B/C) 한 개 토큰이 되도록 프롬프트와 토크나이저를 맞춥니다.
   - 래퍼가 토큰별 로그 확률을 읽어 **각 선택지의 확률**로 변환합니다.

3. **적용 예시**
   - **리뷰 보조 평가**:
     - “이 PR 설명과 변경 코드를 보고, ‘리뷰 필요도’ 점수를 1~5 중 고르라.”
     - LLM의 선택 확률을 기준으로 자동 라벨링, 우선순위 큐 정렬.
   - **테스트 케이스 우선순위 선정**:
     - 각 테스트 케이스의 중요도를 점수화해 상위 N개만 사람 검토로 넘기기.
   - **비전 코드리뷰**:
     - 스크린샷과 코드 스니펫을 함께 넣어, UI 회귀 가능성 점수화.

이 래퍼를 사용하면 평가 결과를 **숫자로 축적**할 수 있어, 실습과 연구에서 LLM 기반 평가의 재현성과 비교 가능성을 확보할 수 있습니다. 강의에서는 “텍스트 대신 점수로 대화하는 LLM” 패턴을 보여주는 좋은 사례가 됩니다.

## 5. Reladraw: LLM과 함께 쓰는 다이어그램 DSL, 오늘 흐름 정리

**Reladraw**는 텍스트 기반 다이어그램 언어이지만, 전적으로 자동 레이아웃에 맡기지 않고 **개발자가 좌표를 직접 결정하거나 상대 배치를 명시**할 수 있는 도구입니다. [출처](https://github.com/reladraw/reladraw)

**기본 활용법**

1. **DSL로 도형·간선 정의**
   - 예시 형태:
     ```txt
     node api "API Server" at (100, 100)
     node db "Database" right_of api by 200
     edge api -> db "reads/writes"
     ```
   - 텍스트만으로 노드와 관계를 정의합니다.

2. **수동·상대 레이아웃 혼합**
   - 핵심 노드는 `at (x, y)`로 좌표를 고정합니다.
   - 나머지는 `right_of`, `below`, `align_with` 같은 상대 위치 지정으로 배치합니다.
   - 이렇게 하면 “중요 구조는 사람이, 세부는 도구가” 정리하는 구조가 됩니다.

3. **LLM 에이전트와 함께 쓰기**
   - GitHub 레포에 **Claude 등 LLM용 스킬**이 포함되어 있습니다.
   - 워크플로 예:
     - LLM에게 “다음 시스템 구조를 Reladraw 코드로 그려 달라”고 요청
     - 사람이 핵심 노드 몇 개의 좌표만 고정
     - 다시 LLM에게 “새 모듈을 추가하되, 기존 좌표는 유지한 채 상대 위치만 조정하라”고 지시

**실전 팁**

- **핵심 노드만 좌표 고정**  
  API 게이트웨이, 메인 DB, 외부 서비스 같은 축 노드만 좌표를 명시하고, 나머지는 자동에 맡기면 유지보수가 편합니다.
- **PR 리뷰와 문서화를 하나로 묶기**  
  에이전트가 코드 변경을 요약해 Reladraw 다이어그램을 갱신하도록 하면:
  - 시스템 다이어그램이 항상 최신 상태에 가깝게 유지됩니다.
  - 강의에서는 “코드 → 다이어그램 → 에이전트” 삼각 관계를 보여줄 수 있습니다.

오늘 신호를 모아보면, **“에이전트를 더 많이 돌리자”가 아니라 “어디까지 맡기고, 어떻게 기록·평가·시각화할 것인가”**가 중심 축입니다. 브라우저 자동화로 결과물을 고정된 영상으로 남기고, Atlas로 전체 맥락을 히스토리에 붙이며, Jev 래퍼와 Reladraw로 평가와 구조를 수치·텍스트 다이어그램으로 재현 가능하게 만드는 흐름이 이어집니다.
