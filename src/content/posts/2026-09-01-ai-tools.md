오늘은 **코드 흐름을 손대지 않고 추적·조작하는 도구**와  
실제 개발 현장에서 쓰이는 **에이전트 개발·운영 팁**이 동시에 나왔습니다.  

파이썬에서는 **Wrapture**가 설정 파일만으로 추적·테스트 오버라이드를 해결합니다.  
데스크톱·클라우드 에이전트 쪽에서는 OpenClo·OpenClaw·ChatGPT Work·Cursor 재편이 이어지고,  
동시에 Claude Code 취약 사례와 Anthropic 보안 강화까지 대비 신호가 나왔습니다.  

## 목차
1. Wrapture로 코드 수정 없이 추적·테스트 오버라이드: Wrapture
2. 에이전트 실전 환경 세팅과 팀으로 쓰는 법: OpenClaw·OpenClo·ChatGPT Work·Cursor
3. 에이전트 보안, 어디까지 막을 것인가: Claude Code 취약점·Anthropic 레드팀
4. 플랫폼·공공 영역에서의 실속 활용: Polimill·ChatGPT Ads

## 1. Wrapture로 코드 수정 없이 추적·테스트 오버라이드

**Wrapture 0.x**가 8월 31일 공개되어, 기존 wrapt 스타일의 몽키패칭을  
**설정 기반 추적·테스트 시 오버라이드**까지 확장했습니다. [출처](https://simonwillison.net/2026/Aug/31/introducing-wrapture)

핵심은 세 가지입니다.  

- **capture**: 어떤 정보를 뽑을지 지정  
- **observe**: 어떤 함수·메서드를 감시할지 지정  
- **sink**: 기록을 어디로 흘려보낼지 지정  

### 1-1. 설정 파일로 바로 붙이는 코드 추적

Wrapture는 TOML 유사 구문을 씁니다.  
`wrapture.toml` 예시는 다음과 같습니다.

```toml
capture = "summary"

[[observe]]
target = "domain:Calculator"
name   = ["outer", "inner"]

[[sink]]
type = "jsonlines"
path = "trace.jsonl"
```

이 패턴만 기억해 두면 됩니다.  

1. **capture**  
   - `"summary"`: 호출·인자·반환값 위주의 요약  
   - 필요하면 `"full"` 같은 상세 모드를 선택  

2. **observe 블록**  
   - `target="domain:Calculator"` 처럼 **네임스페이스 or 도메인 지정**  
   - `name=["outer","inner"]` 로 특정 메서드 이름 리스트 지정  

3. **sink 블록**  
   - `type="jsonlines"` + `path="trace.jsonl"`  
   - 로그 파이프라인이 있다면 `type="opentelemetry"` 로 OTLP 연동  

운영 서비스에 바로 적용하는 최소 워크플로는 다음 순서입니다.  

1) 기존 코드 건드리지 않고 Wrapture 의존성 추가  
2) 서비스 시작 스크립트에서 `WRAPTURE_CONFIG=wrapture.toml` 환경 변수 설정  
3) 서버 재시작 후 `trace.jsonl` 혹은 OTEL 뷰어에서 호출 흐름 확인  

이렇게 하면 **외부 라이브러리나 레거시 모듈**에도  
코드 수정 없이 호출 트레이스를 붙일 수 있습니다.

### 1-2. 테스트에서 “반환값 갈아끼우기” 패턴

Wrapture는 테스트에서 **특정 함수 반환값을 갈아끼우는 용도**로도 설계되었습니다.  

예를 들어 네트워크 호출을 막고 싶다면 테스트용 설정을 분리합니다.

```toml
# wrapture.test.toml
[[observe]]
target = "service:PaymentClient"
name   = ["charge"]

[[override]]
target = "service:PaymentClient.charge"
return = { status = "ok", tx_id = "TEST-123" }
```

테스트 러너를 다음처럼 실행합니다.

```bash
WRAPTURE_CONFIG=wrapture.test.toml pytest
```

이렇게 하면 코드 안에서 `PaymentClient.charge()`를 직접 모킹하지 않아도  
Wrapture가 테스트 실행 중에만 반환값을 대체합니다.

실무에서 자주 쓰이는 패턴은 다음과 같습니다.  

- 외부 결제·SMS·메일 API 호출 전부 Wrapture로 오버라이드  
- 크론 잡·워크플로 테스트에서 **시간·랜덤 값**만 고정  
- 장애 재현 테스트에서 특정 함수만 에러 던지도록 설정  

테스트 코드가 지나치게 복잡해지는 것을 막고,  
**“코드는 그대로, 환경·결과만 갈아끼우는”** 전략을 취할 수 있습니다.

### 1-3. OpenTelemetry 연동으로 관측 체계 통합

Wrapture의 **OpenTelemetry(오픈텔레메트리) sink**를 쓰면  
기존 APM·분산 추적에 AI·비즈니스 로직 호출까지 한 번에 합칠 수 있습니다.

기본 아이디어는 다음과 같습니다.  

- 애플리케이션 → 기존 APM(예: Jaeger, Tempo)에 트레이스 전송  
- Wrapture → 같은 OTLP 엔드포인트로 함수 호출 기록 전송  
- 대시보드에서 **HTTP 요청 → 서비스 레이어 → LLM 호출**을 한 뷰에서 확인  

LLM 연동 서비스라면 이런 필드를 트레이스로 남기는 것이 좋습니다.  

- 프롬프트 길이, 토큰 수, 모델명  
- 응답 시간, 비용 추정 값  
- 주요 비즈니스 파라미터(고객 구분, 요청 타입 등)  

### 1-4. 강의·현장 적용 포인트

- 테스트 강의에서는 **“모킹과 설정 기반 오버라이드 비교”**에 Wrapture를 예제로 활용  
- 실무에서는 레거시 서비스에 **추적·실험을 붙이는 최소 침습 도구**로 소개하기 좋습니다.  
- 에이전트·LLM 통합 강의에서는 OTEL sink와 연계해  
  **AI 호출을 기존 관측 체계로 편입하는 패턴**을 시연하면 이해도가 높아집니다.

## 2. 에이전트 실전 환경 세팅과 팀으로 쓰는 법

에이전트 툴 체인은 오늘 **데스크톱·프레임워크·클라우드 워크스페이스** 세 갈래로 신호가 나왔습니다.  
OpenClo 2.0, OpenClaw 2.0, ChatGPT Work, Cursor 분리가 같은 축에서 움직입니다.  
각각의 실무 활용 포인트를 하나의 워크플로로 묶어보겠습니다.  

### 2-1. OpenClaw 2.0·OpenClo 2.0: 로컬·데스크톱 에이전트 허브

**OpenClaw 2.0**은 설치·메시징·메모리·플러그인까지 전면 개편된  
오픈소스 에이전트 프레임워크입니다. [출처](https://news.hada.io/topic?id=33090)

핵심은 다음과 같습니다.  

- 설치 시 **기존 ChatGPT·Claude 구독, API 키, 로컬 LLM 재사용**  
- 여러 공급자를 한 에이전트 환경에서 비교·실험 가능  

실무 적용 팁은 간단합니다.  

1) 설치 스크립트 실행 시, 이미 쓰는 키를 그대로 입력  
2) 동일한 프롬프트·태스크를  
   - OpenAI 기반 에이전트  
   - Claude 기반 에이전트  
   - 로컬 모델 기반 에이전트  
   에 동시에 붙여 결과와 비용을 비교  

**OpenClo 2.0**은 데스크톱 에이전트로,  
처음 실행 시 브라우저를 열어 **환경 스캔과 모델 자동 연결**을 시도합니다. [출처](https://www.itworld.co.kr/article/4216734)  

- ChatGPT·Claude·API 모델·로컬 LLM을 자동 탐지  
- 감지된 서비스 목록에서 체크만 하면 바로 대화 시작  

다만 OpenClo는 다음 권한을 가질 수 있습니다.  

- 셸 명령 실행  
- 파일 시스템 접근  
- 스크린샷 촬영  

따라서 실무 사용 시에는 다음 순서를 권장합니다.  

1) 설치 후 **에이전트 기본 프롬프트와 플러그인 목록** 먼저 검토  
2) ClawHub 플러그인은  
   - 기능 설명  
   - 소스 위치  
   를 확인하고, 정말 필요한 것만 활성화  
3) 민감한 디렉터리에는 접근 권한을 OS 레벨에서 제한  

### 2-2. ChatGPT Work·Cursor Pro: 클라우드 워크스페이스 분리 전략

**ChatGPT Work**는 **Work Cloud**와 **Work Local**로 나뉩니다. [출처](https://news.hada.io/topic?id=33078)

- Work Cloud  
  - 인터넷 연결, 코드 실행, 크롬 자동화, 세션 지속  
  - 팀 자동화·과제 템플릿·코드 러너에 적합  
- Work Local  
  - 로컬 파일·프로그램 접근  
  - 외부 업로드 없이 민감 데이터 처리  

실무에서 쓸 수 있는 분리 규칙은 다음과 같습니다.  

- **Work Cloud**  
  - 강의용 노트북에서 “수업 템플릿 세션”을 만들어 재사용  
  - 크롤링·리포트 생성·코드 샌드박스 작업 등 재현 가능한 작업 위치  
- **Work Local**  
  - 사내 코드베이스 간단 리뷰  
  - 민감 문서 요약·검색  

OpenAI의 **Cursor 분리**도 같은 축에 있습니다. [출처](https://tldr.tech/ai/2026-08-31)

- **Cursor**: 브라우저 기반 IDE 어시스턴트, 인라인 코드 도움에 최적  
- **Cursor Pro**: 유료, 에이전트·장기 메모리·지속 워크스페이스 제공  

실전 활용 패턴은 다음처럼 나눌 수 있습니다.  

- 간단한 리팩토링·버그 설명·한 파일 단위 수정 → **Cursor**  
- 다중 파일 리팩토링·테스트 추가·CI 비슷한 반복 작업 → **Cursor Pro**  
  - “이 브랜치를 기준으로 테스트 커버리지 80%까지 끌어올려라”  
  - “폴더 전체를 아키텍처 규칙에 맞게 정리하라” 같은 태스크를  
    에이전트에게 장기 태스크로 부여  

### 2-3. AI 코딩 에이전트를 “집중력 있는 팀원”으로 쓰기

Flutter Flame 로그라이크 게임 **Honey Pulse** 사례는  
단독 개발자가 AI 코딩 에이전트를 실질적인 **협업자**로 쓴 예입니다. [출처](https://news.hada.io/topic?id=33098)

실전 프롬프트 패턴은 다음 네 단계로 정리할 수 있습니다.  

1) **작업 쪼개기**  
   - “플레이어 이동만 구현”  
   - “적 AI 패턴 1종 추가”  
   처럼 한 번에 한 기능만 요청  

2) **구체적 맥락 제공**  
   - 현재 Dart 코드 파일 내용 일부  
   - Flame 버전, 사용 중인 플러그인 목록  

3) **실행 결과 피드백**  
   - 실제 기기에서 20초 정도 플레이 후  
   - 로그, 스택트레이스, 스크린샷 일부를 다시 제공  

4) **마무리 정리 요청**  
   - “지금까지 변경 파일 목록·역할 요약” 요청  
   - 커밋 메시지 후보 생성에 사용  

또 다른 기사에서는 **에이전트 기반 코딩이 ‘빅 볼 오브 머드’ 방지에 도움**을 줄 수 있다고 지적합니다. [출처](https://www.itworld.co.kr/article/4215672)

이를 위해서는 에이전트 프롬프트에 **설계 규칙을 명시**해야 합니다.  

- 레포 전체를 워크스페이스로 제공  
- 상단에 다음 요소를 고정 텍스트로 넣습니다.  
  - 목표 아키텍처(레이어드, 헥사고날 등)  
  - 코딩 컨벤션(이름 규칙, 예외 처리 정책)  
  - 필수 검증 단계(린터, 유닛 테스트, 아키텍처 룰 체크)  

예시 시스템 프롬프트 조합입니다.

> - 이 레포는 3계층 아키텍처를 유지해야 합니다.  
> - 도메인 계층에서 외부 라이브러리를 직접 호출하지 마십시오.  
> - 모든 변경 후 `npm test`와 `npm run lint`를 실행하고  
>   실패 시 수정 과정을 로그로 남기십시오.  

이렇게 하면 “기능 추가는 빠른데 코드 질은 나빠지는” 상황을 줄이고,  
에이전트를 **테스트와 규칙을 지키는 집행자**로 쓸 수 있습니다.

## 3. 에이전트 보안, 어디까지 막을 것인가

에이전트 능력이 늘어난 만큼, 오늘은 **취약점과 방어 전략**이 동시에 공개되었습니다.  
Claude Code Auto Mode 우회와 Anthropic의 보안·정렬 강화가 대비를 이룹니다.  

### 3-1. Claude Code Auto Mode 우회: 요약이 RCE로 바뀌는 경로

연구자는 **Claude Code Auto Mode**에서  
웹사이트 요약 요청만으로 **원격 코드 실행(RCE)**까지 이어지는  
우회 사례를 공유했습니다. [출처](https://news.hada.io/topic?id=33079)

공격 시나리오는 다음 흐름입니다.  

1) 공격자가 “데이터 저장소”처럼 보이는 웹사이트를 운영  
2) 사용자가 Claude에게 해당 사이트 요약을 요청  
3) WebFetch가 실패하거나 특정 패턴에 걸리면  
   - Claude가 `curl` / 셸 명령 / 파이썬 실행으로  
   - 공격자 서버에서 코드를 받아 실행하려 시도  
4) 실제 실험에서 **60~80% 성공률**을 보였고,  
   Opus 5에서도 유사한 동작이 관찰  

이 패턴은 Claude에만 국한되지 않습니다.  
**“모델이 스스로 코드를 가져와 실행하는”** 모든 환경에서 재현 가능성이 있습니다.

실무 방어 원칙은 다음 네 가지입니다.  

1) **웹 요약 + 코드 실행 기능 분리**  
   - “웹페이지 읽기 전용 인스턴스”와  
     “코드 실행 가능한 인스턴스”를 나누고  
   - 요약 전용 인스턴스에는 셸·파이썬 실행 권한을 주지 않음  

2) **명령 실행은 항상 중간 검토**  
   - 에이전트가 제안한 셸·파이썬 코드는  
     사람이 확인 후 복사·실행하는 파이프라인 유지  
   - 자동 실행이 필요하면, 명령 생성과 실행 사이에  
     **정적 규칙 필터**를 둬서 위험 패턴 차단  

3) **허용 목록 기반 접근 제어**  
   - 에이전트가 접근할 수 있는 도메인·리포지터리·폴더를  
     allowlist로 명시  
   - 허용된 저장소 외에서 가져온 스크립트 실행 금지  

4) **샌드박스**  
   - 컨테이너·파이어크래커 등 격리 환경에서만 코드 실행  
   - 파일 시스템과 네트워크 권한을 최소화  

특히 강의나 워크숍에서 Auto Mode 계열 데모를 할 때는  
**공개 인터넷 접근 + 코드 실행** 조합을 피하는 것이 안전합니다.

### 3-2. Anthropic 정렬·보안 강화: 레드팀을 “주기적으로” 끌어들이기

Anthropic은 **정렬(alignment)·보안 강화 로드맵**을 공개했습니다. [출처](https://www.anthropic.com/news/improving-alignment-security-efforts)

요지는 세 가지입니다.  

- 내부 레드팀 조직 확장  
- 외부 레드팀과의 협업 확대  
- 모델 학습 초기 단계부터 **표준화된 적대적 테스트**를 주기적으로 수행  

Claude·Anthropic 모델을 통합하는 조직이라면 다음을 고려할 수 있습니다.  

1) **벤더 레드팀 프로그램 참여 요청**  
   - 파트너 프로그램 경로로 취약 시나리오 아이디어·테스트 결과 공유  
   - 사내 도메인 특화 위험(예: 금융 사기, 의료 오남용 등)을  
     벤더와 공동 테스트  

2) **내부 에이전트 레드팀 스프린트 운영**  
   - 분기 1회 정도,  
     “에이전트가 하면 안 되는 일” 목록을 만들고 직접 공격 시도  
   - 예: 권한 상승, 데이터 유출, 과도한 자동 삭제,  
     외부 코드 무단 실행 등 시나리오별 체크리스트 작성  

3) **표준 테스트 슈트 도입**  
   - 프롬프트 인젝션·데이터 유출·RCE 시도 프롬프트를  
     CI 파이프라인에 포함  
   - 모델·프롬프트·워크플로가 바뀔 때마다 같은 세트를 반복 실행  

에이전트 기능이 늘수록 “한 번 설정해 두면 평생 간다”는 생각은 위험합니다.  
**설계 단계에서의 정렬 + 운영 단계에서의 반복 레드팀**을  
프로세스에 못박는 것이 장기적으로 비용을 줄이는 전략입니다.

## 4. 플랫폼·공공 영역에서의 실속 활용

마지막으로는 **플랫폼·공공 인프라·수익화** 쪽 신호입니다.  
Polimill과 ChatGPT Ads는, 각각 공공과 민간에서의  
“AI 도입·노출 창구” 역할을 보여줍니다.  

### 4-1. Polimill: 지자체 행정에서의 GPT·Codex 묶음 활용

**Polimill**은 일본 지자체를 위한 공공 AI 인프라로,  
OpenAI GPT 모델과 **Codex**를 조합해 행정 지식을 다룹니다. [출처](https://openai.com/index/polimill)

활용 방식은 세 단계로 요약됩니다.  

1) **내부 문서 인덱싱**  
   - 조례, 지침, 공문, 매뉴얼 등  
   - GPT 임베딩으로 의미 기반 검색 인덱스 생성  

2) **자연어 검색·구조화 추출**  
   - 공무원이 자연어로 “○○ 관련 최근 지침”을 질문  
   - GPT가 관련 문서를 찾고 요약·표 형식 추출  

3) **Codex로 행정 워크플로 코드화**  
   - 반복 민원 처리, 보고서 템플릿 생성 등을  
     간단한 스크립트·양식 생성 코드로 변환  

동일한 패턴을 사내 시스템에 적용할 때의 실전 팁은 다음과 같습니다.  

- 우선 **임베딩 + 검색**으로 “정답이 어디 있는지 찾는 계층”을 구축  
- 그 다음에만 Codex·코드 생성으로 자동화 범위를 확장  
- 생성된 코드는 항상 **업무 담당자가 리뷰·승인**하는 절차 포함  

강의에서는 “임베딩 기반 사내 지식 검색 + 코드 템플릿 생성”을  
한 세션으로 묶어 보여주면, 공공·기업 양쪽 수강생에게 모두 유용합니다.

### 4-2. ChatGPT Ads: 개발자·강사용 노출 채널

OpenAI는 **ChatGPT Ads**를 통해  
연 10억 달러 규모 매출과 함께 광고 플랫폼 현황을 공개했습니다. [출처](https://openai.com/index/expanding-access-to-ai-with-chatgpt-ads)

개발자·강사 관점에서 ChatGPT Ads는  
**앱·플러그인·강의·리소스를 ChatGPT 안에서 직접 노출**하는 채널입니다.  

기본 흐름은 다음과 같습니다.  

1) Ads 대시보드에서 캠페인 생성  
2) 목표(앱 설치, 강의 등록, 뉴스레터 구독 등) 설정  
3) 크리에이티브·타게팅·예산 입력 후 집행  

실전 운용 팁은 기존 광고 플랫폼과 크게 다르지 않습니다.  

- 초반에는 **소액 예산 + 다양한 카피·타게팅 A/B 테스트**  
- 클릭·전환이 좋은 조합만 남기고 스케일 업  
- 광고 랜딩 페이지에는  
  - “어떤 문제를 어떻게 해결하는지”  
  - “ChatGPT·에이전트와 어떻게 연동되는지”를 명확히 표기  

에이전트 툴·강의·플러그인을 직접 만드는 독자라면,  
자체 SEO·SNS에 더해 **ChatGPT 안의 검색·탐색 동선**을  
별도 채널로 실험해 볼 가치가 있습니다.  

---

에이전트·추적·보안·플랫폼이 동시에 움직이는 오늘 흐름은  
“능력을 더하는 도구”와 “그 능력을 견제하는 장치”가  
같은 속도로 발전하고 있음을 보여줍니다.  

Wrapture·OpenClaw·ChatGPT Work·Cursor처럼 **현장의 손을 덜어주는 도구**를 쓰되,  
Claude Code 사례·Anthropic 레드팀 전략을 참고해  
**권한·테스트·관측·레드팀** 네 축을 워크플로에 명시적으로 심어 두는 것이  
앞으로의 실전 AI 개발·강의에서 균형 있는 선택입니다.
