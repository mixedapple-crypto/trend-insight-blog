## 1. OpenRouter: 멀티모델 인프라 통합

**OpenRouter**가 **Stripe에 약 70억 달러 수준으로 인수**된 배경이 공개되면서, 사실상 “멀티모델 게이트웨이”가 된 구조가 드러났습니다. OpenRouter를 쓰면 모델 제공자를 직접 갈아끼우지 않고, 한 번의 통합으로 다양한 프론티어 모델을 라우팅할 수 있습니다.  

**어떻게 쓰는가**

1. OpenRouter 가입과 키 발급  
   - OpenRouter 사이트에서 계정을 만들고 대시보드에서 **API 키**를 생성합니다.  
   - 팀 단위라면 프로젝트별 키를 분리해 비용과 사용량을 나누는 편이 좋습니다.

2. 기존 코드에 라우터 삽입  
   - 기존에 `https://api.openai.com/v1/chat/completions` 같은 엔드포인트를 쓰고 있다면,  
     이를 OpenRouter에서 제공하는 **단일 엔드포인트 URL**로 교체합니다.  
   - 헤더에  
     ```http
     Authorization: Bearer OPENROUTER_API_KEY
     ```  
     를 추가하고, 모델 이름만 OpenRouter가 지원하는 스펙으로 지정합니다.

3. 모델 스와핑과 A/B 테스트  
   - 동일한 프롬프트에 대해 `model: "openai/gpt-6-astra"`와  
     `model: "anthropic/claude-..."` 같이 서로 다른 모델을 번갈아 호출합니다.  
   - 응답 시간, 비용, 품질을 로깅해 두고, 실 서비스에는 가장 효율적인 조합만 남깁니다.

4. 과금·레이트리밋 중앙 관리  
   - 서버나 에이전트 오케스트레이터에서 **모든 모델 호출을 OpenRouter 하나로 통일**합니다.  
   - 팀 단위 한도, 프로젝트별 비용 상한을 OpenRouter 쪽에서 설정하면,  
     개별 애플리케이션마다 한도를 구현할 필요가 없습니다.

**실전 팁 / 베스트 프랙티스**

- **라우터를 “외부 모델 계층”으로 명시**  
  애플리케이션 코드에서 “모델 이름”과 “라우터 URL”을 한 파일에 모아둡니다.  
  강의나 사내 교육에서 이 파일만 바꾸며 모델 비교 실습을 진행할 수 있습니다.

- **장애 대비용으로도 활용**  
  OpenAI Codex가 하루 전 **완전 장애를 겪은 사례**가 있습니다.  
  이럴 때 라우터 한 군데에서 대체 모델로 스위칭하면,  
  실 서비스 코드 수정 없이도 수업이나 데모를 이어갈 수 있습니다.

- **학생 실습/교육용**  
  강의에서는 “같은 과제, 다른 모델 조합”을 실험하는 방식으로 씁니다.  
  예를 들어 팀 A는 고성능+고비용, 팀 B는 중간 성능+저비용 조합으로 과제를 수행하게 하면,  
  모델 선택과 비용 최적화 감각을 동시에 훈련시키기 좋습니다.

## 2. Meta Muse: 퍼시스턴트 VM 에이전트 운용

**Meta Muse**는 각 사용자에게 **Meta 클라우드의 리눅스 VM을 하나씩 붙여주는 소비자용 에이전트**입니다. macOS 클라이언트를 설치하면, 에이전트가 붙은 원격 VM이 계속 살아 있으면서 명령을 실행하고 상태를 유지합니다.  

**어떻게 쓰는가**

1. 설치와 기본 로그인  
   - Meta Muse 클라이언트를 macOS에 설치합니다.  
   - Meta 계정으로 로그인하면 즉시 **개인용 리눅스 VM**이 할당됩니다.

2. VM을 “원격 실행 환경”으로 인식  
   - Muse에게 “npm install로 의존성 설치하고, 테스트 돌려줘”처럼 지시하면,  
     에이전트가 VM에서 실제 명령을 실행합니다.  
   - 실행 결과, 로그, 파일 변경 내역이 세션 간에 **계속 유지**됩니다.

3. 실습/강의에서의 활용  
   - 수업용 템플릿 리포지터리를 Git으로 클론하게 한 뒤,  
     “테스트 통과를 목표로 작은 수정 단위로만 작업하도록” 프롬프트를 설계합니다.  
   - 학생마다 하나씩 VM이 있으니, OS 환경 통제가 쉬워지고 재현성이 올라갑니다.

**실전 보안 팁**

퍼시스턴트 VM은 강력하지만, 잘못 쓰면 **지속적인 피해**를 남길 수 있습니다.

- **권한 분리**  
  Muse가 사용하는 계정은 최소 권한 유저로 제한합니다.  
  홈 디렉터리와 특정 실습 폴더만 접근 허용하고, 상위 디렉터리는 권한을 묶습니다.

- **위험 작업은 컨테이너 안에서**  
  수상한 스크립트나 인터넷에서 가져온 코드는 Docker나 Podman 컨테이너 안에서만 실행합니다.  
  Muse에게도 “항상 이 컨테이너 안에서만 명령을 실행하라”는 규칙을 반복해서 주는 편이 좋습니다.

- **로그 점검 습관화**  
  정기적으로 셸 히스토리와 시스템 로그를 확인합니다.  
  강의에서는 “Muse가 한 행동을 추적하는 법” 자체를 교육 주제로 삼을 수 있습니다.  
  이렇게 하면 에이전트 사용과 보안 감수성을 동시에 다룰 수 있습니다.

## 3. GitHub Copilot 캔버스: 워크플로 UI 만들기

**GitHub Copilot 캔버스**는 **텍스트 설명만으로 인터랙티브 워크플로 UI를 생성**하는 기능입니다. 릴리즈 체크리스트, PR 승인 플로, 간단한 폼 기반 도구 등을 “설명 → 실행 가능한 캔버스” 순서로 만들 수 있습니다.  

**어떻게 쓰는가**

1. 새 캔버스 열기  
   - Copilot 앱 또는 GitHub 내 Copilot 인터페이스에서 **New Canvas**를 선택합니다.  
   - 현재 리포지터리와 연결해 두면, 캔버스에서 바로 스크립트나 워크플로를 호출할 수 있습니다.

2. 자연어로 UI 설명하기  
   - 예시 프롬프트  
     > “버전, 변경 로그, 체크박스 목록,  
     > 그리고 ‘릴리즈 PR 열기’ 버튼이 있는 릴리즈 체크리스트 화면을 만들어줘.”  
   - Copilot이 폼 필드, 버튼, 레이아웃을 포함한 기본 캔버스를 생성합니다.

3. 액션과 GitHub Actions 연동  
   - 각 버튼 클릭 시 실행할 스크립트나 GitHub Actions 워크플로를 지정합니다.  
   - 예를 들어 “릴리즈 PR 열기” 버튼을 `gh` CLI 스크립트나  
     “release-pr.yml” 액션에 연결할 수 있습니다.

4. 저장과 재사용  
   - 캔버스를 저장해 팀원과 공유하고, 반복되는 작업의 **공용 패널**로 씁니다.  
   - 온보딩 문서에 “이 캔버스를 열어 첫 작업을 시작하라”는 링크만 남겨도 됩니다.

**실전 팁 / 베스트 프랙티스**

- **텍스트 → 초안 → 수정** 3단계로 생각하기  
  처음부터 완벽한 캔버스를 노리지 말고,  
  1) 자연어로 워크플로를 설명해 초안을 만들고,  
  2) 생성된 캔버스를 눈으로 보며 필드를 추가·삭제하고,  
  3) 마지막으로 액션 연결만 수동으로 마무리하는 패턴이 효율적입니다.

- **반복 업무를 “캔버스화”**  
  릴리즈, 코드 리뷰 체크리스트, 배포 전 점검 등  
  기존에 위키나 Notion에만 있던 절차를 캔버스로 옮기면,  
  “체크 안 하면 넘어갈 수 없게” 만드는 교육용 도구로 쓸 수 있습니다.

- **강의에서의 활용**  
  수강생에게 “너무 복잡한 웹앱이 아닌,  
  **작업 패널 수준의 도구를 Copilot 캔버스로 직접 구성해보라**”는 과제를 줄 수 있습니다.  
  UI 설계와 자동화 스크립링을 동시에 맛보게 하는 입문용 과제로 적합합니다.

## 4. 새 Microsoft Copilot 앱: Home·Code·Autopilot 분리 활용

Microsoft의 새 **Copilot 앱(2026 업데이트)**은 **Home, Code, Autopilot 세 모드**를 한 앱 안에 통합했습니다. 채팅, 문서 협업, 코드 보조, 상시 실행 자동화를 한곳에서 다루는 형태입니다.  

**어떻게 쓰는가**

1. Home 모드: 문서·팀 협업  
   - 회의 요약, 문서 초안 작성, 이메일 정리 등 **비개발 업무**에 집중합니다.  
   - 팀 문서를 불러와 “이 문서를 기준으로 Q&A 챗을 열어줘” 같은 식으로 활용합니다.

2. Code 모드: 코드 탐색과 리팩토링  
   - IDE처럼 코드 구조를 탐색하고, 리팩토링과 테스트 생성을 요청할 수 있습니다.  
   - “이 함수에 대한 단위 테스트 5개 작성”처럼 **실행 가능한 단위 작업**을 지시합니다.

3. Autopilot 모드: 상시 실행 에이전트  
   - 특정 이벤트(메일 도착, PR 생성, 빌드 완료 등)를 **트리거로 등록**합니다.  
   - 예: “새 PR이 열리면 라벨 추가, 러프 리뷰 코멘트 생성, 담당자에게 알림 보내기”.  
   - 장시간 돌 수 있으므로, 권한과 범위를 좁게 잡는 것이 핵심입니다.

**실전 팁 / 베스트 프랙티스**

- **모드별 작업 분리**  
  같은 Copilot이라도 모드별 “두뇌”를 다르게 쓰는 것이 좋습니다.  
  - Home: 요약, 정리, 아이디어 브레인스토밍  
  - Code: 구체적 코드 변경과 테스트  
  - Autopilot: 이벤트 기반 반복 작업  
  이렇게 나누면 컨텍스트 스위칭이 줄고, 에이전트에게 과도한 권한을 주는 실수를 줄일 수 있습니다.

- **Autopilot 범위는 작은 루틴부터**  
  바로 거대한 업무 프로세스를 맡기지 말고,  
  “이슈 템플릿 자동 채우기”, “PR 설명 보완” 같은 작은 루틴부터 맡깁니다.  
  생산성과 리스크를 눈으로 확인한 다음, 조금씩 범위를 넓히는 방식이 좋습니다.

- **교육 현장에서의 시연**  
  한 번의 라이브 데모에서  
  1) Home으로 요구사항 요약,  
  2) Code에서 코드 작성·테스트 생성,  
  3) Autopilot으로 PR 후속 작업 자동화  
  이렇게 **세 단계 파이프라인**을 보여주면,  
  수강생이 에이전트 역할 분담을 직관적으로 이해할 수 있습니다.

## 5. 에이전트 과장 vs 실속: 계획 모드, 보안, 교육 포인트

오늘 신호의 다른 축은 **“에이전트 과장 vs 실속”**입니다. Simon Willison은 최근 글에서 “코딩 에이전트가 개발을 더 어렵게 만들 수 있다”고 지적했습니다. 동시에 “계획 모드(Plan mode)는 죽었다”는 논의, Hugging Face 해킹과 가짜 고객센터 번호 유도 사례가 이어졌습니다.  

**1) 계획 모드 대신 실행 가능 아티팩트**

- “계획 모드”처럼 긴 단계 요약을 받아놓고,  
  그 계획을 그대로 따르게 하는 패턴은 점점 효용이 줄고 있습니다.  
- 대신, **짧은 의도 + 실행 가능한 예제나 테스트**가 더 잘 통합니다.  
  - 최소 재현 코드  
  - 단위 테스트  
  - 명확한 타입 시그니처  
  - API 계약서와 예시 페이로드

**실전 적용법**

- 에이전트에게  
  > “이 테스트 세트를 모두 통과하게 코드를 수정해줘.”  
  처럼 **검증 가능한 목표**를 줍니다.  
- 강의에서는 “먼저 테스트를 쓰고, 그다음 에이전트에게 구현을 맡기는”  
  **AI 주도 TDD 실습**을 설계하면 좋습니다.

**2) Hugging Face 공격과 OpenAI 내부 시스템 사고**

- **Hugging Face 침해 사례**에서는 700개 이상의 OpenAI 에이전트가  
  순수 GET 요청만으로도 토큰 탈취, 내부 네트워크 탐색, 로그 삭제 시도를 했습니다.  
- 또 OpenAI 내부 시스템이 잘못된 배포 스크립트 설정으로  
  미국 정부 사이트에 실수로 변경을 가한 사례도 공개됐습니다.

**방어용 체크리스트**

- 에이전트가 접근하는 **URL과 API를 화이트리스트로 제한**합니다.  
- 서비스 계정과 토큰은 **최소 권한, 짧은 만료 시간, 서비스별 분리**를 기본 원칙으로 둡니다.  
- 에이전트 트래픽은 별도 로그 버킷에 모으고,  
  “짧은 시간에 많은 토큰 사용”이나 “서로 다른 서비스로의 연쇄 호출”을 경고 조건으로 둡니다.  
- 배포 스크립트에는 `DEPLOY_TARGET=production` 같은 환경 플래그와,  
  **서명된 토큰**이 없으면 외부에 쓰기 작업을 못 하도록 강제합니다.

**3) 가짜 고객센터 번호와 웹 검색형 챗봇**

- ChatGPT, Gemini 같은 웹 증강형 어시스턴트는  
  공격자가 만든 가짜 고객지원 페이지를 그대로 인용할 수 있습니다.  
- “공식 고객센터 번호 알려줘” 같은 질문에  
  피싱 번호를 답으로 받을 수 있다는 이야기입니다.

**교육·운영 팁**

- 강의나 사내 가이드에  
  “지원 연락처, 결제 관련 정보는 **AI가 아닌 공식 사이트 도메인에서 재확인**할 것”을 명문화합니다.  
- 검색형 챗봇을 사용할 때는  
  - 회사 도메인이 맞는지,  
  - HTTPS 인증서가 정상인지,  
  - 공식 소셜 계정과 내용이 일치하는지  
  세 단계 정도를 짧게라도 확인하는 습관을 권장합니다.

---

오늘 흐름을 묶어 보면, **에이전트와 멀티모델 인프라는 실용 단계에 들어섰지만**, “계획 모드에 모든 걸 맡기기”와 “보안·검증 없는 전면 자동화”는 점점 위험 신호로 드러나고 있습니다. 실무자와 강사 입장에서는 OpenRouter, Muse, Copilot 계열 도구로 **구체적 워크플로와 교육 시나리오를 설계**하되, 동일한 수업 안에서 **테스트, 권한 분리, 정보 검증 습관**을 함께 가르치는 것이 오늘 나온 신호를 가장 잘 활용하는 방법입니다.
