## 1. 에이전트와 코드 품질: 평가·검증 파이프라인

**Google**이 **Gemini Enterprise Agent Platform**과 **Google ADK(Agent Developer Kit)**를 기반으로 한 에이전트 평가 레퍼런스를 공개했습니다. 멀티턴 에이전트의 행동을 추적하고, 시나리오 테스트와 대시보드까지 이어지는 **지속 평가 파이프라인**입니다. [출처](https://developers.googleblog.com/evaluating-ai-agents-moving-past-the-vibe-check)

**어떻게 쓰는가**

1. **추적(instrumentation) 깔기**
   - 에이전트 서버에 OpenInference 호환 추적을 심습니다.
   - 각 턴에서 다음을 로그로 남깁니다.  
     - 입력, 출력, 사용 도구, 외부 API 호출 결과  
     - 내부 상태 변화(메모리, 플래너 결정 등)  
   - Python 기반 백엔드라면 미들웨어 형태로 한 번 감싸는 방식이 가장 단순합니다.

2. **시나리오 스위트 작성**
   - 실제 유저 흐름을 기준으로 **대화 시나리오**를 정의합니다.
     - 예: “환불 요청 처리”, “HR 문의 응대”, “버그 리포트 triage” 등.
   - 각 시나리오에 대해 다음을 명시합니다.
     - 초기 프롬프트와 환경 상태
     - 기대 결과와 허용 오차
     - 금지 행동(PII 노출, 공격적 언어 등)

3. **CI에 평가 연결**
   - 모델 버전이나 프롬프트, 코드가 바뀔 때마다 아래를 자동 실행합니다.
     - 전체 시나리오 재실행
     - 성공률, 응답 시간, 툴 사용 실패율 집계
     - 안전·정책 위반 카운트
   - 결과를 대시보드로 보내 주 단위 추세를 봅니다.

4. **Anthropic의 독립 평가 활용**
   - **Anthropic**은 **Claude 독립 평가자 프로그램**을 확장하고 있습니다. [출처](https://www.anthropic.com/news/an-update-on-independent-evaluators)
   - 조직 단위로 참여를 신청하거나, 제공되는 평가 리포트를 받아 다음에 활용합니다.
     - 사내 QA 케이스 설계 참고
     - 안전·편향 지표를 사내 목표와 매핑
     - 버전 변경 시 리포트 간 비교

5. **에이전트 기반 코드 검증 루프**
   - 에이전트가 직접 코드를 고치도록 하는 **에이전트 기반 검증** 패턴도 소개되고 있습니다. [출처](https://news.hada.io/topic?id=35443)
   - 기본 루프는 다음 네 단계입니다.
     1) 코드 생성 또는 패치  
     2) E2E 테스트 실행 또는 실제 유저 플로 시뮬레이션  
     3) 실패 로그 분석과 원인 추론  
     4) 코드 수정 후 재실행

**실전 팁 / 베스트 프랙티스**

- **테스트는 “유저 플로” 기준**으로 설계합니다. 유닛 테스트보다, “결제 성공 여부”, “버그 리포트가 올바른 팀에 배정되는지”처럼 실제 흐름을 통째로 검증하는 것이 에이전트에게 더 유효한 피드백이 됩니다.
- 에이전트가 테스트 실패를 보고 **어디를 고쳐야 할지** 이해할 수 있도록,
  - 실패 로그를 구조화(JSON 형태)하고
  - “이 실패 타입이면 어느 디렉터리/모듈을 우선 보라”는 힌트를 프롬프트에 넣습니다.
- 강의에서는 “수동 코드 리뷰”와 “에이전트 기반 검증 루프”를 나란히 보여주면 학습자들이 **품질-생산성 트레이드오프**를 눈으로 비교할 수 있습니다.
- 기업 환경에서는 Google식 시나리오 평가와 Anthropic 독립 평가 리포트를 함께 사용하면, “내부 회귀 테스트”와 “외부 안전 감사”라는 두 축을 한 번에 세울 수 있습니다.

## 2. 인프라 최소화: 맥 수면 토글와 서버 없는 실험

맥북을 덮어도 잠자지 않게 유지해 터미널 기반 AI 작업을 끊기지 않게 하는 **pmset 활용 팁**이 정리되었습니다. Codex CLI, Claude Code, Pi, OpenCode 등 장시간 돌리는 작업에 유용합니다. [출처](https://news.hada.io/topic?id=35460)

여기에, **Simon Willison**이 공개한 **Chirp Pong**은 서버나 WebRTC 없이 두 스마트폰 간에 짧은 오디오 신호만으로 게임 상태를 동기화하는 데모입니다. [출처](https://simonwillison.net/2026/Oct/15/chirp-pong)

**어떻게 쓰는가 – 맥 수면 토글 스크립트**

1. **기본 명령**
   - 수면 방지 켜기:
     ```bash
     sudo pmset -a disablesleep 1
     ```
   - 다시 원래대로:
     ```bash
     sudo pmset -a disablesleep 0
     ```

2. **토글 스크립트 예시**
   ```bash
   #!/bin/zsh

   CURRENT=$(pmset -g | grep disablesleep | awk '{print $2}')

   if [ "$CURRENT" = "1" ]; then
     sudo pmset -a disablesleep 0
     echo "잠자기 다시 활성화"
   else
     sudo pmset -a disablesleep 1
     echo "잠자기 비활성화 (덮어도 깨어 있음)"
   fi
   ```

3. **sudo 비밀번호 없이 사용**
   - `sudo visudo`로 편집 후, 특정 계정과 pmset만 허용합니다.
     ```text
     your_user ALL=(ALL) NOPASSWD: /usr/bin/pmset -a disablesleep *
     ```
   - 이후에는 스크립트 실행만으로 토글됩니다.

4. **자동화**
   - Raycast, Automator, 단축키 앱에 이 스크립트를 등록하면  
     맥북 덮기 직전에 한 번 눌러 활성화할 수 있습니다.

**실전 팁**

- sudoers 설정은 **pmset 명령 하나로만 한정**해야 합니다. `NOPASSWD: ALL` 같은 광범위 허용은 피해야 합니다.
- 장시간 깨어 있는 상태에서는 발열과 배터리 소모가 커집니다.  
  - 가능하면 전원 연결 상태에서만 사용하고,  
  - 작업이 끝나면 `disablesleep 0`을 다시 실행하는 습관을 워크플로에 넣어야 합니다.

**브라우저·모바일 P2P 실험: Chirp Pong**

- Chirp Pong은 **정적 HTML**만으로 돌아가는 2인용 Pong류 게임입니다. 두 폰이 스피커 소리 “chirp”를 주고받으면서 게임 상태를 동기화합니다. [출처](https://simonwillison.net/2026/Oct/15/chirp-pong)
- 사용법은 단순합니다.
  1) 같은 페이지를 두 대의 스마트폰 브라우저에서 엽니다.  
  2) 마이크 권한을 허용합니다.  
  3) 두 기기를 서로 가까이 두고 볼륨을 적절히 맞춥니다.

**실전 팁 / 활용 아이디어**

- 두 기기를 **가까이 두고** 주변 소음을 줄이면 패킷 손실이 줄어듭니다.
- 에이전트나 LLM 앱에서 **“로컬 P2P 동기화”를 가르치는 강의 예제**로 활용할 수 있습니다.
  - 예: “간단한 턴 기반 게임이나 토이 채팅 상태를 chirp 방식으로 동기화해 보자” 같은 프로젝트.
- 서버나 WebRTC 없이도 **저지연 P2P 프로토타입**을 만들 수 있다는 점을 보여주는 데 데모 가치가 큽니다.

**Modal 샌드박스와의 연결**

- 한편, **Modal**은 16억 달러 밸류에이션 시리즈 D와 10억 달러 ARR을 공개하며, **모델 샌드박스 인프라**를 키우고 있습니다. [출처](https://www.latent.space/p/ainews-modals-1b-arr-16b-series-d)
- Modal 대시보드나 CLI에서
  - 런타임과 모델을 선택하고,
  - 코드나 컨테이너를 업로드해
  - **에페메럴 하드웨어** 위에서 실험을 반복합니다.
- Chirp Pong 같은 “저인프라 실험”과 Modal 같은 “고인프라 샌드박스”를 대비해 보여주면, 강의에서 **프로토타입→확장**의 흐름을 설명하기 좋습니다.

## 3. 원격 협업과 교육: Petal, Study Mode, 학계 지원

**Petal**은 CoScreen/ScreenHero를 오픈소스로 재구현한 멀티 커서 페어 프로그래밍 도구입니다. 원 개발팀이 공개했고, 무료로 자체 호스팅할 수 있습니다. [출처](https://petal.live/)

OpenAI는 **ChatGPT Study Mode**와 **GPT-Rosalind 학술 플랜**, Simons Foundation은 수학자를 위한 **AI 연구 지원 프로그램**을 발표했습니다. [출처](https://openai.com/index/teaching-students-to-think-and-learn-through-questions) [출처](https://openai.com/index/introducing-the-rosalind-academic-plan) [출처](https://news.hada.io/topic?id=35428)

**Petal – 어떻게 쓰는가**

1. **설치**
   - GitHub 저장소를 클론합니다.
     ```bash
     git clone https://github.com/kiruna-labs/petal.git
     cd petal
     ```
   - `docker-compose up`으로 서버와 클라이언트를 올리거나, README에 따라 로컬 빌드를 수행합니다.

2. **세션 운영**
   - 서버를 실행하고, 웹 또는 클라이언트 앱에서 세션을 시작합니다.
   - 참여자에게 세션 링크를 공유합니다.
   - 각 참가자는 **자기 커서**로 같은 화면을 동시에 조작할 수 있습니다.

**실전 팁**

- 사내나 수업용 네트워크 안에 Petal을 두면,  
  **코드와 화면이 외부 SaaS로 나가지 않으면서** 실시간 페어 프로그래밍이 가능합니다.
- 강의에서는 “교수 화면만 공유”가 아니라 각 학생에게 한 번씩 커서를 넘겨  
  특정 리팩토링이나 테스트 작성 단계를 직접 수행하게 하면, 참여도가 크게 올라갑니다.

**Study Mode – 질문 중심 학습**

- ChatGPT의 **Study Mode**는 답을 바로 주지 않고,  
  학생에게 **스스로 설명하고 반성(reflection)하도록 유도**하는 모드입니다. [출처](https://openai.com/index/teaching-students-to-think-and-learn-through-questions)
- 수업이나 과제에서 사용할 때는:
  1) 학생이 문제를 풀게 한 다음, Study Mode에서 풀이 과정을 입력하게 합니다.
  2) 모델은 단계별 힌트를 주고, 학생의 중간 생각을 되짚어 보게 합니다.
  3) 교사는 학생의 대화 로그를 보고 **오개념 지점**을 파악합니다.

**실전 팁**

- “힌트 보여주기 전, 학생 답변 1회 필수”를 규칙으로 두면  
  학생이 **수동 복사** 대신 능동적으로 사고하게 만듭니다.
- 브라질 포르투갈어 지원처럼, 한국어 수업에서도  
  학생 모국어로 사고한 뒤 영어 수식/코드로 옮기게 하는 패턴을 활용할 수 있습니다.

**GPT-Rosalind와 Simons Foundation 프로그램**

- OpenAI의 **Rosalind Academic Plan**은 생명과학 연구실에 **GPT-Rosalind** 접근을 후원합니다. [출처](https://openai.com/index/introducing-the-rosalind-academic-plan)
  - 연구실은 프로그램 페이지에서 신청하고,
  - 승인 시 OpenAI 플랫폼이나 API에서 Rosalind 모델을 선택해 사용합니다.
  - 활용 예는 논문 요약, 실험 설계 초안, 프로토콜 초안 생성 등입니다.
- **Simons Foundation**은 Anthropic과 OpenAI와 함께,  
  수학자들의 AI 도입을 위한 **1,500만 달러(약 225억 원)** 규모 지원 사업을 시작했습니다. [출처](https://news.hada.io/topic?id=35428)
  - 공모에 응할 때는
    - 구체적 파일럿 프로젝트
    - 재현 가능한 데이터셋
    - 정확도와 활용도에 대한 평가 지표
    를 제안서에 포함해야 합니다.

**강의·연구 실전 포인트**

- 강의자는 Petal, Study Mode, Rosalind, 지원 사업을 묶어  
  “AI를 쓰는 **연구·교육 워크플로** 한 세트”로 보여주면 설득력이 커집니다.
- 특히 연구실이나 대학 과제에서 **AI 사용 범위**(초안·검산 vs 최종 결과)를 미리 규정하고,  
  Study Mode 로그나 Petal 세션 기록을 **학습 과정 증거**로 활용할 수 있습니다.

## 4. AI 사용 규칙과 법·모델 경제: 거버넌스 실무

미국 잡지 **Current Affairs**가 새 노조 계약에서 **AI가 “생산한” 글·삽화의 게재를 금지**하는 규정을 도입했습니다. AI 도구 자체를 금지한 것이 아니라, **인간 창작을 대체하는 완성물**만 금지 대상입니다. [출처](https://news.hada.io/topic?id=35435)

OpenAI와 로펌 Sullivan & Cromwell이 개발한 **Agreement Analyzer**는 계약서의 문제 조항과 누락된 보호 장치를 자동으로 표시하는 도구입니다. [출처](https://openai.com/index/sullivan-cromwell)

**콘텐츠·팀 규칙 설계 실무**

- Current Affairs 사례는 AI 사용을 다음처럼 구분합니다.
  - 허용: 자료 조사, 아이디어 정리, 초안 보조, 교열
  - 금지: 표기 없이 게재되는 완성 기사·삽화의 직접 생성
- 조직에서 비슷한 규칙을 설계하려면:
  1) “AI 사용 허용 범위” 목록을 작성합니다.  
     예: 리서치 메모, 코드 리뷰 초안, 번역 초안 등.
  2) “금지 항목”을 구체적으로 적습니다.  
     예: 저작권 위험이 있는 완제품, 고객 대면 최종 보고서 자동 생성 등.
  3) **검증 책임자와 승인 절차**를 명시합니다.  
     - 예: 팀 리드 또는 에디터가 최종 책임자,  
       중요 산출물은 “AI 사용 내역”을 내부 티켓에 기록.

**Agreement Analyzer – 법무 워크플로**

- 사용법은 단순합니다.
  1) Analyzer 인터페이스나 연동된 계약 관리 시스템에서  
     검토할 계약서를 업로드합니다.
  2) 도구가
     - 위험 조항
     - 누락된 표준 보호
     - 수정 제안
     을 표시합니다.
  3) 변호사가 이 플래그들을 중심으로 집중 검토를 합니다.

**실전 팁**

- Analyzer의 제안은 **초안**으로 보고,  
  각 조직의 리스크 기준과 관할권에 맞게 노무·법무팀이 2차 검토해야 합니다.
- 교육에서는 이 도구를 “AI의 계약 요약” 예제로 쓰되,  
  “AI가 이렇게 추천했지만 실제로는 이렇게 수정했다”를 함께 보여주면  
  **인간 판단의 위치**를 분명하게 전달할 수 있습니다.

**모델 경제: Distillation 통제**

- Anthropic은 Q3 실적에서 50% 가까운 매출 성장과 더불어,  
  **타사 모델이 Claude 출력을 가져다 학습하는 distillation 사용을 줄였다**고 밝혔습니다. [출처](https://simonwillison.net/2026/Oct/15/anthropic-tells-investors)
- 실무적으로는 API 사업자가 다음을 해야 한다는 신호입니다.
  - **고용량 사용 패턴** 모니터링
  - 비정상적인 출력 스크래핑, 과도한 체인 사용 탐지
  - 약관과 가격 정책에서 distillation 허용 범위와 요금 명시

**실전 팁**

- 자체 모델이나 API를 운영하는 팀은
  - 고빈도, 길이 일정, 체계적 변형이 반복되는 요청 패턴을  
    “잠재적 distillation 신호”로 태깅하는 로그 분석 규칙을 만들 필요가 있습니다.
- 강의에서는 모델 경제 파트에 “distillation은 왜 비용 벡터인가”를 넣으면  
  학생들이 **제공자 입장**에서 레이트 리밋과 가격 차등의 이유를 더 잘 이해합니다.

## 5. ROI와 아키텍처: 프레임워크보다 요구사항

ITWorld는 **파일럿을 넘어 프로덕션에서 AI ROI를 측정하는 프레임워크**를 정리했습니다. 핵심은 **모델이 아니라 워크플로를 가치 단위로 보고, 총비용까지 포함한 ROI를 계산하라**는 점입니다. [출처](https://www.itworld.co.kr/article/4235586)

다른 기사에서는 맥킨지, 딜로이트, Capgemini Resonance AI, Infosys Topaz, TCS AI WisdomNext, Accenture “AI brain” 같은 **대형 벤더 프레임워크**를 그대로 시작점으로 삼지 말고, **요구사항에서 아키텍처를 먼저 도출하라**고 강조합니다. [출처](https://www.itworld.co.kr/article/4235707)

**실전 ROI 계산법**

- ROI 공식:
  - ROI = (가치 − 총비용) / 총비용
- 가치(Value):
  - 시간 절감 × 인건비(loaded cost)
  + 매출 증가
  + 손실 방지 금액
- 총비용(Total cost):
  - 구축 비용
  + 운영 비용
  + 거버넌스 비용
  + 변화 관리 비용

**어떻게 쓰는가**

1. **배포 전 베이스라인 측정**
   - 선택한 워크플로의
     - 처리 시간
     - 품질 지표(에러율, 재작업률)
     - 비즈니스 지표(전환율, CS 재문의율)
   을 실제 시스템에서 계측합니다.

2. **4단계 지표 추적**
   - 활동(Activity): 티켓 수, 호출 수, 메시지 수
   - 품질(Quality): 정확도, 에러율, 사용자 만족도
   - 워크플로(Workflow): SLA 준수율, 처리 소요시간
   - 비즈니스(Business): 매출, 비용, 리스크 감소

3. **운영·거버넌스 비용 포함**
   - 프롬프트 관리, 정책 업데이트, 모니터링 인력까지  
     운영과 거버넌스 비용으로 계상합니다.
   - 변화 관리는 교육, 프로세스 개편, 저항 관리까지 포함합니다.

**실전 팁**

- 지표는 **소수지만 결과와 직접 연결된 것**만 고릅니다.  
  “AI 활동량이 늘었다”는 시그널만으로 성공이라고 가정하면,  
  실제로는 추가 재작업과 리스크 관리에 비용이 더 드는 상황을 놓칠 수 있습니다.
- CI 수준의 평가 파이프라인(1번 섹션)과 이 ROI 프레임워크를 묶으면,  
  “성능이 좋아졌는데도 ROI가 악화되는 지점”을 조기에 포착할 수 있습니다.

**아키텍처와 소프트웨어 가치 구조**

- 프레임워크 기사에서 강조하는 구조는 이렇습니다.
  1) 먼저 **업무·제품 요구사항**을 상세히 적습니다.  
     - 사용 사례 우선순위, 데이터 요구, 지연 허용치, 규제 요구, 예산 한도 등.
  2) 이 요구를 만족하는 아키텍처를 직접 설계합니다.
  3) 이후에야 기존 벤더 프레임워크를  
     “참고 또는 재사용 가능한 부품 창고” 정도로 봅니다.
- 다른 기사에서는 대형 언어 모델이 상용 소프트웨어를 **82% 수준 기능으로 재현**하는 예를 들며,  
  **패키지 소프트웨어 가치가 0에 가까워지는 방향**을 다룹니다. [출처](https://www.itworld.co.kr/article/4235573)
  - LLM으로 상세 기능 목록, UI, 알고리즘 개요를 주고  
    1~2주 반복 패치로 높은 수준의 복제를 만들 수 있다는 관측입니다.

**실전 팁 / 전략**

- LLM이 만든 코드는 **프로토타입/스텁**으로 간주해야 합니다.
  - 자동 테스트, 코드 리뷰, 보안 점검을 필수로 붙입니다.
- 조직 입장에서는 “소프트웨어 패키지”보다
  - 데이터 자산
  - 도메인 특화 워크플로
  - 거버넌스와 브랜드 신뢰
  쪽으로 차별화 축이 이동하고 있음을 강의나 컨설팅에서 강조할 필요가 있습니다.

**오늘 흐름을 묶는 대비**

- 한쪽에서는 Grok Voice 3 같은 음성 인터페이스, Modal 같은 거대 인프라, 에이전트 보고서가 쏟아지고 있습니다. [출처](https://tldr.tech/ai/2026-10-15)
- 다른 쪽에서는 pmset 스크립트, Chirp Pong의 오디오 동기화, Petal의 자체 호스팅처럼,  
  **작은 도구와 요구사항 중심 설계**가 실질 생산성을 좌우합니다.
- 에이전트와 LLM의 기능 격차보다,  
  **어디까지 자동화하고 어떻게 검증·통제할지, 그리고 어떤 워크플로에 얹을지**가 개발자와 강사의 핵심 설계 문제가 되고 있습니다.
