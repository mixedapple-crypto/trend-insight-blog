지난 엿새 동안 AI 도구 쪽에서 가장 쓸모 있는 신호는 새 기능보다 기존 기능의 함정이었습니다. 클로드 코드(Claude Code)의 편의 설정과 훅이 기대와 다르게 움직인다는 실측이 연달아 나왔습니다. 그 사이 사이먼 윌리슨(Simon Willison)은 Opus 5.5 채팅만으로 성능 비교 실험을 끝내는 흐름을 보여 줬습니다. 오픈AI는 GPT-6 Cyber를 발표했지만, 사용 방법은 아직 공개하지 않았습니다.

## 목차
1. 클로드 코드의 편의 설정과 훅을 그대로 믿으면 안 되는 이유
2. 윌리슨이 보여 준 채팅 실험과 PR 정리 요령
3. 에이전트를 갈아타거나 나눠 쓸 때 옮겨지지 않는 것
4. 에이전트가 숙제를 한 번에 푸는 시대의 강의 설계
5. 발표는 굵었고, 실속은 커뮤니티 실측에서 나왔습니다

## 1. 클로드 코드의 편의 설정과 훅을 그대로 믿으면 안 되는 이유

보안 업체 Apiiro는 공개 GitHub 저장소의 `.claude/settings.local.json` 파일 104,185개를 조사했습니다. 이 가운데 **1,122개**에서 비밀번호와 토큰 같은 비밀 정보가 나왔습니다. 다만 해당 자격 증명이 아직 유효한지는 확인하지 않았습니다. [출처](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again)

원인은 권한 프롬프트의 "Yes, and don't ask again" 선택지입니다. 이 선택지를 고르면 승인한 명령 전체가 해당 파일에 저장됩니다. 명령 안에 토큰이 들어 있었다면 토큰도 그대로 기록됩니다. [출처](https://news.hada.io/topic?id=36784)

문제는 클로드 코드가 이 파일을 전역 Git 무시 목록에만 넣는다는 점입니다. 저장소 자체의 `.gitignore`에는 추가하지 않습니다. 따라서 폴더를 나중에 Git 저장소로 만들거나 다른 기기에서 클론하면 보호가 사라집니다.

바로 적용할 조치는 다음과 같습니다.
- 저장소마다 `.gitignore`에 `.claude/settings.local.json`을 추가합니다.
- `git ls-files .claude`로 이미 추적 중인지 확인합니다.
- 추적 중이라면 `git rm --cached`로 추적을 끊고, 노출된 키를 교체합니다.
- 토큰이나 비밀번호가 들어간 명령에는 "다시 묻지 않기"를 쓰지 않습니다.

두 번째 함정은 훅(Hook)의 종료 코드입니다. GeekNews 실측에서 Write 도구에 건 PreToolUse 훅이 "막음"을 출력하고 exit 1로 끝났습니다. 그런데 모델은 성공을 보고했고, hello.txt 파일도 "hi"라는 내용으로 생성됐습니다. [출처](https://news.hada.io/topic?id=36873)

작성자는 아래 명령으로 헤드리스 테스트를 돌렸습니다.

```bash
claude -p --model haiku --setting-sources project --allowedTools "Write"
```

스크립트의 마지막 종료 코드만 1에서 2로 바꾸자 쓰기가 막혔습니다. 즉 테스트 게이트나 가드 훅은 **exit 2**로 끝나야 도구 호출이 실제로 멈춥니다. exit 1은 출력만 보면 차단처럼 보이지만, 쓰기는 그대로 진행됩니다.

두 사례는 출력 메시지와 실제 동작이 다를 수 있다는 점을 보여 주는 교재로 쓸 만합니다. 훅 실습에서는 exit 1과 exit 2를 나란히 돌리고 결과 파일을 직접 확인하게 하면 효과적입니다.

## 2. 윌리슨이 보여 준 채팅 실험과 PR 정리 요령

윌리슨은 일반 Claude 채팅의 Opus 5.5로 SQLite 확장 `parse_number()`를 만들었습니다. 같은 기능을 C와 Rust로 각각 구현해 비교했습니다. 이 함수는 `-$1,234.56`이나 `12.5%` 같은 문자열을 정렬하고 합산할 수 있는 숫자로 바꿉니다. [출처](https://simonwillison.net/2026/Nov/8/sqlite-parse-number-c-vs-rust)

결과는 크기와 속도에서 갈렸습니다. C 빌드는 **14KB**였고, Rust 빌드는 298~321KB였습니다. 반면 속도는 처음에 Rust가 앞섰습니다. Rust의 변환 함수가 C의 `strtod`보다 두 배 빨랐기 때문입니다.

여기서 윌리슨은 Rust를 이기는 C 파서를 직접 짜 달라고 다시 요청했습니다. Claude는 "Clinger's fast path" 방식의 파서를 내놓았습니다. 혼합 데이터에서 행당 처리 시간이 67나노초에서 **19나노초**로 줄었고, 이는 Rust의 41~46나노초보다 빠른 수치입니다.

마지막으로 윌리슨은 기존 저장소 simonw/research를 클론하게 했습니다. 그리고 같은 형식의 연구 보고서를 zip 파일로 받았습니다. 정리하면 이 워크플로는 세 단계입니다.
1. 채팅에서 빠른 탐색 비교를 돌립니다.
2. 예상과 다른 결과가 나오면 겨냥한 후속 프롬프트로 반박합니다.
3. 기존 저장소 형식에 맞춰 결과를 패키징하게 합니다.

같은 기간 윌리슨은 라이브러리 의존성을 걷어 내는 실험도 했습니다. 먼저 Three.js로 갯민숭달팽이 테마의 파베르제 달걀 장면을 만들게 했고, 결과물은 77KB였습니다. 이어 같은 대화에서 순수 JavaScript와 WebGL로 옮기게 했고, 98KB짜리 작동 버전이 나왔습니다. [출처](https://simonwillison.net/2026/Nov/9/hn-50421091)

다만 두 결과물은 똑같지 않았고, 윌리슨도 그 이유를 다 설명하지 못했습니다. 따라서 의존성을 걷어 낼 때는 화면을 나란히 놓고 눈으로 비교해야 합니다. 또한 윌리슨은 Three.js 버전이 더 읽기 쉽다고 봤습니다. 그러니 유지보수할 코드라면 라이브러리를 남기는 편이 나을 수 있습니다.

에이전트가 쓴 PR 설명에 대해서도 윌리슨은 간단한 해법을 내놓았습니다. Claude Code나 Codex가 쓴 설명은 정확하고 꼼꼼합니다. 그러나 읽으면 슬롭(Slop), 즉 성의 없는 AI 문장처럼 느껴진다는 진단입니다. [출처](https://simonwillison.net/2026/Nov/9/details-summary)

방법은 사람이 짧은 소개를 먼저 쓰는 것입니다. 이 PR이 무엇을 위한 것인지, 리뷰어가 주목할 만한지를 두세 줄로 적습니다. 그 아래에 에이전트가 쓴 전체 설명을 접어 둡니다.

```html
이 PR은 페이지네이션 헤더 버그를 고칩니다. 리뷰는 테스트 부분만 보시면 됩니다.

<details><summary>Claude Opus 5.5</summary>

(에이전트가 쓴 문제, 해결, 검증 설명 전체)

</details>
```

GitHub 마크다운은 PR 설명과 이슈 댓글에서 이 태그를 그대로 지원합니다. 접힌 상태에서는 요약 줄과 펼침 화살표만 보입니다. 리뷰어는 사람의 판단을 먼저 읽고, 필요할 때만 상세 내용을 펼치면 됩니다.

## 3. 에이전트를 갈아타거나 나눠 쓸 때 옮겨지지 않는 것

ITWorld에 실린 InfoWorld 칼럼은 코딩 에이전트를 바꾼 뒤 생긴 사고를 소개했습니다. 필자는 전역 지침 파일을 AGENTS.md로 복사하고 제품명을 일괄 치환했습니다. 그 결과 모델 호출을 `codex -p`로 하라는 지침이 남았습니다. [출처](https://www.itworld.co.kr/article/4246138/%eb%aa%a8%eb%8d%b8%eb%a7%8c-%ec%98%ae%ea%b8%b0%ea%b3%a0-%ec%9e%91%ec%97%85%ec%9d%80-%eb%aa%bb-%ec%98%ae%ea%b8%b0%eb%a9%b4ai-%ec%97%90%ec%9d%b4%ec%a0%84%ed%8a%b8-%ea%b5%ac%ec%9e%85-%ec%a0%84.html)

그런데 Codex CLI에서 `-p`는 `--profile`을 뜻합니다. 이 지침은 약 **3개월** 동안 오류 없이 조용히 깨져 있었습니다. 칼럼은 모델은 옮겨도 작업 상태는 옮겨지지 않는다고 진단합니다.

작업 상태에는 지켜야 할 결정과 포기한 접근이 포함됩니다. 실제 적용한 변경과 계획만 한 변경의 구분, 권한과 훅도 여기에 속합니다. 그러나 대화 내보내기는 대화록만 담습니다. MCP(Model Context Protocol)와 AGENTS.md도 이 문제를 다루지 않습니다.

필자는 계약이나 갱신 전에 하루짜리 출구 테스트를 권합니다.
- 기억에 의존하는 유지보수 작업을 고릅니다. 예로 12개 모듈에 걸친 로깅 라이브러리 업그레이드를 듭니다.
- 작업 중간에 사람의 결정을 끼워 넣습니다. 예를 들어 하위 사용자를 위해 옛 로그 형식을 유지하라고 지시합니다.
- 첫 에이전트가 절반쯤 끝내게 합니다. 예시에서는 7개 모듈을 옮기고, 8번째는 이유를 메모한 채 건너뜁니다.
- 요구사항과 결정, 완료한 작업, 남은 단계를 모두 내보내게 합니다.
- 그 내보내기만 다른 업체 에이전트의 새 세션에 넘기고 행동을 관찰합니다.

칼럼은 EU 데이터법의 클라우드 전환 규정도 언급했습니다. 이 규정은 2025년 9월부터 적용됐고, 2027년 1월부터 전환 수수료가 금지됩니다. 다만 이 규정이 에이전트 작업 상태에도 적용되는지는 불분명합니다. 따라서 칼럼은 구매 계획에서 이 규정에 기대지 말라고 조언합니다.

반대로 여러 모델을 작업별로 나눠 쓰는 쪽에서는 Aptly가 GeekNews에 공개됐습니다. Aptly는 Claude Code와 Codex용 로컬 MCP 서버입니다. 사용자가 정한 후보 목록에서 서브에이전트(Subagent)의 모델과 추론 강도를 추천합니다. [출처](https://news.hada.io/topic?id=36852)

또한 Aptly는 PreToolUse 훅이 지원되는 서브에이전트 호출에 기본 모델을 자동으로 지정합니다. 사용자가 모델이나 강도를 명시하면 그 값은 그대로 둡니다. MCP나 CLI로 추천을 직접 요청할 수도 있습니다.

주의할 점은 분류 과정입니다. Aptly는 오픈AI의 Decisions API에 최소한의 작업 요약을 보냅니다. 따라서 민감한 코드베이스에 쓰기 전에는 이 전송 범위를 먼저 확인해야 합니다.

## 4. 에이전트가 숙제를 한 번에 푸는 시대의 강의 설계

Latent Space는 미하일 에릭(Mihail Eric)과 나눈 대화를 실었습니다. 주제는 AI 네이티브 엔지니어링을 가르치는 스탠퍼드 강의 **CS146S**입니다. 출발점은 학생들이 작년 과제를 프롬프트 한 번으로 끝낼 수 있다는 현실입니다. [출처](https://latent.space/p/one_million_ai_engineer_special_how_stanford_teaches_ai-native_engineering_mihail_eric_monaco)

두 번째 개설에서 에릭은 오픈소스 메인테이너를 강의에 불렀습니다. 학생들은 낯선 저장소를 익히고, 그 저장소에 변경을 제안해야 합니다. 다만 공개된 발췌는 과제의 나머지 내용을 담고 있지 않습니다.

강의에 옮겨 쓸 원칙은 분명합니다. 과제를 에이전트가 한 번에 끝낼 수 있는 일에서 떼어 냅니다. 대신 낯선 코드베이스를 탐색하고 기여하는 실제 업무 쪽으로 옮깁니다.

앞의 출구 테스트도 과제로 바꿔 쓸 수 있습니다. 반쯤 진행된 작업을 다른 에이전트에 넘기고, 무엇이 빠졌는지 기록하게 하는 방식입니다. 1번 섹션의 exit 1과 exit 2 비교 역시 짧은 실습 과제로 적합합니다.

강사에게 걸리는 신호는 하나 더 있습니다. ITWorld 칼럼은 구글이 초중고(K-12) 학교에 학생용 소프트웨어의 AI 도구를 켜도록 요구한다고 전했습니다. 켜지 않으면 구글 검색 접근을 잃는 조건입니다. [출처](https://www.itworld.co.kr/article/4246120/ai%eb%a1%9c-%eb%82%a0%ea%b0%9c-%eb%8b%ac-%ec%a4%84-%ec%95%8c%ec%95%98%eb%8d%98-%ea%b5%ac%ea%b8%80-ai%ec%97%90-%eb%b0%9c%eb%aa%a9-%ec%9e%a1%ed%98%94%eb%8b%a4.html)

크롬북은 세계 초중고 기기 시장의 60.1%를 차지합니다. 따라서 구글 플랫폼을 쓰는 학교라면 AI 도구 설정과 개인정보 정책을 다시 점검할 필요가 있습니다.

## 5. 발표는 굵었고, 실속은 커뮤니티 실측에서 나왔습니다

오픈AI는 이 기간 GPT-6 Cyber를 발표했습니다. 취약점을 찾고 수정안을 만드는 보안 특화 모델입니다. 오픈AI는 이 모델이 승인된 범위 안에 머물도록 훈련됐다고 설명합니다. [출처](https://openai.com/index/introducing-gpt-6-cyber)

그러나 접근 방법과 가격, API 제공 여부는 발췌에 나오지 않습니다. Merge 고객 사례에서도 Codex가 코드 리뷰에 쓰인다는 정도만 확인됩니다. 또한 데이터센터 정책 프레임워크 발표는 개발 도구와 거리가 멉니다.

반면 바로 쓸 수 있는 정보는 대부분 개인과 보안 업체의 실측에서 나왔습니다. settings.local.json 스캔과 exit 2 실험이 대표적입니다. 윌리슨의 채팅 실험과 출구 테스트 설계도 같은 흐름입니다.

안전장치와 약관 쪽에서도 같은 교훈이 반복됐습니다. 메타는 고객 반발 끝에 기업용 AI 약관 시행을 무기한 보류했습니다. 고객 웹사이트 콘텐츠를 가져가고, AI 오류의 책임을 고객에게 넘기는 조항이 문제였습니다. [출처](https://www.computerworld.com/article/4245784/meta-does-a-u-turn-on-controversial-new-ai-terms-for-businesses-2.html)

또한 오픈 웨이트 모델 13종의 거부 행동이 단 하나의 활성화 방향에 달려 있다는 연구도 나왔습니다. 이 방향을 지우는 가중치 편집만으로 유해 요청에 대한 거부가 줄었습니다. 모델에 내장된 거부 기능만 믿고 배포하면 안 되는 이유입니다. [출처](https://news.hada.io/topic?id=36785)

이 기간의 도구 흐름을 한 줄로 묶으면 다음과 같습니다. 새 모델의 발표보다, 기본값과 편의 기능을 직접 검증하는 습관이 실무의 차이를 만들었습니다.
