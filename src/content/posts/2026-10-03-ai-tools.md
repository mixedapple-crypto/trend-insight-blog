1. LLM을 제품에 심는 법: Airbnb, Chatham, 보안 스캐너

## 1. LLM을 제품에 심는 법: Airbnb, Chatham, 보안 스캐너

### 1-1. Airbnb의 “Inside‑Out AI” 패턴: LLM은 부품으로 설계할 것

**에어비앤비(Airbnb)**가 Ahmad Al‑Dahle 리드 아래, 내부 도구와 게스트 경험 전반을 다시 짜는 **“inside‑out AI” 전략**을 공개했습니다. 핵심은 LLM을 완제품이 아니라 **파이프라인 안의 컴포넌트**로 다루는 구조입니다. [출처](https://www.latent.space/p/airbnb)

**어떻게 쓰는가 (엔지니어링 워크플로):**

- 내부 개발용  
  - 코드 생성, 디자인 문서 초안, 내부 검색에 LLM을 붙입니다.  
  - 예: PR 템플릿에 “LLM 리뷰 필요” 라벨을 달고, CI 단계에서  
    1) 변경 코드와 테스트 요약을 LLM에 보내 코드 리뷰 초안을 받고  
    2) 사람이 그 초안을 기반으로 최종 리뷰를 합니다.
- 게스트/사용자 인터페이스  
  - 메시지 개인화, FAQ 대응, 동적 도움말 생성에 LLM을 삽입합니다.  
  - 예: “예약 전 질문” 플로우에서, LLM이 먼저 답변 초안을 만들고  
    정책, 환불, 약관은 룰 엔진으로 재검증하는 2단계 구조를 둡니다.

**필수 설계: 강한 피드백 루프**

- 사용자 신호 수집  
  - 메시지 “유용/무용” 버튼, 추가 질문 클릭률, 이탈률 등을 이벤트로 기록합니다.  
  - LLM 응답 ID와 함께 저장해, 나중에 응답 품질을 역추적할 수 있게 합니다.
- A/B 테스트  
  - 동일 플로우에 “기존 규칙 기반”과 “LLM 강화 버전”을 동시에 띄웁니다.  
  - 전환율, 고객센터 문의량, 처리 시간으로 LLM 효과를 정량 평가합니다.
- 인간 검토  
  - 고위험 영역(결제, 환불, 법무 관련 문구)은 LLM 초안 뒤에  
    필수 휴먼 승인 단계를 둡니다.

**실전 팁:**

- LLM 호출은 “도메인 서비스 레이어”에 숨기고,  
  비즈니스 로직에서는 `SuggestionService`, `ExplanationService` 정도로만 부릅니다.  
  이렇게 하면 모델 교체나 파라미터 조정이 쉬워집니다.
- 응답 스키마를 고정하세요.  
  자연어만 받지 말고,  
  ```json
  { "answer": "...", "risk": "low|high", "needs_handoff": true|false }
  ```  
  처럼 구조화하여, 후속 파이프라인 제어에 활용합니다.

**강의/개발 활용 포인트:**  
실무 교육에서는 “LLM 앱 튜토리얼”보다, **기존 서비스에 LLM을 컴포넌트로 꽂는 리팩터링 과제**가 더 유용합니다. Airbnb식 패턴을 슬라이드 한 장으로 정리해, 수업 과제의 기본 아키텍처로 쓰기 좋습니다.

### 1-2. Chatham 금융 워크플로: GPT‑5.6 + Codex 이원화 패턴

**Chatham Financial**은 **GPT‑5.6과 Codex**를 조합해 자본시장 툴과 거래 검증 파이프라인을 재구축했습니다. 그 결과, 거래 1건당 검증 시간이 약 30분에서 **4분 미만**으로 줄었다고 보고합니다. [출처](https://openai.com/index/chatham-financial)

**어떻게 쓰는가 (워크플로 분할):**

- GPT‑5.6 → 고수준 규칙 해석과 전략 결정  
  - 입력: 구조화된 거래 데이터, 리스크 정책, 규정 텍스트  
  - 출력: “어떤 규칙들을 어떤 순서로 점검해야 하는지”에 대한 플랜
- Codex → 실제 검증 코드 생성  
  - GPT‑5.6이 만든 플랜을 바탕으로,  
    “이 거래의 금리 상한 검증 함수를 작성하라” 식의 요청을 보냅니다.  
  - 생성된 코드를 CI 파이프라인에서 바로 테스트합니다.

**실전 방어선:**

- 단위 테스트 먼저, 모델 호출은 나중  
  - 규칙마다 “정상 케이스/위반 케이스”를 미리 테스트 코드로 작성합니다.  
  - Codex가 새로운 검증 함수를 만들거나 수정하면,  
    CI에서 이 테스트를 통과해야만 머지하도록 설정합니다.
- 코드 리뷰 게이트  
  - LLM이 쓴 코드에는 `// generated by LLM at <timestamp>` 주석을 남깁니다.  
  - 리뷰어는 이 구간을 우선적으로 확인하고,  
    모델 버전과 프롬프트를 메타데이터로 남겨 나중에 회귀를 추적합니다.

**강의/개발 활용 포인트:**  
“한 모델로 다 한다” 대신, **추론 모델과 코드 모델을 분리하는 설계**를 과제로 주면 좋습니다. 금융이 부담된다면, 쇼핑몰 할인 규칙 검증, 게임 밸런스 체크 등으로 축소해도 같은 패턴을 교육할 수 있습니다.

### 1-3. LLM 기반 취약점 스캐너: 리포트 전 ‘재현’이 핵심

리눅스 커널 메인테이너 **Greg Kroah‑Hartman**은 LLM 기반 취약점 스캐너가 실제 운영에서 만드는 문제를 공유했습니다. “79개의 리눅스 취약점”이라는 리포트 상당수가 **이미 패치된 이슈, 중복, 재현 불가**였다는 내용입니다. [출처](https://news.hada.io/topic?id=34683)

**어떻게 쓰는가 (팀용 프로세스):**

1. LLM 스캐너를 “후보 이슈 수집기”로만 사용  
   - 자동 리포트는 바로 이슈 트래커에 올리지 않습니다.  
   - 사내 전용 “triage backlog”에만 적재합니다.
2. 각 항목별 최소 재현 절차 확보  
   - 로컬 또는 컨테이너 환경에서 취약점 트리거를 재현합니다.  
   - 입력 값, 커널/라이브러리 버전, 로그를 정리해 둡니다.
3. git 히스토리와 패치 여부 확인  
   - 유사한 함수명, 파일 경로로 기존 패치 여부를 체크합니다.  
   - 이미 수정된 코드 라인을 대상으로 한 리포트는 내부에서 종료합니다.

**실전 팁:**

- 취약점 리포트 템플릿에  
  “재현 스크립트 또는 명령”, “테스트에 사용한 커밋 해시” 필드를 필수로 두면,  
  자동 리포트와 사람 리포트를 같은 기준에서 평가할 수 있습니다.
- 교육에서는 “LLM 스캐너가 뱉은 리포트 10개 중,  
  어떤 것을 실제 이슈로 올릴지 고르는 팀 실습”을 하면,  
  학생이 LLM 한계와 검증 스킬을 동시에 익힐 수 있습니다.

## 2. 새 코딩 인프라 3종: Pi 1.0, GPT‑6, Gemini Pro

### 2-1. Pi 1.0: 타입스크립트에서 모델 입출력 타입을 고정

**Pi 1.0**이 안정 버전으로 공개되면서 **타입스크립트(TypeScript) 1급 지원**을 제공합니다. Pi는 여러 LLM을 하나의 런타임에서 다루는 “미니멀 모델 하니스”입니다. [출처](https://www.latent.space/p/ainews-pi-10-pi-durable-and-aie-nyc)

**기본 사용법:**

1. 패키지 설치  
   ```bash
   npm install @pi-ai/core
   ```
2. 런타임과 모델 래퍼 정의  
   ```ts
   import { Pi } from '@pi-ai/core';

   type ChatInput = { userId: string; message: string };
   type ChatOutput = { reply: string; intent: string };

   const chatModel = Pi.model<ChatInput, ChatOutput>({
     provider: 'openai',
     model: 'gpt-6-mini',
   });
   ```
3. 호출 시 타입 보장  
   ```ts
   const res = await chatModel.call({
     userId: 'u123',
     message: '환불 규정 알려줘',
   });
   // res.reply, res.intent 에 타입 자동 완성
   ```

**실전 팁:**

- **프롬프트 입력 구조를 타입으로 먼저 설계**한 뒤,  
  그 타입에 맞게 UI와 백엔드를 맞추면 런타임 에러를 크게 줄일 수 있습니다.
- 모델 응답을 `any`로 두지 말고,  
  `ResponseOk | ResponseError` 같이 분기 가능한 유니온 타입으로 잡으면,  
  예외 처리 로직까지 컴파일 타임에 점검됩니다.

강의에서는 “타입을 먼저 설계하고, 그에 맞춰 LLM을 세팅하는 TDD 스타일”을  
피쳐 단위 실습에 적용하기 좋습니다.

### 2-2. GPT‑6 패밀리 가이드: “프롬프트 최소, 스킬 최대” 패턴

오픈AI가 **GPT‑6 패밀리 실전 가이드**를 스타트업과 개발팀용으로 공개했습니다. 모델 선택, 추론 강도, 도구 연결 방식을 한 번에 설계하는 워크플로가 핵심입니다. [출처](https://openai.com/index/practical-guide-building-gpt-6)

**가이드의 추천 흐름:**

1. 모델 스케일 결정  
   - 빠른 응답이 필요한 채팅, 자동완성 → 경량 GPT‑6 변종  
   - 복잡한 체인, 데이터 분석 → 상위 모델
2. “추론 노력” 노브 설정  
   - 단답/요약: 낮은 설정  
   - 멀티스텝 추론, 계획 수립: 높은 설정
3. 스킬과 도구를 외부로 분리  
   - 프롬프트에 복잡한 규칙을 다 쓰지 않습니다.  
   - “가격 계산 스킬”, “DB 조회 스킬”을 별도 함수나 서비스로 만들고,  
     LLM은 언제 어떤 스킬을 쓸지 결정만 하게 합니다.

**프롬프트‑스킬 패턴 실습 예:**

- 프롬프트  
  > “사용자 질문을 읽고 필요한 스킬만 호출하라.  
  > 직접 계산하지 말고, 가격이 필요하면 `getPrice`, 재고가 필요하면 `getStock`을 호출하라.”

- 스킬 구현은 일반 코드로 작성 후, 툴 호출 인터페이스에 연결합니다.

**실전 팁:**

- 강의에서는 “프롬프트에 규칙 20줄 쓰기” 과제 대신,  
  같은 기능을 **스킬 3개와 짧은 프롬프트 3줄**로 쪼개게 하면,  
  유지보수성과 모니터링의 차이를 바로 체감하게 할 수 있습니다.
- 모니터링 시에는 “프롬프트 버전”이 아니라  
  “스킬 조합 패턴”을 기준으로 성능을 비교하는 것이 좋습니다.

### 2-3. Gemini Pro 스트리밍 코드 자동완성: 1M 토큰 코드베이스용

구글은 9월 업데이트에서 **Gemini Pro의 실시간 스트리밍 코드 자동완성**과 **최대 100만 토큰 컨텍스트** 지원을 발표했습니다. 대형 모노리포나 장수 프로젝트에 유용한 구성이 가능합니다. [출처](https://blog.google/innovation-and-ai/technology/ai/google-ai-updates-september-2026)

**API 활용 개요:**

- 요청 시 `stream=true`를 설정해 gRPC 또는 웹소켓 엔드포인트에 연결합니다.  
- 모델은 토큰을 점진적으로 전송하고, 에디터 플러그인은  
  이를 받는 즉시 화면에 가벼운 그레이 텍스트로 미리 뿌립니다.

**에디터 플러그인 설계 팁:**

- 디바운스  
  - 매 키 입력마다 재요청하지 말고, 200~400ms 입력이 멈출 때만 호출합니다.  
  - 커서가 크게 이동하면 기존 스트림을 취소하고 새 요청을 보냅니다.
- 부분 편집 적용  
  - 긴 제안 전체를 한 번에 넣지 말고,  
    함수 시그니처, 루프 헤더, 본문 블록 등 단위로 나누어 적용합니다.  
  - 사용자가 한 블록을 수락하면, 다음 블록 요청을 다시 보내도록 합니다.
- 1M 토큰 컨텍스트 활용  
  - “현재 파일 + 관련 인터페이스 정의 + 최근 변경된 파일 10개” 정도를  
    고정 컨텍스트로 설정합니다.  
  - 프로젝트 전 파일을 무작정 넣기보다는,  
    Git 변경 이력과 임포트 관계를 기준으로 추립니다.

강의에서는 VS Code 확장 템플릿에 위 패턴을 구현해보는 과제가 적합합니다.  
“스트리밍 없이 완성 → 스트리밍 적용 후 UX 비교”를 실습하면 효과가 뚜렷합니다.

## 3. Anthropic의 인재 전략: Claude Academy와 과학 모델

### 3-1. Claude Frontier Academy: 1만 명 엔지니어 양성 실험

**Anthropic**은 **100만 달러가 아닌, 100억 원 이상 규모(100M 달러)**를 투자해  
**Claude Frontier Academy**를 출범했습니다. 목표는 1만 명 엔지니어에게  
엔터프라이즈급 AI 시스템 구축 교육을 제공하는 것입니다. [출처](https://www.anthropic.com/news/claude-frontier-academy)

**활용 방법:**

- Anthropic 웹사이트에서 코호트별 지원서를 제출하고 선발되면,  
  Claude Frontier 모델을 활용한 실습, 멘토십, 프로젝트 랩을 제공합니다.
- 커리큘럼은  
  - 데이터 파이프라인 구성  
  - 프롬프트 설계  
  - 안전 장치와 거버넌스  
  - 프로덕션 모니터링  
  같은 엔터프라이즈 필수 요소를 포함합니다.

**실전 팁:**

- 교육을 받는다면 “프롬프트 실험”으로 시간을 쓰기보다,  
  **엔드 투 엔드 프로젝트**를 정의하는 것이 좋습니다.  
  예: 사내 FAQ 봇이 아니라 “실제 티켓 시스템과 연동된 헬프데스크 에이전트”.
- 스스로에게 “이 프로젝트를 그대로 사내 파일럿으로 들고 갈 수 있는가”를  
  기준으로 잡으면, 수업 결과물이 바로 실무 전환 가능합니다.

강사 입장에서는 Academy의 공개 커리큘럼 구조를 벤치마킹해,  
사내 교육이나 부트캠프의 모듈 구성을 재정렬하기 좋습니다.

### 3-2. Claude‑for‑Science: 노트북형 추론과 인용 중심 설계

Anthropic은 과학 워크플로에 특화된 **Claude‑for‑Science** 변종을 공개했습니다.  
노트북 스타일 추론과 인용 중심 출력을 강화한 모델입니다. [출처](https://tldr.tech/ai/2026-10-02)

**사용법 요약:**

- 콘솔 또는 API에서 모델을 **Claude‑for‑Science**로 선택합니다.  
- 프롬프트에 명시적으로 요구합니다.  
  - “계산 과정을 단계별로 보여달라.”  
  - “각 결론에 최소 1개 문헌을 인용하라.”  
  - “코드는 재현 가능한 형태로, 전체 셀을 제공하라.”

**프롬프트 예시:**

> “아래 데이터를 바탕으로 회귀 분석을 수행하라.  
> Step 1: 데이터 전처리, Step 2: 모델 선택, Step 3: 평가를 각각 설명하라.  
> 각 주요 선택마다 [저자, 연도, DOI] 형식으로 인용을 붙여라.  
> 마지막에 파이썬 코드 전체를 한 코드 블록으로 제공하라.”

**실전 팁:**

- 학생 과제용 “연구 도우미”를 만들 때,  
  답변에서 **인용을 반드시 제출하게 하고, 이를 검증하는 연습**을 포함하면,  
  LLM 의존과 정보 검증 스킬을 함께 다룰 수 있습니다.
- 노트북 통합 시에는  
  - “해석 설명 셀”  
  - “실행 코드 셀”  
  을 분리해 주고, 코드만 자동 실행하도록 설정하면  
  잘못된 서술이 바로 계산 결과를 망치는 일을 줄일 수 있습니다.

### 3-3. “AI는 나를 슬프게 한다”: 에이전트 시대의 주도권 지키기

국내 커뮤니티에는 “AI는 나를 슬프게 한다”는 제목으로,  
일반 목적 코딩 에이전트 의존이 개발자의 정체성과 동기에도  
영향을 준다는 보고가 올라왔습니다. [출처](https://news.hada.io/topic?id=34673)

요지는 다음과 같습니다.

- 직접 코딩하는 시간이 줄며 **손맛과 성취감 상실**  
- “내 스타트업과 코드베이스가 짧은 프롬프트로 복제될 수 있다”는  
  **IP 불안감**  
- 최종 결과에 대한 **통제감 저하**

**실전 대응 워크플로:**

- 모든 에이전트 세션 결과를  
  - 코드  
  - 테스트  
  - 디자인 문서  
  로 나눠 **버전 관리 시스템에 커밋**합니다.  
- 커밋 메시지는  
  - “에이전트 초안”  
  - “인간 리팩터링”  
  을 명시적으로 구분합니다.
- 필수적으로  
  - 사람이 리뷰  
  - 리팩터링  
  - 테스트 작성  
  을 수행하는 단계를 남겨, “소유한 지식”의 층을 유지합니다.

강의에서는 “에이전트가 작성한 서비스 모듈을, 사람이 디버깅하고 리팩터링해 성능을 2배 올리는 과제”처럼, **AI를 이기는 구간**을 의도적으로 설계하면 학습 동기 유지에 도움이 됩니다.

## 4. 에이전트로 만드는 것들: 오디오, 웹사이트, 레고 CAD

### 4-1. Audionaut: 멀티트랙 편집을 에이전트에게 위임

**Audionaut**는 오픈소스 멀티트랙 오디오 편집기로,  
편집 작업을 **AI 에이전트(예: Claude via MCP)**에게 맡길 수 있습니다. [출처](https://news.hada.io/topic?id=34682)

**기본 워크플로:**

1. 프로젝트에 멀티트랙 세션을 불러옵니다.  
2. 타임라인에서 특정 트랙이나 구간을 선택합니다.  
3. 에이전트에게 “여기부터 여기까지 크로스페이드”  
   “이 인터뷰의 음량을 일정하게 맞춰라” 같은 지시를 보냅니다.  
4. 각 수정은 개별 이력으로 남고, 사람이 검토 후 확정하거나 되돌립니다.

**실전 팁:**

- 에이전트 호출은 항상 **작은 구간과 명확한 라벨**을 기준으로 합니다.  
  - “인터뷰 1 질문 3~5”  
  - “인트로 BGM 00:00–00:15”  
- 에이전트 수정 이력을 수업 자료로 활용해  
  - 전/후 파형 비교  
  - 자동 편집이 만든 아티팩트  
  를 분석하는 과제를 만들면, 음향 감각과 도구 이해를 함께 키울 수 있습니다.

---

### 4-2. ChatGPT Sites: 대화형 웹/앱 제작과 배포

**ChatGPT Sites**는 ChatGPT 내부에서 **웹사이트, 앱, 게임을 대화만으로 만들고 호스팅**까지 할 수 있는 새 플로우입니다. [출처](https://news.hada.io/topic?id=34681)

**사용법 개요:**

1. “쇼핑몰 랜딩 페이지 + 간단한 장바구니 데모를 만들고 싶다”처럼 요구사항을 설명합니다.  
2. Figma, 기존 코드, 리소스 파일이 있다면 업로드합니다.  
3. 내장 브라우저로 결과를 실행해 보고,  
   “헤더 색을 어둡게”, “결제 버튼에 토스트 메시지 추가” 등  
   대화로 점진 수정합니다.  
4. 안정되면 대시보드에서 바로 게시하고 URL을 공유합니다.

**실전 팁:**

- 완전 제로에서 시작하기보다,  
  **기존 Codex 프로젝트나 HTML/CSS 템플릿을 먼저 올리고**  
  “이 구조를 유지한 채 스타일만 바꿔라” 식으로 지시하면  
  예측 가능한 변경이 가능합니다.
- 강의에서는 “에이전트로 뼈대를 만든 뒤,  
  참가자 각자 로컬 IDE에서 세부 로직을 손으로 고치는 2단계 과제”가 좋습니다.  
  이때 Sites는 빠른 프로토타입과 공유 채널로 사용합니다.

### 4-3. ldraw‑nova: LLM으로 LEGO CAD 모델 생성

**ldraw‑nova**는 오픈소스 파이썬 + 도커 웹앱으로,  
**GPT‑6 Astra, Opus 5.5** 등 다양한 모델을 사용해  
LDraw 형식(.mpd, .ldr) 레고 CAD 파일을 자동 생성합니다. [출처](https://github.com/anteloc/ldraw-nova)

**사용법:**

1. 저장소를 클론하거나 제공된 도커 이미지를 실행합니다.  
2. 웹 UI에서 모델 제공자와 에이전트를 선택합니다.  
3. “4x4 베이스 위에 작은 우주선”, “90년대 스타일 레고 집” 등  
   원하는 레고 모델을 자연어로 설명합니다.  
4. 출력된 .mpd/.ldr 파일을 **LDView, LeoCAD, Studio**로 열어 확인합니다.

**실전 팁:**

- 생성된 `.mpd` 파일 상단의 `"0 FILE"` 섹션과 첫 코멘트들을 확인하면  
  에이전트의 설계 의도가 드러납니다.  
  이 정보를 바탕으로  
  - 색상 팔레트  
  - 부품 종류 제한  
  - 층별 조립 순서  
  를 프롬프트에 구체적으로 명시하면,  
  실제 조립 가능한 결과를 얻기 수월합니다.
- 수업에서는 동일한 요구사항으로  
  - “통제 없는 프롬프트 버전”  
  - “세부 제약을 모두 적은 버전”  
  의 결과를 비교하면, 제약 기반 프롬프트 설계의 효과를 직관적으로 보여줄 수 있습니다.

## 5. 과장 vs 실속: 피드백, 검증, 주도권을 남기는 설계

오늘 신호를 묶으면 세 가지 축이 보입니다. Airbnb와 Chatham, GPT‑6 가이드, Pi 1.0은 **LLM을 제품 안의 컴포넌트로 넣고 측정하는 구조**를 제시합니다. Gemini 스트리밍, Audionaut, ChatGPT Sites, ldraw‑nova는 **“에이전트가 만들어 준다”는 체감 속도를 극대화합니다.**

그 사이에서 Greg Kroah‑Hartman의 사례와 “AI는 나를 슬프게 한다”는 토픽은,  
**검증되지 않은 자동 리포트와 통제감 상실의 비용**을 보여줍니다.  
검증 없는 자동화는 유지보수 부담과 감정 소진으로 돌아옵니다.

오늘 정리할 실속 있는 원칙은 단순합니다.  
1) LLM은 완성품이 아니라 **측정 가능한 부품으로 설계**하고,  
2) 모델 출력 앞뒤에는 **강한 피드백과 재현 가능한 검증**을 두며,  
3) 코딩과 설계의 최종 결정권은 **사람에게 남기는 워크플로**를 강제하는 것입니다.  
이 세 가지를 지키면, 새 도구와 모델이 나올수록 실무자와 강사는 더 많은 것을 맡기면서도, 품질과 기술적 주도권을 함께 유지할 수 있습니다.
