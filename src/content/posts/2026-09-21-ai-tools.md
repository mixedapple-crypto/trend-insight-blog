## 1. Claude 코드 올인 조직: LLM 단일 소스 리스크

**2026-09-20**, 한 회사가 **Claude Code**로 사양, 코드, 테스트, PRD, 티켓, 리포트까지 “거의 전부”를 생성하는 사례가 소개되었습니다. 엔지니어는 “Claude와 대화해 코드 만들고 푸시하라”는 지시를 받고, 사람이 보는 시간은 줄고 모델 출력이 사실상 단일 소스가 되었습니다. [출처](https://simonwillison.net/2026/Sep/20/voxium)

**실무에서 어떻게 써야 하는가**

- **LLM은 저자, 사람은 편집자**로 두 단계 분리합니다.  
  - 1단계: Claude Code로 초안 생성(코드, 테스트, 문서).  
  - 2단계: 사람 리뷰에서 “요구사항·설계·위험”을 체크리스트로 확인합니다.

- **명세는 반드시 사람 작성 또는 사람 최종 편집**을 요구합니다.  
  - 이슈 템플릿에 항목을 고정합니다.  
    - 문제 설명, 비즈니스 영향, 비기능 요구사항, 롤백 전략.  
  - Claude가 제안한 사양은 그대로 쓰지 말고, 엔지니어가 요약 후 “자기 말로” 다시 씁니다.

- **변경 단위를 작게 쪼갭니다.**  
  - “기능 1개 + 테스트 1세트”를 한 PR에 묶고,  
  - Claude에게도 “이 PR에서 바꿀 파일 목록”을 명시하게 합니다.  
  - `git diff` 기준 200~400줄 수준을 상한으로 정하면 리뷰 가능성이 올라갑니다.

- **코드 리뷰를 의무화하고, LLM 출력을 명시합니다.**  
  - PR 템플릿에 “어디에 LLM을 썼는지” 체크 항목을 넣습니다.  
  - 리뷰어는 LLM 사용 영역을 우선 순위로 보고,  
  - “테스트 증거”(실행 로그, 스크린샷)를 함께 요구합니다.

**실전 팁**

- LLM이 만든 테스트도 신뢰하지 말고,  
  - PR에 “테스트가 어떤 버그를 잡을 수 있는지” 자연어 설명을 붙이게 하면,  
  - 테스트와 요구사항이 어긋났는지 쉽게 눈으로 검증할 수 있습니다.
- 사내 규칙으로 “LLM이 생성한 코드만 있는 리포지터리는 금지”라고 못 박고,  
  - 최소 한 명이 해당 도메인을 설명할 수 있도록 **지식 보유자 지정**을 권장합니다.

강의에서는 “전사 LLM 의존 사례”를 안티 패턴으로 소개하고, 명세·리뷰·작은 변경 세트를 통한 **지식 손실 방지와 기술 부채 관리**를 실습 과제로 삼을 수 있습니다.

## 2. 원격 코딩 에이전트 키 관리: llm-keys-ui 0.1

**llm-keys-ui 0.1**은 Simon Willison의 원격 코딩 에이전트용 키 관리 플러그인입니다. 원격 머신에서 도는 에이전트(Codex Remote 등)에 API 키를 안전하게 건네주고, 이후에는 쉘 명령으로 불러올 수 있게 해 줍니다. [출처](https://simonwillison.net/2026/Sep/20/llm-keys-ui)

**어떻게 쓰는가**

1. **원격 에이전트를 플러그인과 함께 실행**합니다.  
   예시:

   ```bash
   uvx --with llm-keys-ui llm keys-ui --all
   ```

   이때 터미널에 **웹 UI 주소**가 뜹니다.  
   로컬 네트워크 또는 Tailscale IP일 수 있습니다.

2. **웹 UI에서 API 키를 등록**합니다.  
   - 브라우저에서 해당 URL 접속.  
   - `anthropic`, `openai` 같은 이름으로 키를 저장합니다.  
   - 이 키는 “원격 머신에만” 저장됩니다.

3. **스크립트나 에이전트에서 키를 가져와 사용**합니다.

   ```bash
   export ANTHROPIC_API_KEY="$(llm keys get anthropic)"
   ```

   이후 코드는 평소처럼 `ANTHROPIC_API_KEY`를 사용합니다.

**실전 팁**

- 디버깅이나 수업에서 **키를 세션에 붙여넣지 말고**,  
  - 원격 머신에서만 열리는 llm-keys-ui에 입력하게 하면,  
  - 키가 채팅 로그, 화면 녹화, 스크린샷에 남을 위험을 줄일 수 있습니다.
- 모바일이나 태블릿으로 원격 제어할 때는  
  - 키 입력은 데스크톱에서 웹 UI로 하고,  
  - 이동 중에는 이미 저장된 키를 쓰는 명령만 실행하는 패턴이 안전합니다.

이 패턴을 강의에서 “원격 에이전트 보안 기본기”로 보여주면, 학습자들이 **API 키 스파게티 환경**으로 빠지는 것을 초기에 막을 수 있습니다.

## 3. UI 자동 테스트 치유: 교차 검증 설계법

AI 기반 **테스트 로케이터 치유(locator healing)** 기능이 널리 쓰이고 있지만, 벤치마크에서는 약 **25% 정도** 잘못된 대상을 고르는 사례가 보고되었습니다. LLM이 셀렉터를 고쳐 주지만, “틀린 곳을 열심히 검사해서 초록불”인 상황이 자주 발생한다는 의미입니다. [출처](https://www.itworld.co.kr/article/4224133/ai%ea%b0%80-%ea%b3%a0%ec%b3%a4%eb%8b%a4%eb%8a%94-%ed%85%8c%ec%8a%a4%ed%8a%b8-%ec%98%ac%eb%b0%94%eb%a5%b8-%eb%8c%80%ec%83%81%ec%9d%84-%ea%b0%80%eb%a6%ac%ed%82%ac%ea%b9%8c-ai-%ed%85%8c%ec%8a%a4.html)

**어떻게 쓰는가**

- 기존 UI 테스트 스위트에 **AI 치유 기능을 켭니다.**  
  - 깨진 셀렉터, 타임아웃, 약한 assertion을 LLM이 자동 수정하게 합니다.
- 같은 사용자 플로우를 **다른 관측 지점으로 중복 검증**합니다.  
  - UI 테스트가 “성공”이라고 할 때,  
    - API 호출, DB 상태, 이벤트 로그 등도 함께 확인합니다.
- 치유된 테스트는 **태깅해서 모니터링**합니다.  
  - 예: `@healed_by_ai` 태그.  
  - 배포 후 이 태그가 붙은 테스트의 실패율, 경향을 따로 봅니다.

**실전 교차 검증 패턴**

1. **UI + 백엔드 쌍 검증**  
   - UI 테스트: “장바구니 추가 버튼” 클릭 후 성공 메시지 확인.  
   - 백엔드 검증: 같은 테스트 안에서 API로 장바구니 목록을 조회해  
     - 실제로 해당 상품이 들어갔는지 assert.

2. **UI + 텔레메트리 검증**  
   - UI 테스트가 특정 플로우를 지나갈 때,  
   - OpenTelemetry나 이벤트 로그에 “예상 이벤트 이름”이 찍혔는지 확인합니다.  
   - 이때 이벤트 이름은 비즈니스 팀과 합의된 스키마를 기준으로 합니다.

3. **다른 셀렉터 전략으로 이중 테스트**  
   - 메인 스위트는 AI 치유 셀렉터 사용,  
   - 소규모 샘플은 사람 작성의 “데이터 속성 기반 셀렉터”만 사용.  
   - 두 스위트의 성공률이 장기간 크게 갈리면, 치유가 잘못된 방향일 수 있습니다.

강의에서는 “자동 치유를 켜면 테스트가 좋아지는 것이 아니라, **검증 지점이 늘어날 뿐**”이라는 메시지와 함께, UI·백엔드·로그를 엮는 **멀티 레이어 테스트 설계 실습**으로 연결할 수 있습니다.

## 4. LangChain 유료 광고 에이전트: 슬랙 기반 운영 패턴

LangChain이 **슬랙 기반 유료 광고 운영 에이전트** 사례를 공개했습니다. 이 에이전트는 광고 플랫폼과 사내 데이터를 묶어 성과를 분석하고, 캠페인 수정 제안을 만들며, 사람 승인과 실행 체크를 슬랙으로 처리합니다. [출처](https://news.hada.io/topic?id=34041)

**어떻게 구성하는가**

1. **워크스페이스 정의**  
   - 에이전트가 쓸 수 있는 계산 자원과 도구를 명시합니다.  
     - 광고 플랫폼 API 클라이언트  
     - 내부 BI 쿼리 함수  
     - 슬랙 메시지 전송 / 워크플로 실행 훅

2. **온보딩 문서 제공**  
   - “우리 회사식 광고 운영 방식”을 문서로 만들고,  
   - 에이전트에 연결합니다. 예:  
     - 기본 CPA, ROAS 목표  
     - 요일·시간대별 예산 룰  
     - 금지 키워드, 민감 카테고리

3. **시스템 프롬프트는 “필요한 맥락만” 제한적으로**  
   - 전사 위키 전체를 넣지 말고,  
   - “유료 광고 운영 관련 섹션”만 선택해 넣습니다.  
   - 프롬프트에는  
     - 할 수 있는 일, 할 수 없는 일  
     - 사람이 꼭 승인해야 하는 경계  
     - 리포트 출력 포맷  
     을 구체적으로 적습니다.

4. **슬랙 승인·실행 플로우 연결**  
   - 에이전트는 제안을 “슬랙 스레드”로 올립니다.  
   - 사람이 이 스레드에서 승인하면  
     - 별도 배포 훅이 실제 캠페인 설정을 변경합니다.  
   - 에이전트는 “승인 결과와 실제 변경 내용”을 다시 요약해 기록합니다.

**실전 팁**

- 에이전트에 **구체적인 도구**를 줘야 감상 대신 액션이 나옵니다.  
  - 예: `get_cpc_trend(campaign_id, days)` 같은 함수.  
  - 이 함수 위주로 생각하게 하면, 설명도 데이터 기반으로 정리됩니다.
- 승인 메시지 포맷을 고정합니다.  
  - “현재 상태 요약 → 제안되는 변경 → 예상 영향 → 롤백 방법”  
  구조를 강제하면, 사람이 검토하기 쉬워집니다.
- 처음에는 **읽기 전용 모드**로만 운영하게 하고,  
  - 일정 기간 정확도가 검증되면 “소액 캠페인 자동 집행”으로 범위를 늘리는 식의  
  - 단계적 개입 확대가 안전합니다.

이 패턴은 광고뿐 아니라 CRM, 추천, 가격 조정 등 **“돈이 걸린 에이전트” 설계 템플릿**으로 강의에서 재활용하기 좋습니다.

## 5. 프롬프트는 실재하지 않는다: 회귀 테스트로 관리

“**프롬프트는 실재하지 않는다**”는 글은, 프롬프트를 안정된 아티팩트로 취급하지 말라는 메시지를 던집니다. 모델 버전, 주변 지시, 도구 구성이 조금만 바뀌어도, 같은 프롬프트가 전혀 다른 결과를 낼 수 있기 때문입니다. [출처](https://news.hada.io/topic?id=34036)

**어떻게 관리하는가**

- 프롬프트를 수정할 때마다 **자동화된 반복 실험**을 합니다.  
  - 같은 입력 세트를 N회 반복 실행합니다.  
  - 모델 버전과 온도, 도구 구성은 고정합니다.
- 변경 전·후 결과에 대해  
  - 성공률, 실패 유형, 응답 길이, 변동성 등을 비교합니다.  
  - 단일 예시가 아니라 **분포**를 봅니다.

**실전 베스트 프랙티스**

1. **프롬프트 테스트 하니스 구축**  
   - 프롬프트마다 “테스트 케이스 JSON”을 둡니다.  
   - 각 케이스는  
     - 입력, 기대 조건(키워드 포함 여부, 포맷 규칙 등), 중요도  
     를 포함합니다.

2. **회귀 테스트 파이프라인에 포함**  
   - 앱 코드 테스트와 함께 “프롬프트 테스트”를 CI에 넣습니다.  
   - 모델 버전 또는 프롬프트 파일이 바뀌면 자동으로 실행되게 합니다.

3. **에이전트 프롬프트는 특히 버전 관리**  
   - 시스템 프롬프트 변경 시마다  
     - `PROMPT_VERSION = "2026-09-21-v3"`처럼 명시합니다.  
   - 에러나 피드백을 수집할 때  
     - “어떤 프롬프트 버전에서 나온 문제인지”를 기록합니다.

4. **실패 사례를 프롬프트가 아닌 데이터로 해결**  
   - 프롬프트 문장을 계속 쥐어짜기보다,  
   - few-shot 예시를 바꾸거나,  
   - 도구를 추가하고,  
   - 후처리 검증 로직을 넣는 방향으로 해결합니다.

강의에서는 “같은 프롬프트가 내일도 통할 거라는 믿음”이 왜 위험한지, 작은 A/B 실험과 CI 연동 데모로 보여주면, 학습자들이 프롬프트를 **코드와 동급의 버전·테스트 대상**으로 취급하게 만들 수 있습니다.

## 6. AI 속도 조절, 보안 쿠키, UN 브리핑: 거버넌스 실무선 정리

오늘 흐름에는 “속도를 늦추자”는 **AI 안전 논쟁**, **제3자 평가(assurance)**, **쿠키 기반 추적**, **UN 안전 브리핑**이 함께 등장했습니다. 모두 “모델 성능보다 거버넌스와 관측”이 병목이 되고 있다는 신호입니다.  
- AI 업계는 테스트, 모니터링, 거버넌스 역량이 뒤처져 **통제력 상실**을 우려하며,  
  - 배포 전 시뮬레이션, 행동 로그, 비정상 탐지, 단계적 릴리즈 도입을 권고합니다. [출처](https://www.itworld.co.kr/article/4224149/%ec%95%88%ec%a0%84-%eb%92%a4%ec%97%90-%ea%b0%90%ec%b6%b0%ec%a7%84-ai-%ec%97%85%ea%b3%84%ec%9d%98-%ec%86%8d%eb%8f%84-%ec%a1%b0%ec%a0%88-%ec%9d%b4%ec%9c%a0.html)  
- **제3자 모델 평가(assurance)**가 새로운 산업층으로 부상하며,  
  - 안전 테스트, 규제 준수, 지역·수출 제한 등을 사전에 검증합니다. [출처](https://www.itworld.co.kr/article/4224135/%eb%b9%85%ed%85%8c%ed%81%ac%ec%9d%98-ai-%ec%95%88%ec%a0%84-%eb%85%b8%ec%84%a0-%ea%b0%88%eb%93%b1%ea%b3%bc-%ea%b3%b5%ea%b8%89-%eb%a6%ac%ec%8a%a4%ed%81%ac%ec%9d%98-%ed%98%84%ec%8b%a4%ed%99%94.html)  
- OpenAI의 광고 코드가 **ChatGPT 계정 연동 쿠키(__obi)**와 페이지 정보를 전송한다는 이슈로,  
  - 제3자 스크립트 검증과 프라이버시 컴플라이언스의 중요성이 드러났습니다. [출처](https://news.hada.io/topic?id=34025)  
- Sam Altman의 **UN 안보리 브리핑**은  
  - 수출 통제, 안전 기준, 검증 메커니즘이 국제 의제로 올라왔음을 의미합니다. [출처](https://www.reuters.com/business/openais-sam-altman-to-brief-un-security-council-next-week-during-2026-09-18)

**실무에서 취할 수 있는 최소 조치**

1. **기능 롤아웃 구조화**  
   - 캔리 배포, 내부 베타, 제한된 고객군으로 단계적 확장.  
   - 각 단계에 “에이전트 비정상 행동 트리거”를 정의합니다.  
     - 예: 비정상 API 호출 빈도, 예산 초과, 민감 데이터 접근 시 자동 차단.

2. **제3자 평가 결과를 계약과 로드맵에 반영**  
   - 모델 벤더와 계약할 때  
     - 안전 테스트 범위, 사용 제한, 지역 제한, 변경 통지 SLA를 명시합니다.  
   - 모델 접근이 언제든 제한될 수 있다는 전제로  
     - 대체 모델 전략과 기능 축소 플랜을 마련합니다.

3. **쿠키·스크립트 감사 루틴**  
   - 정기적으로 웹 서비스에서  
     - 제3자 스크립트와 쿠키를 스캔합니다.  
   - 테스트용 브라우저 프로필에서는  
     - ChatGPT 계정 쿠키를 분리하거나,  
     - 민감 기능 테스트 시 비로그인 브라우저를 사용합니다.

4. **교육과 강의에서 정책 신호를 함께 다루기**  
   - 기능 시연만 하지 말고,  
   - “이 기능이 규제·윤리·프라이버시에 주는 의미”를 슬라이드로 고정합니다.  
   - 특히 학생과 초급 개발자에게  
     - API 키, 쿠키, 이벤트 로그를 보는 **관찰 습관**을 함께 가르치는 것이 중요합니다.

오늘 신호를 한 줄로 묶으면, **“더 똑똑한 에이전트”보다 “더 잘 보이는 에이전트”가 먼저라는 것**입니다. 코드 생성, 테스트, 광고 운영, 프롬프트 설계까지 모두, LLM을 신뢰하는 기술이 아니라 **LLM을 검증하고 통제하는 기술**이 실질 경쟁력이 되는 국면으로 옮겨가고 있습니다.
