## 1. 코딩 에이전트 신뢰도 재점검: Claude Opus 4.5, GPT-5.1

**2026년 9월 기준, Claude Opus 4.5와 GPT-5.1**이 나오면서 “코딩 에이전트가 일상 개발에 쓸 만해졌다”는 평가가 나왔습니다. 각각 **Claude Code**와 **Codex-agent 워크플로**에 붙이면, 코드 생성과 실행을 반복하는 루프를 거의 손으로 안 건드리고도 돌릴 수 있습니다. [출처](https://simonwillison.net/2026/Sep/27/2026-in-llms-so-far)

실제 사용 시에는 먼저 에이전트 하네스부터 고정하는 것이 좋습니다.  
- Claude 쪽은 **Claude Code**에서 언어, 런타임, 프로젝트 루트 디렉터리를 명시해 둡니다.  
- GPT-5.1은 제공되는 **코딩 에이전트 템플릿(예: Codex-agent)**에 리포지토리와 실행 권한 범위, 테스트 명령을 미리 설정합니다.

그 위에 다음 루틴을 습관처럼 적용하는 편이 안전합니다.  
1. “요구사항 → 인터페이스 설계 → 테스트 코드 생성”까지를 에이전트에 먼저 시킵니다.  
2. 에이전트가 제안한 테스트를 검토해 누락 케이스를 수동으로 추가합니다.  
3. 그다음에만 구현 코드를 맡기고, **항상 테스트부터 실행**하게 합니다.  
4. 실패 로그를 에이전트에 다시 먹여 수정 루프를 돌립니다.

실무 팁은 “**에이전트를 ‘틀릴 수 있는 시니어 주니어’로 대하는 것**”입니다. 도메인 특화 규칙이나 복잡한 비즈니스 로직은 여전히 틀릴 수 있으므로,  
- 외부 API 호출은 모두 **mock** 뒤에서 먼저 돌리고,  
- 데이터 마이그레이션이나 배치 작업은 **샘플 1% 데이터**로만 실행한 뒤 전체에 적용합니다.

강의에서는 이 흐름을 그대로 “**자동 TDD 시연**”으로 만들기 좋습니다. 개발자에게는 “테스트 설계와 코드 리뷰는 사람이, 구현은 에이전트가”라는 역할 분담 구조를 명확히 보여 줄 수 있습니다.

## 2. 에이전트 생애주기와 통제: ADLC, Okta for AI Agents

**ADLC(Agent Development Life Cycle)**가 전통적인 SDLC를 확장하는 새로운 틀로 제안되고 있습니다. 에이전트를 하나의 프로그램이 아니라, 정의부터 거버넌스까지 관리하는 대상으로 보자는 접근입니다. [출처](https://www.itworld.co.kr/article/4227331/ai-%ec%97%90%ec%9d%b4%ec%a0%84%ed%8a%b8-%ec%83%9d%ec%95%a0%ec%a3%bc%ea%b8%b0-%ea%b4%80%eb%a6%ac%ec%9d%98-%ec%83%88-%ec%a0%91%ea%b7%bc%eb%b2%95-adlc%ec%9d%98-%eb%b6%80%ec%83%81.html)

ADLC에서 실무자가 바로 적용할 수 있는 포인트는 네 가지입니다.  
1. **에이전트 정의 문서화**  
   - 범위: “호텔 예약 문의 중 표준 템플릿에 맞는 1차 응대만”처럼 구체적으로 적습니다.  
   - 성공 지표: “유효 예약 요청의 95%를 사람 개입 없이 처리”처럼 측정 가능하게 둡니다.  
   - 금지 행위: “결제 API 직접 호출 금지”, “외부 URL 접속 금지”처럼 명시합니다.

2. **행동 설계**  
   - 단일 에이전트인지, **슈퍼바이저+전문가 멀티 에이전트**인지 토폴로지를 선택합니다.  
   - 메모리 정책을 정합니다. 최근 N회만 유지할지, 벡터 스토어에 영구 저장할지부터 결정합니다.

3. **지속 평가와 관측**  
   - 테스트 데이터셋을 고정하고, 정기적으로 리그레션 테스트를 돌립니다.  
   - 결정 경로, 도구 호출, 프롬프트 히스토리를 모두 로깅해 “왜 이런 결론에 도달했는지”를 추적 가능하게 합니다.

4. **아이덴티티와 거버넌스**  
   - 어떤 시스템에 어떤 권한으로 접근하는지를 “역할” 단위로 관리합니다.

여기에 **Okta의 “Okta for AI Agents”**가 맞물립니다. Okta는 **에이전트 SSO**와 에이전트 간 상호작용 규칙, 런타임 정책과 로깅 기능을 공개했습니다. [출처](https://www.itworld.co.kr/article/4227318/%ec%97%90%ec%9d%b4%ec%a0%84%ed%8a%b8-%eb%b3%b4%ec%95%88-%ec%8b%9c%ec%9e%a5%ec%9d%98-%ec%83%88-%ea%b2%a9%ec%a0%84%ec%a7%80-%ec%95%84%ec%9d%b4%eb%8d%b4%ed%8b%b0%ed%8b%b0-%ea%b4%80%eb%a6%ac.html)

실무 설정 순서는 다음과 같습니다.  
1. Okta에서 **에이전트 계정**을 사람 사용자처럼 등록합니다. 역할과 그룹으로 권한을 최소화합니다.  
2. “에이전트 A는 에이전트 B에게만 이 토큰을 위임 가능” 같은 **에이전트 간 권한 위임 규칙**을 정의합니다.  
3. Okta 관리자 콘솔에서 **실행 시 정책(Run-time Policy)**을 켜고,  
   - 허용된 도메인, HTTP 메서드, API 스코프를 정책으로 묶습니다.  
   - 모든 호출을 세션 ID와 함께 로깅해, 사고 시 추적이 가능하도록 합니다.

핵심 팁은 “**상시 자격증명 제거, 런타임 최소 권한**”입니다. 에이전트 코드 내부에 API 키를 넣지 말고, 항상 SSO와 짧은 수명의 토큰으로 대체합니다. 강의에서는 ADLC와 Okta를 묶어 “에이전트 아키텍처 설계 + 보안 설계” 세션으로 구성하면, 단순 프롬프트 튜닝을 넘어선 커리큘럼을 만들 수 있습니다.

## 3. 웹 자동화 에이전트 실패 사례: 크롤링, 렌더링, 봇 탐지

국내 사례에서는 **블로그 자동화 코딩 에이전트**가 자체 셀프테스트(GATE_OK)는 통과했으나, 실데이터 261개 중 6개만 정확히 처리하는 문제가 보고되었습니다. 테스트 환경에서는 “잘 된다”가 찍혔지만, 실제 웹의 DOM과 렌더링 조건에서 크게 어긋난 것입니다. [출처](https://news.hada.io/topic?id=34399)

주요 원인은 두 가지였습니다.  
1. **innerText 오염 문제**  
   - 서치콘솔 수집기 구현 시, 테이블 셀의 `innerText`에 호버 버튼 문구까지 같이 들어갔습니다.  
   - 크롤러는 `innerText` 대신 **텍스트 노드만 추출**하거나,  
     정확한 CSS 선택자와 `aria-label` 속성을 조합해 “실제 콘텐츠”만 가져오도록 바꿔야 했습니다.

2. **광고 렌더링 판정 오류**  
   - 단순 산술 판정으로 “렌더 실패”를 결론냈지만,  
   - 실제로는 브라우저 렌더 상태를 확인하지 않은 탓이었습니다.  
   - 해결책은 **헤드리스 브라우저 스냅샷**을 찍어 DOM, CSS 적용 결과를 같이 비교하는 2단계 검증입니다.

에이전트의 자체 테스트만 믿지 말고, 반드시 **실제 사이트 샘플로 엔드투엔드 검증**을 추가하는 것이 좋습니다.  
- 파이프라인 전체(크롤 → 렌더 → 비교)를 자동 테스트로 구성합니다.  
- 여러 유형의 사이트에서 20~30개 정도를 골라, 정답을 수동 라벨링한 뒤 회귀 테스트에 포함합니다.

한편, **Bluesky reply bot checker**는 반대 방향의 좋은 참고 사례입니다. 이 도구는 Bluesky 프로필의 글들을 가져와,  
- 답변 속도가 비정상적으로 빠른지,  
- 원글 비중이 거의 없는지,  
- 물음표 위주의 비슷한 답변이 반복되는지  
같은 **콘텐츠+타이밍 휴리스틱**으로 자동 응답 계정을 추정합니다. [출처](https://simonwillison.net/2026/Sep/27/bluesky-bot-check)

사용법은 간단합니다. 제공된 스크립트나 API 예제를 참고해 특정 핸들을 넣고, 결과 점수가 높은 계정만 사람이 수동 검토하면 됩니다. 대량 댓글 소음 속에서 “먼저 볼 계정”을 자동으로 선별해 주는 셈입니다.

두 사례를 합치면 실무 팁은 분명합니다.  
- “에이전트 셀프테스트 만족”과 “실제 환경에서의 성능”은 다를 수 있으니, **실제 데이터 분포를 흉내 내는 샘플 기반 테스트**를 별도로 둡니다.  
- 또, 완벽한 분류기를 만들려 하기보다, **휴리스틱으로 우선순위를 뽑고 사람 검토를 얹는 하이브리드 구조**가 현재로서는 가장 실용적입니다.

## 4. 인프라와 캐시 전략 재조정: S3 비용, Cloudflare Vary

Amazon S3는 마지막 가격 인하 이후 **2016년부터 GB-월당 0.023달러** 수준에서 더 이상 내려가지 않았다는 분석이 나왔습니다. “스토리지는 시간이 지나면 싸진다”라는 직관이 S3에는 더 이상 그대로 적용되지 않는다는 신호입니다. [출처](https://simonwillison.net/2026/Sep/27/hn-49871741)

이 신호를 실무에서 쓰는 방법은 다음과 같습니다.  
1. AWS 콘솔이나 **AWS Pricing API**로 Standard, Glacier, Glacier Deep Archive 단가를 가져옵니다.  
2. 데이터셋별로 “월 평균 GB-월, 예상 조회 횟수, 예상 복원 횟수”를 엑셀이나 스크립트로 모델링합니다.  
3. **수명주기 정책(Lifecycle Policy)**으로  
   - 30일 미접근 데이터는 Glacier로,  
   - 180일 이후에는 Deep Archive로  
   자동 전환하도록 설정합니다.

팁은 “옮기기 전에 **AWS Pricing API로 시뮬레이션**을 해보는 것”입니다. 저장비는 줄이지만, 실제로는 복원과 egress 비용 때문에 전체 비용이 늘어나는 패턴이 자주 발생합니다. 특히 교육용이나 분석용 데이터는 예측보다 자주 꺼내 보게 되므로, 강의에서는 “콜드 스토리지로 옮기면 더 비쌀 수 있는 사례”를 함께 보여 주는 편이 좋습니다.

한편, **Cloudflare는 HTTP Vary 헤더를 제대로 존중하는 캐싱 기능**을 새로 지원합니다. 이제 `Vary: Accept` 등이 설정된 응답에 대해, 요청 헤더별로 다른 캐시 엔트리를 유지할 수 있게 되었습니다. [출처](https://simonwillison.net/2026/Sep/23/hn-49823961)

사용 순서는 이렇습니다.  
1. 오리진 서버에서 `Vary: Accept`, `Vary: Accept-Language` 같은 헤더를 정확히 설정합니다.  
2. Cloudflare 대시보드의 캐시 설정에서 새 **Vary 인식 옵션**이 켜져 있는지 확인합니다.  
3. curl이나 브라우저 DevTools로 서로 다른 `Accept` 헤더로 요청을 보내고, Cloudflare 캐시 로그로 동작을 검증합니다.

다만, 좋은 실무 팁은 여전히 “가능하면 **포맷별 별도 URL**을 쓰는 것”입니다.  
- `/api/item.json`, `/api/item.xml` 처럼 명시적인 경로를 두면,  
- Vary에 의존할 때 생길 수 있는 헤더 누락, 디버깅 난이도를 피할 수 있습니다.

AI 에이전트가 붙는 서비스는 대량의 로그와 파일을 다루기 때문에, S3와 캐시 정책은 곧 운영비와도 직결됩니다. 강의에서는 “에이전트 기능 추가”와 함께 “스토리지·캐시 설계 변경”을 세트로 보여 주면, 참가자들이 전체 시스템 관점에서 비용과 성능을 같이 보는 연습을 할 수 있습니다.

## 5. 에이전트 서사와 커리어: 언어, 리스크, 역할 설계

에이전트 관련 사고를 설명할 때 **“통제를 벗어났다”는 표현을 피하라는 권고**가 나왔습니다. 대신 어떤 권한과 데이터 접근 범위, 어떤 안전 제약이 있었는지를 구체적으로 기술하라는 입장입니다. [출처](https://news.hada.io/topic?id=34375)

실무 보고서나 포스트모템에서는 다음과 같이 템플릿을 바꾸는 편이 좋습니다.  
- “에이전트가 임의로 외부 사이트를 크롤링했다” 대신,  
- “에이전트에 HTTP GET, 주어진 도메인 리스트, N회까지 재시도 권한을 부여했으며, 허용 도메인 검사는 누락되었다”처럼 기술합니다.

이렇게 쓰면 책임 소재와 재발 방지책이 분명해집니다.  
- **권한 부여 설계의 문제**인지,  
- **제약 규칙 미적용**인지,  
- **모니터링 부재**인지가 드러나기 때문입니다.

Anthropic CEO **다리오 아모데이(Dario Amodei)**가 SNL Weekend Update에서 AI 리스크를 설명한 짧은 클립도 함께 화제가 되었습니다. [출처](https://news.hada.io/topic?id=34378)
