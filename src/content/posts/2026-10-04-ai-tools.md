## 1. 클라우드 사용량 하드캡: 예산 폭주 방지 장치

**새 소식**  
Simon Willison이 모든 사용량 기반 서비스에 **기본 하드 예산 캡**이 필요하다고 주장했습니다. 최근 AWS도 월별 사용 한도 도달 시 과금 중단 옵션을 제공했습니다. 설정만 해두면 한도를 넘는 순간 요청이 실패하고, 더 이상 요금이 쌓이지 않습니다. [출처](https://simonwillison.net/2026/Oct/3/default-hard-budget-caps)

**어떻게 쓰는가 (실무 워크플로)**  
1) 각 서비스 콘솔에서 Billing 또는 Cost Management로 이동합니다.  
2) "Budget", "Spending limit" 같은 항목에서 월간 한도를 금액으로 지정합니다.  
3) "도달 시 자동 중단" 또는 "하드 캡" 옵션이 있으면 반드시 활성화합니다.  
4) API를 쓰는 경우, 비용 한도를 적용하는 Billing API가 있으면 IaC(Terraform 등)에 포함해 코드로 관리합니다.

테스트용과 개인 프로젝트 계정은 **프로덕션보다 더 빡센 한도**를 두는 편이 안전합니다. 강의용 샌드박스 계정은 수강생 수를 기준으로 1인당 1일 최대 예상 사용료의 1.5배 정도로 잡고, 초과 시 바로 차단되도록 설정하는 방식이 유효합니다.

**실전 팁 / 베스트 프랙티스**  
- 디폴트는 "하드캡 ON"으로 두고, 예외 계정만 체크박스로 해제하는 정책이 좋습니다.  
- 에이전트(Agent) 실험용 계정은 한도를 더 낮게 잡고, 한도 도달 에러를 받아서 "예산 초과, 중단" 안내를 하도록 에이전트 로직에 포함합니다.  
- 프로덕션은 "하드캡 + 알람"을 같이 씁니다. 예를 들어 50%, 80%, 100% 지점에서 Slack 또는 이메일로 알림을 보내고, 100% 도달 시는 강제로 일부 기능을 읽기 전용으로 전환하는 코드를 배포합니다.

이렇게 해두면, 강의나 사내 실험에서 에이전트가 폭주해도 "장애 + 에러 로그" 선에서 멈추고, "과금 폭탄"으로 이어지는 상황을 막을 수 있습니다.

## 2. Fable 클래스 모델: 코드와 프롬프트의 단일 스키마

**새 소식**  
Simon Willison이 **Fable 클래스 모델** 예시와 도구 체인을 newsletter에서 정리했습니다. Fable은 클래스 스타일 문법으로 모델(스키마)을 정의하고, 이를 바탕으로 직렬화와 검증, 프롬프트 스펙까지 통일하는 흐름을 지향합니다. [출처](https://simonwillison.net/2026/Oct/3/newsletter)

**어떻게 쓰는가 (기본 사용 패턴)**  
1) Python 환경에서 Fable 패키지를 설치합니다.  
2) 아래처럼 타입과 검증이 들어간 클래스 모델을 정의합니다.

```python
from fable import Model, field

class LessonPlan(Model):
    title = field(str)
    level = field(str, choices=["beginner", "intermediate", "advanced"])
    duration_min = field(int)
    sections = field(list[str])
```

3) 이 모델로부터 JSON 스키마, 직렬화기, 검증기를 생성합니다.  
4) LLM 호출 시 시스템 프롬프트에 "반드시 이 JSON 스키마를 따르라"는 지시와 함께, 위 모델에서 뽑은 예시 JSON을 포함합니다.  
5) 응답을 받은 뒤에는 항상 Fable 검증을 통과시켜야만 애플리케이션 로직에 넘기도록 합니다.

**실전 팁 / 베스트 프랙티스**  
- "프롬프트 안의 설명"이 아니라, **"코드 안의 모델 클래스"를 진짜 소스 오브 트루스**로 삼습니다. 프롬프트 문구를 바꿀 일이 생기면, 먼저 모델 클래스를 수정하고 자동으로 문서와 예시를 다시 생성합니다.  
- 강의에서 수강생 프로젝트를 평가할 때도, 데이터 제출 형식을 Fable 모델로 정의한 뒤, LLM에게 "이 스키마에 맞게 정규화해서 요약"하도록 시키면 불일치 오류를 줄일 수 있습니다.  
- 테스트 코드에서는 "모델 검증 실패 시 실패"를 기본 규칙으로 둡니다. 이렇게 하면 LLM이 살짝 다른 필드를 내보내도 바로 잡아낼 수 있습니다.

이 패턴을 쓰면 "모델이 이런 필드라고 생각했는데, 프롬프트는 저렇게 요구한다"는 식의 스키마 불일치를 크게 줄일 수 있어, 실무 통합과 강의용 데모 모두 안정성이 높아집니다.

## 3. Claude Opus 5.5: 멀티스텝 작업 설계 패턴

**새 소식**  
Anthropic이 **Claude Opus 5.5**를 공개했습니다. 긴 맥락 유지와 멀티스텝 추론, 도구 사용이 개선됐고, 특히 "처음에 준 작업 규칙"을 세션 전체에 끌고 가는 능력이 강조됩니다. Claude 웹과 Claude Code에서 모델 **opus-5.5**를 선택해 사용할 수 있고, API에서는 `model: "opus-5.5"`로 지정합니다. [출처](https://claude.dev/blog/getting-the-most-out-of-opus-5-5) [출처](https://news.hada.io/topic?id=34734)

**어떻게 쓰는가 (프롬프트 구조화)**  
Opus 5.5에서는 "생각 열심히 해봐" 같은 추상 프롬프트보다, **절차와 종료 조건을 명시하는 설계**가 더 잘 먹힙니다.

권장 구조는 다음과 같습니다.

1) 시스템 메시지에 다음 요소를 한 번에 넣습니다.  
- 전체 목표  
- 완료 조건  
- 체크포인트 지점  
- 질문이 필요할 때 규칙  

예:  
> "이 세 가지 기능을 가진 FastAPI 서비스를 설계하고 구현하십시오.  
> 각 기능 구현 후 멈추고, '테스트 케이스 X, Y가 괜찮은지' 질문하십시오.  
> 모든 기능과 테스트 코드가 준비되면 'DONE'만 적고 종료하십시오."

2) 이후 대화에서는 "현재 단계"만 간단히 알려주고, 규칙은 다시 반복하지 않습니다. Opus 5.5가 처음 규칙을 세션 전반에 유지합니다.  
3) Claude Code에서는 파일 단위 변경을 요청할 때, "이 변경이 끝나면 멈추고 diff를 요약해 달라"는 조건을 같이 둡니다.

**실전 팁 / 베스트 프랙티스**  
- "체인 구성" 대신 "프로토콜 설계"에 가깝게 접근합니다. 완료 조건과 중간 승인 포인트를 **처음 메시지에 모두 박아두는 것**이 핵심입니다.  
- "생각 단계 나눠서 답해라" 대신, "각 서브태스크 끝날 때마다 3줄 요약과 다음 행동 제안"처럼 구체적인 체크포인트를 명시하면, 긴 세션에서도 맥락이 괜찮게 유지됩니다.  
- 긴 강의 실습에서는, 과제 설명을 그대로 복붙하지 말고 "규칙 버전"을 따로 만든 뒤 시스템 메시지로 넣고, 수강생에게는 사용자 메시지 부분만 보여주는 방식이 관리에 유리합니다.

이 패턴을 익혀두면, Opus 5.5를 단순 "답변기"가 아니라, **세션 단위 워크플로 엔진**처럼 다루는 수업과 실무 자동화를 설계할 수 있습니다.

## 4. 에이전트 코딩 4위험: 코드 리뷰 규칙으로 막기

**새 소식**  
국내 기사 "에이전트 코딩의 묵시록 4기사"가 에이전트 기반 코드 생성의 네 가지 위험을 정리했습니다. 대충 짜는 코드, 개발자 소외, 스킬 저하, 팀 결속 약화를 지적하며, LLM이 쓴 코드는 사람에게 읽기 어려운 방식으로 쌓인다는 점을 강조합니다. [출처](https://news.hada.io/topic?id=34713)

**어떻게 쓰는가 (팀 규칙 설계)**  
에이전트 도입 시 아래 세 가지는 최소 규칙으로 두는 편이 좋습니다.

1) **필수 인간 리뷰**  
"에이전트가 직접 main 브랜치에 머지"는 금지합니다. 모든 변경은 사람이 리뷰하고 승인하도록 CI와 브랜치 보호 규칙을 사용합니다.

2) **스타일·린트 강제**  
- 프로젝트 공통 포맷터(Prettier, Black, gofmt 등)를 강제합니다.  
- 규칙을 통과하지 못한 PR은 자동으로 실패하게 합니다.  
- 에이전트가 생성한 코드에도 동일 기준을 적용합니다.

3) **"왜" 코멘트 요구**  
- 새로 생성된 주요 함수나 모듈에는 "이 설계 선택을 한 이유"를 한두 줄로 적게 합니다.  
- 사람이 수동으로 쓰더라도 동일하게 요구해, 팀 전체의 설계 설명 습관을 유지합니다.

강의 현장에서는, 수강생이 에이전트로 코드를 만들었을 때 "코드 리뷰 보고서"를 과제 일부로 제출하게 하는 방식도 가능합니다. 이때 변경 요약, 의도, 잠재 버그를 적게 하면 "읽으면서 이해하는 연습"을 강제할 수 있습니다.

**실전 팁 / 베스트 프랙티스**  
- 에이전트가 생성했다는 사실을 PR 템플릿에 체크박스로 남기면, 리뷰어가 어느 정도까지 설명을 요구해야 할지 감을 잡기 쉽습니다.  
- 페어 프로그래밍 시간을 일부러 잡아 "인간 + 에이전트" 조합으로 작업하게 하고, 마지막 10분은 사람 둘이 결과를 리뷰하도록 하면 팀 결속 약화 이슈를 줄일 수 있습니다.

이런 규칙을 깔아두면 "빠르니까 에이전트가 다 하게 두자"는 유혹을 통제하면서, 코드베이스의 가독성과 학습 가능성을 유지할 수 있습니다.

## 5. AI 안전 리더 사임: 벤더 신뢰 대신 팀 프로세스 정비

**새 소식**  
OpenAI의 안전 리더 **David Robinson**이 사임하며 회사 문화가 "망가졌다"고 공개 비판했습니다. 규칙만 조금 고치는 수준이 아니라, 조직 전체의 근본 개편이 필요하다고 주장했습니다. 같은 이슈를 다룬 영국 언론 보도도, OpenAI의 안전 문화가 흔들리고 있음을 전했습니다. [출처](https://news.hada.io/topic?id=34742) [출처](https://www.theguardian.com/technology/2026/oct/03/openai-safety-leader-quits-warning-ai-companys-culture-is-broken)

Anthropic 쪽에서는 동시에 **도덕 추론 레이어**를 Claude에 도입했다는 기사가 나왔습니다. 단순 필터링 대신, 윤리 원칙에 따라 답변 방향 자체를 조정하는 레이어입니다. 개발자는 Anthropic의 API 설정에서 새 안전·행동 프로필을 고를 수 있습니다. [출처](https://www.nytimes.com/2026/09/29/us/anthropic-claude-morals-ai.html)

**어떻게 쓰는가 (팀 내부 프로세스 관점)**  
1) **벤더 가이드라인은 "힌트"로만 취급**합니다.  
모델 교체나 버전 업 시에는, 기존 프롬프트와 워크플로를 통과하는 자체 테스트 세트를 돌려 결과를 비교합니다.  

2) **안전·윤리 관련 결정을 코드와 함께 버전 관리**합니다.  
- `safety/` 디렉터리나 전용 문서 리포에서 정책 변경 이력과 이유를 남깁니다.  
- 주요 릴리스마다 "이 버전에서 추가된 제한 사항과 완화된 제한 사항"을 정리합니다.

3) Anthropic을 쓰는 경우, **값 판단이 필요한 기능에만 도덕 추론 프로필을 선택**합니다.  
예를 들어, 정책 문서 초안, 학교 과제 가이드라인, 커뮤니티 모더레이션에는 도덕 추론 레이어를 켜고, 단순 코드 생성이나 데이터 정제에는 기본 프로필을 쓰는 식입니다.

**실전 팁 / 베스트 프랙티스**  
- 모든 대규모 프롬프트 변경과 모델 교체에는 "사전 점검 체크리스트"를 둡니다. 오용 방지, 편향, 개인정보 관련 항목을 체크하고 결과를 기록해 두면, 향후 인사 변화가 있어도 판단 근거를 복원할 수 있습니다.  
- 벤더가 "의식, 도덕성" 같은 추상 개념을 홍보할 때는, 개발 관점에서 "예측 가능성, 실패 모드, 통제 가능성"에 대한 구체적 근거를 요구하는 습관을 들이는 편이 좋습니다.

오늘 신호들을 묶어 보면, **도구 자체의 성능 향상(Opus 5.5)과 비용·안전 장치(하드캡, 코드 규칙, 내부 프로세스)가 동시에 필요하다**는 점이 드러납니다. 성능에 혹하기보다, 예산과 사람, 조직을 지키는 최소 장치를 먼저 깔아두는 설계가 앞으로의 AI 실무 경쟁력이 됩니다.
