각 섹션은 “지금 내 수업/프로젝트에 바로 꽂을 수 있는 워크플로” 중심으로 정리합니다.

## 1. Gemini 4 Argon: 대규모 코드와 로봇 에이전트

**무엇이 새로운가**

- **Gemini 4 Argon**이 정식 공개되며,  
  1) 물리 추론과 로봇 제어,  
  2) 대형 코드베이스 최적화 자동화  
  두 축을 동시에 겨냥하는 모델로 소개됐습니다.  
- 구글은 Argon을 **Python ADK 에이전트**로 밤새 돌려 20만 줄급 코드베이스의 성능을 개선한 사례를 공개했습니다.  
- 로보틱스용 Argon은 시뮬레이션, 코드 생성, 정책 학습에 특화된 API 경로를 제공합니다.  

### 1-1. 20만 줄 코드베이스 “밤샘 최적화” 절차

이 흐름을 그대로 따라 하면, 팀 내 레거시 프로젝트에도 바로 실험할 수 있습니다.

1. **ADK 에이전트 구성**
   - Google Python ADK를 프로젝트에 설치합니다.  
   - `.agents/skills` 디렉터리에 재사용 가능한 스킬을 나눠 만듭니다. 예:
     - `scan_startup.py`: 모듈 임포트 그래프 분석
     - `profile_imports.py`: cold start 프로파일링
     - `apply_patch.py`: PR 형태로 패치 생성
   - 각 스킬은 “입력 → 행동 → 산출물 경로”가 명확해야 합니다.

2. **/goal 모드로 고수준 지시 내리기**
   - ADK에서 Argon 에이전트를 `/goal` 모드로 실행합니다.  
   - 프롬프트 예시:
     - “이 레포의 cold import 시간을 최소 20% 줄이고, 기존 테스트를 모두 통과하게 만들 것.”  
     - “성능 관련 변경은 모두 `perf/argon-YYYYMMDD` 브랜치에 커밋할 것.”  
   - 세부 단계는 모델이 스스로 쪼개도록 남겨두는 것이 핵심입니다.

3. **자동 수정 루프 설계**
   - 에이전트의 루프:
     1) 전체 코드 스캔 및 병목 후보 식별  
     2) 프로파일링 스킬 호출로 수치 확보  
     3) 변경 제안 코드 생성 후 임시 브랜치 패치  
     4) 테스트 스킬로 회귀 검사  
   - 실패 시 원인 요약을 프롬프트로 다시 먹여, Argon이 다른 접근을 시도하도록 합니다.

4. **야간 배치로 돌리기**
   - CI에서 “야간 Argon 최적화 파이프라인”을 따로 둡니다.
   - 종료 조건:
     - 목표 개선율 달성,  
     - 지정 횟수 이상 회귀 발생,  
     - 실행 시간 상한 초과 등으로 정의합니다.  

**실전 팁**

- `/goal` 모드를 쓸 때는 **비즈니스 제약을 명시**합니다.
  - “공개 API 시그니처 변경 금지”, “로깅 레벨 유지” 등.  
- 에이전트가 남긴 변경은 **PR 단위로만 머지**하게 하고,  
  리뷰 템플릿에 “Argon 변경” 항목을 추가해 사람 리뷰를 강제하는 것이 좋습니다.  
- 강의에서는 “기존 리팩터링 과제”를 Argon 에이전트 버전으로 한번 더 시켜,  
  수동·자동 접근을 비교해보는 실습이 유용합니다.

### 1-2. 로보틱스와 시뮬레이션 우선 워크플로

로봇 쪽에서는 Argon을 “물리 추론 + 코드 생성기”로 붙이는 구성이 기본입니다.

1. **접근 경로 선택**
   - **Google AI Studio** 또는 **Gemini API**에서 Argon 모델 ID를 선택합니다.  
   - 로봇 연구 환경이면 **Google Antigravity** 같은 전용 환경도 지원됩니다.

2. **입력 구성 방식**
   - Argon 프롬프트에는 다음을 함께 넣는 것이 좋습니다.
     - 환경 서술: “테이블, 컵, 카메라 위치, 로봇 암의 관절 범위”  
     - 센서·액추에이터 스키마: 토픽 이름, 단위, 주기  
     - 안전 제약: 힘 한도, 금지 구역, 속도 상한  
   - 가능하면 **MuJoCo 상태, 심플 3D 서술, 카메라 이미지**를 함께 보냅니다.

3. **“코드로서의 정책” 생성**
   - 출력은 아래 둘 중 하나로 고정합니다.
     - 시뮬레이터용 환경 스크립트 (예: Gym 스타일 환경 클래스)  
     - 로봇 제어 노드 (ROS2 노드, 플러그인 등)  
   - 예시 프롬프트:
     - “위 환경에서 컵을 집어 옆 테이블에 옮기는 정책을 MuJoCo 시뮬레이션 코드로 생성하라. `safety_checks()` 함수에 충돌 검사 로직을 분리하라.”

4. **시뮬레이션 우선 루프**
   - Argon이 생성한 코드를 **MuJoCo나 유사 시뮬레이터에서만 먼저 실행**합니다.
   - 결과 로그와 실패 케이스(넘어짐, 충돌)를 다시 Argon에 요약 형태로 입력해,
     보정 정책을 제안받습니다.
   - 하드웨어로 내릴 때는 “스텝 수 제한, 안전 경계 두 겹”을 추가합니다.

**실전 팁**

- 로봇 프롬프트는 “3D 상태 + 단계별 목표”를 포함할수록 ERQA 같은 3D 물리 과제 성능을 실제 코드에 옮기기 쉽습니다.  
- 시뮬레이터에서 **성공 확률과 안전 위반률을 수치로 요약**해 Argon에 다시 입력하면, 모델이 “어디를 줄여야 하는지”를 스스로 찾아갑니다.  
- 로봇 강의에서는 “수동 설계한 RL 환경 vs Argon이 만든 환경”을 비교 실험으로 보여주면 학습 효과가 큽니다.

## 2. Anthropic Scion: Git 이후 모노레포 소스 관리

**무엇이 새로운가**

- Anthropic이 내부 모노레포용 소스 관리 시스템 **Scion**을 설계해, Git 기반 워크플로를 대체했습니다. [출처](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic)  
- 메인 브랜치 히스토리만 약 100GB인 규모에서, 하루 **2,500만 회 CI 체크아웃** 같은 부하를 견디도록 설계된 중앙 집중식 모델입니다.  

### 2-1. “클론 우선”에서 “서버 우선”으로 사고 전환

Scion의 설계는 Git을 버리라는 메시지보다, **“대규모 자동 체크아웃 시대”의 관점 전환**에 가깝습니다.

1. **오프라인 전제 버리기**
   - 대형 모노레포에서 개발자마다 전체 클론을 갖는 방식은  
     - 스토리지 낭비,  
     - CI와 에이전트 샌드박스의 중복 네트워크 사용을 야기합니다.  
   - Scion은 “온라인 서버가 항상 진실 소스”가 되고,  
     개발 환경과 CI, 에이전트가 서버에서 **가벼운 워킹 카피**만 땡겨오는 구조입니다.

2. **팀 적용 시나리오**
   - Git을 완전 교체하지 않고도, 이런 절충이 가능합니다.
     - 서버에 **중앙 베어 리포 + 캐시 계층**을 두고  
     - 로컬 개발, CI, 에이전트가 모두 이 계층에서 shallow 체크아웃을 받게 합니다.
   - “에이전트용 리드온리 미러”를 별도 운영해,
     대량 코드 생성·변경 실험을 사람용 메인 리포와 분리하는 것도 한 방법입니다.

3. **마이그레이션 운영 팁**
   - Anthropic은 7명 팀이 5개월 동안 마이그레이션을 완료했습니다.  
   - 비슷한 전환 시:
     - 1단계: 신규 서비스만 신규 시스템에 생성  
     - 2단계: 고빈도 CI 대상부터 이전  
     - 3단계: 레거시 레포를 점진적으로 통합  
   - 이때 “오프라인 개발 지원”은 명시적으로 포기하거나,  
     소수 인원에게만 별도 Git 미러를 제공하는 방식이 현실적입니다.

**실전 팁**

- CI와 자동화 에이전트가 **레포 I/O의 절반 이상을 차지하는 조직**이라면,  
  개발자 경험보다 “서버·네트워크 최적화”를 우선하는 구조를 검토할 시점입니다.  
- 강의에서는 Git, Perforce, Scion 같은 중앙/분산 대비를 사례로 설명하고,  
  “에이전트 시대의 소스 관리 아키텍처”를 별도 세션으로 다루면 좋습니다.

## 3. OpenAI Higgsfield: 10분 넘는 장편 AI 영상 파이프라인

**무엇이 새로운가**

- OpenAI의 **Higgsfield**가 GPT-6 Astra, GPT-Image-2.5, GPT-Live를 결합해  
  10분 이상 길이의 AI 영상을 생성하는 워크플로를 제시했습니다. [출처](https://openai.com/index/higgsfield-longer-videos-voice)  
- 핵심은 “Astra로 이야기와 샷 블록을 설계하고, Image-2.5로 고화질 프레임, GPT-Live로 음성 지시를 덧입히는” 구조입니다.  

### 3-1. 장편 영상 제작 기본 패턴

강의용 콘텐츠, 제품 데모, 튜토리얼 시리즈에 바로 쓸 수 있는 구조입니다.

1. **샷 리스트부터 뽑기 (Astra)**
   - 프롬프트 예:
     - “10분 분량 AI 교육 영상. 15초 내외 샷 40개로 나눠, 각 샷에  
       - 장면 설명,  
       - 등장 인물,  
       - 자막 대사,  
       - 카메라 움직임을 표로 정리하라.”  
   - Astra 출력은 곧바로 “콘티 스크립트”가 됩니다.

2. **키프레임 렌더링 (Image-2.5)**
   - 각 샷마다 1~3개의 **키프레임**만 생성합니다.
   - 프롬프트에 샷 번호를 넣어 일관성을 유지합니다.
     - “Shot 12. 이전 Shot 11의 주인공과 같은 얼굴, 같은 의상. 카메라는 좌측에서 줌 인.”  
   - 해상도와 스타일은 초기에 고정해두고, 샷마다 바꾸지 않는 것이 좋습니다.

3. **중간 프레임 보간 및 합성**
   - 자체 도구나 외부 비디오 툴에서 키프레임 사이를 보간하거나,  
     Image-2.5로 “중간 프레임 묶음”을 따로 생성합니다.  
   - 1분 단위로 조각 영상을 만든 뒤, 편집기에서 최종 10분 영상으로 합칩니다.

4. **GPT-Live로 실시간 조정**
   - 생성 중에 “조금 더 밝게”, “카메라를 한 박자 더 늦게 이동” 같은 지시를  
     음성으로 GPT-Live에 전달할 수 있습니다.
   - 강의 촬영처럼, 진행자가 직접 AI에게 지시하면서 영상이 바뀌는 데모를 만들 수 있습니다.

**실전 팁**

- 10분 전체를 한 번에 만들려 하기보다 **1~2분 에피소드** 단위로 쪼개어 합치는 것이  
  스토리·톤 일관성을 잡고, 실패 샷을 갈아끼우기에도 안전합니다.  
- Astra에는 “시청자 수준(입문/중급), 채널 톤, 브랜드 컬러”를 시스템 프롬프트로 먼저 지정해두고,  
  이후 샷별 지시는 짧게 유지하면 수정 작업이 줄어듭니다.  
- 수업에서는 “기존 슬라이드 강의 5분 분량”을 Higgsfield 파이프라인으로 재현하는 실습이 적합합니다.

## 4. Muse Wonder와 플러그인: Claude·Meta·Gemini 라인업 활용법

**무엇이 새로운가**

- MSL의 **Meta Muse Wonder / Wonder Full**이 **Claude 5.5급** 프론티어 모델로 소개됐습니다. [출처](https://www.latent.space/p/ainews-meta-muse-wonder-and-wonder)  
- Simon Willison의 **llm-meta-ai 0.2**와 **llm-gemini 0.35**가 각각  
  Muse Wonder 계열, Gemini 4 Argon을 지원하도록 업데이트됐습니다.  

### 4-1. Muse Wonder 계열: 개발·강의에서 쓰는 법

1. **모델 티어 선택**
   - **Wonder**: 빠른 응답, 비용 절감.  
     - 반복 프롬프트 실험, 코드 스케치, 초안 문서용.  
   - **Wonder Full / Max**: 높은 추론 능력과 긴 컨텍스트.  
     - 복잡한 리팩터링, 긴 사양서, 시험 문제 자동 생성용.  

2. **Claude 호환 클라이언트에서 사용**
   - 기존 Claude API 클라이언트에서 **모델 이름만 Wonder 계열로 변경**하면 됩니다.
   - 요청 형식은 Claude 지시 프롬프트 스타일을 그대로 씁니다.
   - 강의 예:
     - 실시간 코드 리뷰는 Wonder,  
       시험용 난이도 높은 문제 생성은 Wonder Full/Max로 분리합니다.

3. **llm-meta-ai 플러그인 활용**
   - Python 환경에서 `llm-meta-ai`를 0.2로 업그레이드합니다. [출처](https://simonwillison.net/2026/Oct/12/llm-meta-ai)  
   - `llm` CLI나 라이브러리에서:
     - `--model muse-wonder`, `--model muse-wonder-full`처럼 선택합니다.
   - “max reasoning level” 옵션을 가장 어려운 과제에만 제한하면  
     비용 대비 성능 곡선을 명확히 비교할 수 있습니다.

### 4-2. Gemini 4 Argon을 llm-gemini로 부르는 패턴

1. **업그레이드 후 모델 선택**
   - `llm-gemini`를 0.35로 올립니다. [출처](https://simonwillison.net/2026/Oct/13/llm-gemini)  
   - 모델 파라미터만 `"gemini-4-argon"`으로 바꿉니다.
   - 동일한 코드베이스에 Claude, Muse, Argon을 번갈아 꽂아  
     비교 실험을 하기에 적합합니다.

2. **비용 구조 주의**
   - Argon은 현재 저렴한 토큰 단가지만,  
     **12월 1일 이후 가격이 두 배**로 오른다는 점이 포인트입니다.
   - 지금 단계에서
     - “프로젝트당 평균 토큰 사용량”,  
     - “한 번 돌렸을 때 개선 수치”를 로깅해 두면  
     가격 인상 후에도 ROI 판단이 수월합니다.

### 4-3. AesCode로 UI 샘플을 HTML/CSS로 바로 빼내기

1. **기능 개요**
   - 마이크로소프트 **AesCode**는 슬라이드, 포스터, 대시보드 같은  
     **이미지 디자인을 HTML/CSS 코드로 변환**합니다. [출처](https://news.hada.io/topic?id=35322)  

2. **실용 워크플로**
   - 디자이너 시안 이미지를 입력으로 주고,  
     텍스트 프롬프트에는 “텍스트 내용, 숫자, 접근성 힌트”만 지시합니다.
   - 레이아웃과 스타일은 이미지에서 읽고,  
     내용만 프롬프트에서 교정하게 만드는 방식입니다.
   - 생성된 HTML/CSS는 바로 IDE에서 열어 “반응형 보정”이나  
     프레임워크 통합(React, Vue 템플릿 변환)만 추가로 진행합니다.

**실전 팁**

- 프로젝트별로 “모델 셋”을 정해 놓으면 좋습니다.
  - 예: “코드 리팩터링은 Argon, 문서와 Q&A는 Muse Wonder, UI 코드는 AesCode + Wonder”.  
- 강의에서는 같은 과제를 세 모델에 동시에 시켜 보고  
  - 코드 길이, 오류율, 설명 품질을 비교하는 식의 “모델 벤치마크 실습”이 교육 효과가 큽니다.

## 5. 품질과 보안: Pre-commit, Parsimony, 물리 보안 점검

**무엇이 새로운가**

- 에이전트가 작성하는 코드에 **관측·진단 라이브러리 강제**를 위해,  
  pre-commit 훅을 쓰는 사례가 공유됐습니다. [출처](https://simonwillison.net/2026/Oct/13/geoffrey-huntley)  
- **Parsimony**라는 오픈소스 벤치마크가 “코드 몇 줄” 대신  
  “문(statement), 호출, 리터럴 등 코드 단위”로 양을 측정합니다. [출처](https://parsimony.lasu.dev/)  
- 한편 OpenAI 사무실에서의 도청 장치 사건이 연달아 보도되며,  
  물리 보안이 AI 개발 리스크 관리의 한 축으로 다시 떠올랐습니다. [출처1](https://news.hada.io/topic?id=35315) [출처2](https://sfstandard.com/2026/10/13/openai-engineer-arrested-alleged-bugging-executive-conference-room)  

### 5-1. “진단 우회 금지” pre-commit 훅

1. **훅 동작 아이디어**
   - 커밋 전, staged diff에서
     - 필수 진단 라이브러리 import  
     - 진단 API 호출 존재 여부를 검사합니다.
   - 에이전트가 로그 없이 직접 네트워크 호출, 파일 접근을 추가하면  
     커밋을 실패시키고, 수정 안내 메시지를 출력합니다.

2. **실전 적용 패턴**
   - 언어별 스크립트 예:
     - Python: `import observability`, `trace_event(` 패턴 탐색  
     - Node: `from '@company/diag'` 같은 고정 모듈명 검색  
   - 실패 시 커밋 메시지에 “에이전트용 피드백 프롬프트”를 덧붙여,  
     같은 프롬프트를 다시 인풋으로 주면 에이전트가 수정 코드를 내도록 연결할 수 있습니다.

**팁**

- 에이전트를 팀 개발자와 동급으로 취급하는 순간,  
  “코딩 가이드라인을 지키게 하는 자동 장치”가 필수가 됩니다.  
- 강의에서는 “에이전트 전용 pre-commit 정책 만들기”를 별도 과제로 내면,  
  품질과 거버넌스 주제를 동시에 다룰 수 있습니다.

### 5-2. Parsimony와 “짧고 정확한 패치” 지향

1. **도구 사용법**
   - DeepSWE, SWE-bench처럼 이미 존재하는 벤치마크 패치나  
     자체 프로젝트의 AI 패치 diff를 Parsimony에 입력합니다.
   - 각 패치에 대해
     - 추가된 단위 수,  
     - 삭제된 단위 수,  
     - 순증 단위 수를 계산합니다.

2. **실전 활용**
   - 팀 내 모델 비교 시
     - “테스트 통과율 + 순증 코드 단위”를 동시에 보며  
       불필요하게 장황한 모델을 거르는 데 사용합니다.
   - 리뷰 템플릿에 “Parsimony 점수” 항목을 넣어  
     에이전트 출력이 지나치게 비대해지는 것을 제어할 수 있습니다.

**팁**

- “AI 코딩이 뛰어난데 왜 새 앱이 안 보이느냐”는 논의처럼,  
  현 시점 AI는 **새 제품**보다 “기존 코드의 보수·성능 개선”에서 가치를 내는 경향이 큽니다. [출처](https://news.hada.io/topic?id=35319)  
- 따라서 벤치마크도 “한 번에 새 앱을 잘 짓는가”보다  
  “기존 패치를 얼마나 작고 깨끗하게 고치는가”에 맞추는 것이 현실적입니다.

### 5-3. 물리 보안: 회의실도 개발 환경의 일부

1. **사건이 던지는 신호**
   - OpenAI 사무실에서 **숨겨진 녹음 장치**가 발견돼,  
     관련 엔지니어가 체포됐다는 보도가 이어졌습니다. [출처](https://twitter.com/OpenAINewsroom/status/2110095403198849132)  
   - 문제는 소프트웨어 보안이 아니라, 회의실과 AV 장비의 물리적 취약점이었습니다.

2. **실무 체크리스트**
   - 민감한 AI 개발 논의를 하는 공간에서:
     - TV 뒤, 케이블 덮개, 사용하지 않는 USB 포트 주변을  
       정기적으로 눈으로 점검합니다.
     - 회의실 AV 장비의 USB 포트를 비활성화하고,  
       필요 포트에는 봉인 스티커나 봉인 커버를 사용합니다.
     - RF 탐지기나 간단한 스캐너로 비정상 신호를 주기적으로 검사합니다.
   - 이상 징후 발견 시에는 **법무·보안팀과 즉시 공유**하고,  
     계정·키를 선제적으로 교체합니다.

**마무리 메시지**

오늘 신호들은 한 방향으로 모입니다.  
코드와 로봇을 다루는 에이전트(Gemini Argon, Dyna-2), 이를 감시하고 평가하는 도구(Pre-commit 훅, Parsimony), 그리고 이를 둘러싼 인프라(Scion, 물리 보안)까지, **“AI를 잘 쓰는 조직”은 모델 성능보다 워크플로와 통제 장치 설계에 더 많은 공을 들인다는 점**이 분명해지고 있습니다.
