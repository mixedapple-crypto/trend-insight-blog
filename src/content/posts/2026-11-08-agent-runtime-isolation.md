에이전트가 브라우저 조작과 코드 실행, 비동기 작업으로 손을 뻗으면서 자율성은 비약적으로 커졌지만, 동시에 런타임의 안전과 권한 격리가 핵심 과제로 떠올랐습니다. 오늘 짚어본 랭체인의 브라우저 연동과 비동기 하위 에이전트 흐름에 이어, 이번 글에서는 에이전트가 외부 환경과 맞닿는 지점에서 위험을 차단하고 신뢰를 확보하는 다섯 가지 실전 격리 아키텍처를 정리합니다.

## 목차

1. 브라우저·코드 실행의 임시 샌드박스 격리와 수명 주기 관리
2. 도구 호출 가로채기(Interceptor)와 실시간 정책 엔진
3. 하위 에이전트 간 컨텍스트 오염 방지와 계층형 메모리 설계
4. 작업 단위 벤치마크와 변경 회귀 테스트 자동화
5. 자격 증명 무노출(Zero-Exposure) 주입과 최소 권한 게이트웨이

## 1. 브라우저·코드 실행은 일회용 가상 머신에서 격리해야 합니다

에이전트가 웹을 탐색하거나 코드를 직접 실행할 때 로컬 머신이나 영구 컨테이너를 쓰는 방식은 심각한 보안 부채를 남깁니다. 악의적인 웹페이지의 스크립트 실행이나 프롬프트 인젝션을 통한 임의 명령 실행이 호스트 시스템 전체로 번질 수 있기 때문입니다.

실무에서 가장 안정적인 해법은 작업 세션마다 즉시 생성되고 폐기되는 마이크로 VM(MicroVM) 또는 샌드박스 환경을 붙이는 것입니다. 브라우저 조작의 경우 Browserbase나 Cloudflare Browser Rendering과 같은 격리형 헤드리스 세션을 사용해 네트워크와 파일 접근을 세션 단위로 격리합니다.

코드 실행 또한 E2B나 Modal, Firecracker 기반 런타임을 호출해 임시 격리 공간 안에서만 파일 쓰기와 라이브러리 설치가 이뤄지도록 제한해야 합니다. 실행이 끝나면 상태를 즉시 파기하고 필요한 결과 아티팩트만 호스트로 회수하는 구조가 기본 원칙입니다.

## 2. 도구 호출은 실행 직전에 정책 엔진을 통과해야 합니다

모델이 도구 호출(Tool Call)을 생성했다고 해서 이를 곧바로 외부 환경에 실행해서는 안 됩니다. 모델의 판단과 실제 실행 레이어 사이에 가로채기(Interceptor)와 정책 엔진(Policy Engine)을 배치해 인자(Arguments)를 실시간 검증해야 합니다.

검증 레이어는 세 가지 계층으로 구성합니다:
- **정적 인자 스키마 검증**: 필수 파라미터 타입과 허용 범위(화이트리스트) 대조
- **작업 위험도 분류**: 단순 조회(Read)는 자동 승인, 수정·삭제(Write/Delete)나 결제, 권한 변경은 사람의 명시적 승인(Human-in-the-loop) 요구
- **목적지 URL 및 도메인 필터링**: SSRF(서버 측 요청 위조)를 방지하기 위해 사설 IP 대역(10.x, 192.168.x 등)과 비인가 도메인 접근 차단

Simon Willison의 datasette-apps가 쓰기 쿼리 전에 사용자 승인을 강제한 것처럼, 민감 작업 직전의 인터럽트 장치는 자동화의 편리함보다 우선해야 하는 안전판입니다.

## 3. 하위 에이전트 간 컨텍스트 오염을 막는 계층형 메모리가 필요합니다

비동기 하위 에이전트(Async Subagent)가 여러 갈래로 작업을 수행할 때 주 에이전트의 전체 컨텍스트를 통째로 복제해 넘기면 토큰 낭비뿐만 아니라 컨텍스트 오염(Context Poisoning)이 발생합니다. 하위 작업에서 발생한 오류나 환각이 주 에이전트의 판단 흐름 전체를 왜곡할 수 있기 때문입니다.

이를 방지하기 위해 계층형 메모리 구조를 적용해야 합니다:
- **격리된 실행 컨텍스트**: 하위 에이전트는 자신에게 위임된 단일 임무의 브리프(Brief)와 필수 도구만 받고 독립 실행
- **정형 결과 리포트 반환**: 작업 완료 후 원본 대화 로그 대신 정제된 결과와 산출물 경로만 주 에이전트로 반환
- **글로벌 상태 보존**: 여러 에이전트가 공유해야 하는 저장소 규칙이나 고정 정책은 정적 파일(CLAUDE.md, AGENTS.md)이나 MCP 기반의 읽기 전용 공유 스토리지로 분리

이러한 분리 구조는 디버깅을 단순하게 만들고, 특정 하위 에이전트의 실패가 전체 파이프라인의 중단으로 이어지지 않도록 격리벽 역할을 합니다.

## 4. 프롬프트나 도구를 수정할 때는 태스크 회귀 테스트를 거쳐야 합니다

에이전트 시스템에서는 도구 설명(Tool Description)의 한 문장이나 프롬프트의 작은 수정이 기존에 잘 동작하던 다른 작업의 실패를 유발하는 사이드이펙트가 잦습니다. 따라서 모델의 벤치마크 점수 대신 실무 작업 평가 세트(Evaluation Suite)를 상시 운영해야 합니다.

실무 회귀 테스트 구축 순서는 다음과 같습니다:
- 과거 실패 사례와 주요 성공 시나리오 50~100건을 골라 골든 데이터셋을 구축합니다.
- 변경 사항이 생길 때마다 격리된 샌드박스에서 해당 작업들을 헤드리스로 일괄 실행합니다.
- 최종 태스크 완수율(Task Success Rate), 도구 호출 오류율, 실행 토큰 비용의 변화를 수치로 대조합니다.

최근 OpenAI의 BioBasicsBench나 Realtime-Bench가 보여주듯, 에이전트 평가는 일반 지능 측정에서 실제 업무 완수 검증으로 완전히 이동하고 있습니다.

## 5. 자격 증명은 에이전트에 노출하지 않고 주입해야 합니다

에이전트가 외부 서비스에 로그인하거나 결제를 처리해야 할 때, API 키나 비밀번호 같은 민감한 자격 증명을 프롬프트나 컨텍스트에 텍스트로 넘기는 것은 가장 피해야 할 안티패턴입니다. 로그와 트레이스에 비밀값이 평문으로 남을 뿐 아니라, 프롬프트 인젝션 공격에 무방비로 노출됩니다.

올바른 설계는 **볼트(Vault) 무노출 주입 아키텍처**입니다:
- 에이전트는 "인증이 필요한 상태"만을 감지하고, 실제 자격 증명 입력은 브라우저 제어 레벨에서 볼트가 직접 필드에 채워 넣습니다.
- API 호출 시에는 장기 토큰 대신 세션 한정 일회용 스코프 토큰(Short-lived Scoped Token)을 프록시를 통해 발급합니다.
- 토큰 발급 이력과 호출 로그를 작업 단위로 묶어 비정상적인 대량 호출이나 이상 패턴을 즉시 차단합니다.

결국 에이전트가 안전하게 현장에 안착하기 위한 조건은 "얼마나 똑똑한 모델을 쓰느냐"가 아니라 "얼마나 엄격하게 권한과 런타임을 통제하느냐"로 귀결되고 있습니다.
