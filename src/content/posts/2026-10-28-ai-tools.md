## 1. 모델·PC 이중 설계: GPT-6.1 Terra와 AI PC

**GPT-6.1 “Terra”**가 새로 공개되었습니다. API에서는 `model="gpt-6.1-terra"`로 지정하면 되고, 플랫폼 UI에서는 모델 목록에서 **GPT-6.1 Terra**를 선택하면 됩니다. 텍스트와 이미지가 함께 들어가는 대량 작업에서, 기존 상위 모델 대비 더 낮은 단가와 지연 시간을 목표로 한 변종입니다. [출처](https://tldr.tech/ai/2026-10-27)

**실무에 바로 쓸 수 있는 라우팅 패턴입니다.**

- 프로토타입, 고난도 작업  
  → 기존 GPT-6 / 상위 모델 유지
- 검증된 템플릿, 반복 대량 처리  
  → Terra로 라우팅

예시 설계입니다.

- 프롬프트·테스트 설계는 상위 모델로 먼저 튜닝  
- 승인된 프롬프트 세트에 한해, 배치 작업은 Terra로 일괄 처리  
- 배포 전, 중요 케이스 50~100개를 선택해 Terra 결과와 상위 모델 결과를 샘플 비교

여기에 **온디바이스 AI PC** 흐름이 더해집니다. 최근 “Copilot Plus” 계열 AI PC와 서피스, HP Zbook 같은 기종은 로컬 모델과 클라우드 모델을 잇는 **에이전트 계층**을 탑재합니다. [출처](https://www.itworld.co.kr/article/4241424)

실무 설계 관점에서는, “어디서 돌릴지”를 먼저 나눕니다.

- 로컬로 돌릴 것  
  - 반복 코드 완성  
  - 기본 초안 문서, 간단 디자인  
  - 내부 코드/문서 검색처럼 프라이버시 민감한 질의
- 클라우드로 올릴 것  
  - 대형 멀티모달 추론, 고난도 분석  
  - 조직 외부 시스템 연동, 고가치 의사결정

워크플로를 만들 때는 “라우팅 규칙”을 아예 코드나 운영 지침으로 고정하는 것이 좋습니다.

- 예:  
  - 1,000토큰 이하 텍스트 요약 → 로컬  
  - 이미지+텍스트 복합 분석, 또는 4,000토큰 초과 → 클라우드 Terra  
  - 월 단위 보고서 생성처럼 예측 가능한 배치 → Terra, 또는 가능하면 전량 로컬 모델

**애플의 MacBook Pro 14 M6** 역시 같은 맥락입니다. 12코어 CPU, 12코어 GPU, 듀얼 **16코어 뉴럴 엔진**으로 로컬 LLM, 이미지 생성, 업스케일링 속도를 끌어올립니다. [출처](https://news.hada.io/topic?id=36125)

개발·강의 환경에서의 팁입니다.

- 프레임워크는 **Core ML** 또는 **PyTorch MPS** 지원 버전을 우선 사용  
- 교육용 실습에서는 학생별 소형 로컬 모델(예: 3~8B, 4비트 양자화)을 기본으로, 고난도는 클라우드로만 보내도록 실습 구성  
- 비용 실습 시, “같은 작업을 Terra, 상위 모델, 로컬 모델” 3종으로 나눠 실제 지연·비용을 비교하게 하면, 아키텍처 감각을 빠르게 체득할 수 있습니다.

정리하면, 상위 모델과 Terra, 그리고 로컬 모델·AI PC를 함께 설계하는 “다층 라우팅”을 도입할 시점입니다. 강의와 사내 교육에서는, 모델 선택이 곧 아키텍처 설계라는 점을 실감하게 보여 줄 수 있습니다.

## 2. Cursor Agent SDK: 코드로 관리하는 팀 전용 에이전트

**Cursor Agent SDK**가 정식 공개되었습니다. 팀 지식과 도구, 워크플로에 맞춘 에이전트를 **Markdown 지침 + TypeScript 코드**로 한 프로젝트 안에서 관리하는 방식입니다. [출처](https://news.hada.io/topic?id=36138)

구조는 단순합니다.

- `*.md`  
  - 역할 정의, 말투, 한계, 도구 사용 규칙 등 “지침”  
- `*.ts`  
  - 각종 API 호출, 파일 I/O, 내부 서비스 연동 등 “도구 핸들러”  
- SDK CLI  
  - 로컬 테스트, 외부 서비스 연동, 배포 파이프라인

실무 적용 흐름 예시는 다음과 같습니다.

1. 에이전트 역할을 가장 좁게 정의  
   - 예: “프론트엔드 PR 리뷰어”, “데이터 파이프라인 헬스체크 봇”
2. 해당 역할 지침을 `frontend-reviewer.md`처럼 작성  
   - 리뷰 기준, 코딩 컨벤션, 금지 사항, 출력 포맷을 명시  
3. 실제 도구는 TypeScript로 캡슐화  
   - Git diff 읽기, ESLint 실행, 테스트 러너 호출 등을 핸들러 함수로 구현  
4. CI에서 에이전트 테스트 실행  
   - “의도적으로 틀린 PR”에 대해 올바른 피드백을 내는지 자동 테스트  
5. 합격한 버전만 배포 파이프라인을 통해 팀 내 도구로 노출

여기서 핵심 베스트 프랙티스는 “지침은 문서처럼, 도구는 코드처럼”입니다.

- 지침(Markdown)은  
  - 버전 관리, 리뷰, 번역, 주석 처리에 용이  
  - 기획자와 강사가 직접 수정 가능
- 도구(TypeScript)는  
  - 안전 장치(레이트 리밋, 권한 체크)를 코드로 강제  
  - 테스트 코드로 회귀 검증 가능

교육용으로는, 다음과 같은 실습 구성이 적합합니다.

- 1차 강의: “지침만 바꾸어 같은 코드가 어떻게 달리 동작하는지” 실험  
- 2차 강의: “도구 레이어에 권한을 추가/삭제하면 무엇이 막히는지” 확인  
- 마지막에는 학생들이 각자 팀용 헬퍼 에이전트를 만들어, CI에 올리고 PR로 제출하게 하면, 실제 현업과 유사한 경험을 제공합니다.

멀티 에이전트 아키텍처를 가르칠 때도, Cursor Agent SDK 구조를 예시로 보여 주면 “역할 분리, 최소 권한, 코드 기반 관리”라는 세 축을 쉽게 설명할 수 있습니다.

## 3. Oracle·Localiza: 엔터프라이즈용 대화형 워크플로 설계

오픈AI와 **Oracle**의 확장 파트너십으로, **Oracle 비즈니스 애플리케이션과 AI 에이전트**를 ChatGPT 안에서 직접 호출할 수 있게 되었습니다. ChatGPT 설정에서 Oracle 계정을 연결하면, Oracle 앱과 데이터를 다루는 대화형 에이전트를 띄울 수 있습니다. [출처](https://openai.com/index/oracle-apps-in-chatgpt)

엔터프라이즈 워크플로에서의 추천 사용법입니다.

- 데이터 조회·리포트  
  - “지난 분기 지역별 매출 상위 10개를 표로 만들고, PDF로 내보내라”  
  - Oracle 쿼리를 숨기고, 자연어로 리포트를 생성
- 워크플로 트리거  
  - “이 조건을 만족하는 고객에 대해 갱신 캠페인 태스크를 생성해라”  
  - 사람은 조건만 말하고, 에이전트가 워크플로 실행

중요한 팁은 “사람 한 명이 모든 권한을 가진 슈퍼 에이전트”를 만들지 않는 것입니다.

- 기능별, 부서별로 에이전트를 나누고  
- 각 에이전트에 필요한 최소 Oracle 권한만 부여  
- 로그와 실행 내역을 별도 테이블이나 SIEM으로 보내 검증

이 구성은 브라질 모빌리티 기업 **Localiza** 사례와도 맞닿습니다. Localiza는 **ChatGPT Enterprise**, **OpenAI API/Codex**, **60개 이상 특화 에이전트**를 조합해 “AI 네이티브” 운영 모델을 만들었습니다. [출처](https://openai.com/index/localiza-generative-ai)

Localiza식 설계의 핵심은 다음과 같습니다.

- “큰 프로세스 한 개” 대신  
  - “아주 작은 업무 단위” 별로 에이전트 생성  
- 각 에이전트는  
  - 한두 개 API와 데이터만 접근  
  - 프롬프트, 로그, 권한이 독립

이 패턴을 강의나 사내 PoC에서 활용하려면, 다음 단계를 추천합니다.

1. 기존 업무 프로세스를 10~20단계로 쪼갠 뒤  
2. 각 단계를 “사람+에이전트 페어링”으로 설계  
3. PoC 단계에서는 3~5단계만 실제 에이전트로 구현  
4. Oracle 연동이나 사내 API는 샌드박스 환경에만 붙여 검증

이렇게 하면, 한 번에 “전사 AI 전환”을 시도하지 않고도, 일부 부서에서 검증된 패턴을 다른 조직으로 이식할 수 있습니다. 강사는 이 사례를, “대화형 UI + 다수의 좁은 에이전트 + 최소 권한”이라는 구조로 정리해 보여 주면 좋습니다.

## 4. 보안·안전·오프라인: AI 리스크 관리와 실전 체크리스트

보안과 안전 쪽에서는 “속도와 통제”가 함께 부각됩니다. 오픈AI **Daybreak**가 체크포인트(Check Point)의 취약점 연구 속도를 끌어올린 사례와, 국내 쿤텍의 **AEZIZ, ASH, NEXA** 연동 전략, 그리고 의료 분야의 ChatGPT 오진 사례가 하나의 대비축을 이룹니다.

**Daybreak**는 취약점 리포트, 익스플로잇 샘플, 텔레메트리를 입력받아, 공격 체인과 탐지 룰, 방어 전략을 자동 제안하는 도구로 소개됩니다. [출처](https://openai.com/index/check-point-daybreak)

실무 팁은 “연구 보고서에서 끝내지 말고, SIEM과 룰셋 관리에 바로 연결하라”입니다.

- Daybreak 결과를  
  - IDS/IPS 룰, SIEM 룰, EDR 정책 템플릿으로 매핑  
- 보안 엔지니어가 이 템플릿을 검토 후, 바로 스테이징 환경에 배포  
- 배포와 동시에, 어떤 취약점–룰–서비스가 연결되는지 메타데이터를 남겨, 나중에 회귀 분석 가능하게 구성

국내 쿤텍은 이와 맞물리는 개념으로 **AI-BOM**과 에이전트 보안, 데이터 보안을 묶었습니다. **AEZIZ**로 소프트웨어와 AI 구성요소를 SBOM/AI-BOM 형태로 인벤토리하고, AI 에이전트의 모델, 도구, 외부 호출, 권한을 정적으로 스캔합니다. [출처](https://www.itworld.co.kr/article/4240701)

베스트 프랙티스는 배포 전 “에이전트 안전 점검 체크리스트”를 강제하는 것입니다.

- 이 에이전트가 호출 가능한 도구는 무엇인가  
- 외부 API 키, 데이터베이스, 파일 시스템에 어떤 범위로 접근하는가  
- 사람 승인 없이 실행 가능한 동작이 있는가

이 체크리스트를 통과하지 않으면, 프로덕션 배포를 막는 식의 게이트를 CI에 두면 좋습니다. 멀티 에이전트 시스템일수록, 한 에이전트의 과도한 권한이 전체 리스크로 번지는 경우가 많습니다.

한편, **뉴욕타임즈**는 간질 환자가 약 용량을 줄이는 문제에 대해, ChatGPT가 “감량을 계속해도 된다”는 식의 조언을 하고, 이후 치명적 발작이 발생한 사례를 보도했습니다. [출처](https://www.nytimes.com/2026/10/27/well/ai-chatgpt-medication-epilepsy-death.html)

의료·고위험 도메인에서의 실전 원칙은 단순합니다.

- AI의 진단, 용량, 투약 관련 답변은 “초안”으로만 취급  
- 프롬프트에 “1차 가이드라인, 1차 논문, 용량 범위, 금기 사항을 인용하라”고 명시  
- 그럼에도 불구하고, 반드시  
  - 공인 가이드라인, 약물 정보 데이터베이스  
  - 또는 사람 의사와의 상담으로 재검증

교육 현장에서는, 이 사례를 그대로 프롬프트 설계 실습에 활용할 수 있습니다. “어떻게 묻느냐”보다 중요한 것은 “어떻게 검증하느냐”라는 점을 보여 주기에 적합합니다.

마지막으로, 리스크 관점에서는 “연결이 끊겼을 때”도 대비해야 합니다. **Survival LLM**은 비상 대응 지식과 LLM을 로컬에 저장해, 인터넷 없이도 동작하는 오픈소스 앱과 자가 호스팅 도구입니다. [출처1](https://news.hada.io/topic?id=36130) [출처2](https://www.brangus.io/survival-llm)

실전 팁은 다음과 같습니다.

- 평상시, 인터넷이 있을 때  
  - 비상 매뉴얼, 사내 SOP, 중요 문서를 PDF로 정리해 Survival LLM에 미리 적재  
  - 로컬 LLM은 기기 성능에 맞춰 소형·양자화 모델을 선택해 속도 확보  
- 훈련·강의에서는  
  - 클라우드 모델과 Survival LLM을 번갈아 사용해, 같은 질문에 대한 품질 차이와, 연결 실패 시 동작 방식을 비교

결국 오늘 흐름은, “빠른 AI” 이전에 “통제 가능한 AI”를 어떻게 설계할 것인가로 모입니다. 모델 선택과 비용 최적화, 에이전트 아키텍처, 보안 게이트, 오프라인 플랜을 한 세트로 가르치고 설계하는 것이, 앞으로 개발자와 강사에게 요구되는 기본 역량으로 보입니다.
