오늘 AI 도구 쪽에서 가장 쓸모 있는 신호는 에이전트 비용을 계산하는 방식이 바뀌고 있다는 점입니다. 모든 요청을 비싼 모델에 보내지 않고 싼 계층을 앞에 두는 설계가 여러 곳에서 함께 나왔습니다. 에이전트 권한을 통제하는 방법과 세션 사이에 기억을 공유하는 방법도 실무 신호로 이어졌습니다. 부수 신호로 Anthropic이 상장 신청서를 제출했습니다.

## 목차
1. 에이전트 비용 설계: DoorDash 검색 게이트웨이, Hightouch, Gemini 라우팅
2. 에이전트 권한 통제: datasette-apps 0.3a0, ChatGPT 커넥터, Project Chrysalis
3. 세션 간 기억 공유: Heirmos, Claude Code와 Codex
4. 음성 에이전트: ADK 논블로킹 도구, OpenAI 발신 SIP
5. 상장과 회의론 사이의 실속: Anthropic S-1, ActivTrak 조사

## 1. 에이전트 비용은 토큰 단가가 아니라 작업 단위로 따져야 합니다

**DoorDash**는 LLM 웹 검색 비용을 98% 넘게 줄였다고 공개했습니다. 모델에 내장된 웹 검색 대신 별도 검색 API를 붙인 결과입니다. 질의 의도 분류 평가에서 정확도는 그대로 유지됐습니다. [출처](https://news.hada.io/topic?id=36733)

구조의 핵심은 여러 에이전트(Agent)가 함께 쓰는 검색 게이트웨이(Gateway)입니다. 이 구조에서는 모델과 검색 제공자를 서로 독립적으로 바꿀 수 있습니다. 결과 개수와 캐시 정책, 장애 시 대체 제공자는 모두 설정으로 관리합니다.

게이트웨이는 같거나 의미가 비슷한 질의의 결과를 재사용합니다. 캐시가 채워진 상태에서 평균 지연은 68% 줄었고, 검색 비용은 첫 실행보다 99% 넘게 낮아졌습니다. 다만 98%라는 수치에는 모델 추론 비용이 빠져 있습니다.

Hightouch도 같은 방향의 사례를 냈습니다. 이 회사는 신원 확인(Identity Resolution)을 판정하는 데 LLM 심판을 씁니다. 저렴한 구성이 필요할 때만 **Claude Opus**에 도움을 요청하게 했습니다. 그 결과 Opus 수준의 정확도를 약 4분의 1 비용으로 얻었다고 밝혔습니다. [출처](https://hightouch.com/blog/llm-judges-identity-resolution)

구글 개발자 블로그는 작업당 비용(Cost per Task)이라는 지표를 제안했습니다. 토큰 단가는 계속 내려가는데 코딩 에이전트 청구액은 오히려 오른다는 진단입니다. 제목으로 보면 저렴한 분류기로 요청마다 Gemini 모델과 사고 수준을 고르는 방식입니다. [출처](https://developers.googleblog.com/cost-per-task-using-cheap-classifiers-to-route-across-gemini-models-and-thinking-levels)

세 사례를 실무에 옮기면 다음 순서가 됩니다.

- 작업 하나를 끝내는 데 든 총비용을 먼저 기록합니다. 토큰 단가표만 보면 재시도와 도구 호출 비용이 가려집니다.
- 웹 검색처럼 반복되는 외부 호출은 모델에서 떼어 공용 계층으로 옮깁니다. 캐시와 대체 제공자도 그 계층에 둡니다.
- 쉬운 요청은 싼 모델이 처리하게 합니다. 판단이 어려운 요청만 상위 모델로 넘기는 경로를 만듭니다.

구글 글의 발췌에는 분류기 선택과 비용 수치가 없습니다. 따라서 라우팅을 도입하기 전에 자체 평가 세트로 정확도부터 확인해야 합니다.

강의에서는 같은 과제를 상위 모델 단독 구성과 라우팅 구성으로 각각 돌려 비교해 볼 수 있습니다. 작업당 비용과 정확도를 함께 보여 주면 설계 논리가 분명하게 전달됩니다.

## 2. 에이전트에게 쓰기 권한을 줄 때는 사람 승인을 끼워 넣어야 합니다

Simon Willison이 11월 4일 **datasette-apps 0.3a0**을 공개했습니다. Datasette 안에서 맞춤 HTML 앱을 호스팅하고 편집하는 플러그인입니다. 이번 버전은 LLM 기반 Datasette Agent와의 연동을 강화했습니다. [출처](https://simonwillison.net/2026/Nov/4/datasette-apps)

사용법은 단순합니다. Agent 채팅에서 #을 입력하면 볼 권한이 있는 앱이 자동 완성으로 뜹니다. 'View app' 링크를 누르면 Agent 패널에서 앱이 전체 화면으로 열립니다.

눈여겨볼 부분은 권한 설계입니다. 새 도구는 app_add_stored_queries()와 app_remove_stored_queries()입니다. 에이전트는 이 도구로 앱이 호출할 수 있는 저장 쿼리를 관리합니다.

app_create()는 요청한 쿼리가 실제로 있는지, 볼 수 있는지를 먼저 확인합니다. 또한 앱을 만들 때와 쓰기 쿼리를 허용할 때는 사용자 승인이 필요합니다. LLM이 만든 앱이 사람 확인 없이 쓰기 권한을 얻지 못하게 막는 장치입니다.

같은 날 나온 datasette-llm 0.1a10은 모델 제한 버그를 고쳤습니다. 설정 파일에 적은 모델로만 범위가 좁혀지지 않던 문제입니다. 설정으로 사용 모델을 제한해 왔다면 바로 업데이트해야 합니다. [출처](https://simonwillison.net/2026/Nov/4/datasette-llm)

반대편 사례도 있습니다. OpenAI 커뮤니티 포럼에 ChatGPT 도구 호출이 다른 커넥터로 조용히 전달됐다는 보고가 올라왔습니다. 재현 절차와 OpenAI의 공식 답변은 아직 확인되지 않았습니다. [출처](https://community.openai.com/t/security-follow-up-tool-call-silently-routed-to-a-different-connector/1413053)

구글의 **Project Chrysalis**는 이 문제를 아키텍처로 다룹니다. 토대는 Gemini Enterprise Agent Platform과 BigQuery입니다. 여기에 에이전트 개발 키트(Agent Development Kit, ADK)를 함께 씁니다.

그 위에 보안 관문 4개를 겹쳐 둡니다. 관문은 Model Armor와 Cloud KMS, Binary Authorization, Open Policy Agent(OPA)입니다. [출처](https://developers.googleblog.com/architecting-governed-self-evolving-ai-agents-on-gemini-agent-platform)

실전 원칙은 하나로 모입니다. 읽기는 넓게 열고, 쓰기와 외부 전송은 사람 승인을 거치게 합니다. 민감한 계정을 여러 커넥터에 동시에 붙이는 일은 원문 스레드를 확인한 뒤로 미루는 편이 안전합니다. 에이전트 실습 과제에서 승인 단계를 기본값으로 두면 수강생이 권한 설계를 자연스럽게 익힙니다.

## 3. Heirmos는 Claude Code와 Codex가 같은 기억을 쓰게 합니다

커뮤니티 플러그인 **Heirmos**가 GeekNews의 Show GN 게시판에 공개됐습니다. Claude Code와 Codex가 하나의 기억 계층을 공유하게 하는 도구입니다. 두 에이전트를 오가도 프로젝트의 결정 사항이 이어집니다. [출처](https://news.hada.io/topic?id=36737)

작동 방식은 다음과 같습니다. 세션이 끝나거나 컨텍스트가 압축되면 대화에서 결정과 선호, 규칙만 뽑아냅니다. 다음 세션이 시작되면 이 내용을 에이전트 컨텍스트에 자동으로 넣습니다.

추출 대상에는 '테스트는 pytest로 작성' 같은 규칙이 들어갑니다. '이 저장소의 마이그레이션은 손으로 작성' 같은 관례도 포함됩니다. 따라서 저장소 관례와 실패한 접근을 매번 다시 설명하지 않아도 됩니다.

작업 중에는 에이전트가 과거 결정을 조회하는 것으로 보입니다. 조회 수단은 모델 컨텍스트 프로토콜(Model Context Protocol, MCP)로 추정됩니다. 다만 게시글 발췌가 중간에 잘려 있어 단정하기는 어렵습니다.

설치 절차와 설정 방법도 발췌에는 없습니다. 따라서 도입 전에 기억이 저장되는 위치와 추출 결과를 직접 검토해야 합니다. 잘못 뽑힌 규칙이 매 세션에 주입되면 오히려 에이전트가 엇나갈 수 있습니다.

Heirmos를 쓰지 않더라도 원리는 바로 적용할 수 있습니다. 세션이 끝날 때 결정과 실패한 시도를 짧게 정리해 프로젝트 문서에 남기면 됩니다. 여러 에이전트를 번갈아 쓰는 실습에서 기억을 외부 계층으로 빼는 설계를 보여 주기에 적합한 사례입니다.

## 4. ADK 음성 에이전트는 느린 도구 호출 중에도 말을 멈추지 않습니다

구글이 ADK로 침묵하지 않는 음성 에이전트를 만드는 단계별 가이드를 공개했습니다. 모델은 **gemini-3.8-live**이고, 파이썬의 논블로킹(Non-blocking) 도구를 씁니다. 백엔드 작업이 느려도 대화가 끊기지 않게 하는 것이 목표입니다. [출처](https://developers.googleblog.com/step-by-step-guide-build-a-voice-agent-that-never-goes-silent-using-adk)

구현 방법은 두 가지입니다. 하나는 진행 상황을 yield로 내보내는 스트리밍 도구를 작성하는 것입니다. 다른 하나는 오래 걸리는 질의를 백그라운드에서 돌리는 것입니다.

도구 결과가 대화에 들어오는 시점은 응답 스케줄링 옵션으로 정합니다. 옵션은 WHEN_IDLE과 INTERRUPT, SILENT 세 가지입니다. 이름으로 보면 대화가 빌 때 전달하거나, 말을 끊고 전달하거나, 말없이 반영하는 방식으로 읽힙니다.

정확한 동작은 원문 코드에서 확인해야 합니다. 실전에서는 결과의 긴급도에 따라 옵션을 나누는 편이 좋습니다. 예를 들어 결제 실패처럼 즉시 알려야 할 결과에만 끼어들기를 허용합니다.

음성 쪽 신호는 하나 더 있습니다. OpenAI는 API의 발신 SIP 통화를 모든 조직에 열었습니다. 설정 절차와 요금은 공식 음성 SIP 가이드에서 확인해야 합니다. [출처](https://developers.openai.com/api/docs/guides/voice-sip)

음성 에이전트 수업에서 도구 호출 중 침묵은 수강생이 가장 먼저 겪는 문제입니다. 이 가이드는 그 해결책을 코드 수준에서 보여 주는 교재로 쓸 수 있습니다.

## 5. 상장 소식은 굵은 신호지만, 실속은 작업 흐름 안에 있습니다

이번 주 가장 큰 헤드라인은 Anthropic의 상장입니다. Anthropic은 미국 증권거래위원회(SEC)에 **S-1** 등록 신고서를 제출했습니다. 공모 규모와 일정은 공개되지 않았고, Claude와 API에 바뀐 점도 없습니다. [출처](https://www.anthropic.com/news/s1-sec)

일부 투자자는 기업가치를 1조 1,000억 달러까지 낮춰 보는 것으로 전해집니다. 논의는 1조 2,000억 달러에서 1조 3,000억 달러 사이에 모였습니다. [출처](https://news.hada.io/topic?id=36726)

반면 회의론도 함께 커졌습니다. Simon Willison이 인용한 Nilay Patel은 지금의 AI 제품이 비용을 정당화하지 못한다고 주장했습니다. 그는 광고 없이도 가치가 분명한 제품이 해법이라고 봤습니다. [출처](https://simonwillison.net/2026/Nov/6/nilay-patel)

실속을 가르는 기준은 도구가 어디에 놓이느냐입니다. ActivTrak은 지식 노동자 **9,140명**을 조사했습니다. 기존 도구에 내장된 AI 사용자는 시간당 0.6회 앱을 전환했습니다. 반면 웹 기반 AI 도구 사용자는 1.7회에서 4.2회를 전환했습니다.

ActivTrak은 이 전환 부담을 회전의자 세금(Swivel Chair Tax)이라고 불렀습니다. 다만 AI를 많이 쓰는 사람의 근무 시간이 더 길다는 결과는 이전 대규모 조사와 엇갈립니다. 두 조사는 표본과 기간이 달라 단정하기 어렵습니다. [출처](https://www.itworld.co.kr/article/4244936/ai-%eb%8f%84%ec%9e%85%ea%b3%bc-%ec%a7%81%ec%9b%90-%ea%b7%bc%eb%ac%b4-%ec%8b%9c%ea%b0%84-%ec%97%87%ea%b0%88%eb%a6%ac%eb%8a%94-%eb%91%90-%eb%8d%b0%ec%9d%b4%ed%84%b0.html)

오늘 도구 흐름은 한 줄로 묶입니다. 비싼 모델을 더 자주 부르는 방식은 실속이 약합니다. 싼 계층과 사람 승인, 공유 기억으로 작업 흐름을 다듬는 쪽이 앞서고 있습니다.
