이번 주(11월 18일~23일) AI 도구 쪽에서 가장 쓸모 있는 신호는 새 모델이 아니었습니다. 병렬로 돌아가는 에이전트를 사람이 어떻게 감독할지에 대한 실전 답이 나왔습니다. AI에게 선택지를 펼치게 한 뒤 사람이 고르는 워크플로도 함께 공유됐습니다. 그 사이 Anthropic 상장과 리만 가설 증명 주장이 헤드라인을 채웠지만, 도구 사용법을 바꾸는 신호는 아니었습니다.

## 1. 병렬 Claude Code 세션은 매니저 세션 하나로 거를 수 있습니다

한 개발자가 GeekNews에 **Claude Code** 매니저 세션 운영기를 공개했습니다. 세션 여러 개를 병렬로 돌리자 모든 응답을 읽는 방식이 버티지 못했습니다. [출처](https://news.hada.io/topic?id=37609)

문제는 알림이었습니다. 에디터 탭의 응답 표시는 "서브에이전트 결과 대기" 같은 중간 보고에도 켜졌습니다. 따라서 어느 세션이 실제로 판단을 기다리는지 구분하기 어려웠습니다.

해법은 워커 세션들에 대한 결정 권한을 쥔 별도 매니저 세션입니다. 회사의 위임 전결 관행을 본뜬 구조입니다. 기본 화면에는 요점과 대기 중인 결정만 올라옵니다.

필요할 때만 한 단계씩 내려갑니다. 먼저 상세 설명을 보고, 그래도 부족하면 워커의 원문 출력을 엽니다. 매니저는 워커의 질문을 **네 갈래**로 나눕니다.

- 자율 처리
- 처리 후 사후 보고
- 판단이 필요한 사안으로 상신
- 직접 지시가 필요한 사안으로 상신

이 구조가 통한 이유는 단순합니다. 워커 질문 상당수는 이미 답이 정해져 있었습니다. 합의된 계획의 다음 단계를 묻는 식이었습니다.

도입 순서도 제시됐습니다. 처음에는 '수습 기간'을 두고, 매니저는 자신이 내렸을 결정을 보고만 합니다. 신뢰가 쌓이면 자율 범위를 조금씩 넓힙니다.

또한 "알아서 처리" 규칙을 매니저 한 곳에 모으는 것이 핵심입니다. 그러면 워커마다 같은 규칙을 지시문에 반복해 넣지 않아도 됩니다. 개발자라면 네 갈래 분류표를 매니저 지시문에 옮기는 것부터 시작하면 됩니다.

강의에서는 멀티 에이전트를 도구 문제가 아닌 조직 설계 문제로 보여 주는 예제로 쓸 수 있습니다. 수강생이 결재 구조를 직접 정의해 보는 실습으로 이어 가기도 좋습니다.

## 2. 정답을 묻기 전에 AI에게 변형을 모두 펼치게 합니다

Simon Willison이 11월 22일 'Select Styling Specimens'라는 HTML 페이지를 공개했습니다. HTML `<select>` 상자를 꾸미는 여러 방식을 한 장에 나란히 보여 주는 페이지입니다. 제작에는 **Claude Fable 5.2**를 썼습니다. [출처](https://simonwillison.net/2026/Nov/22/select-styling)

배경은 브라우저 편차입니다. select 상자는 브라우저마다 다르게 그려지고, 크롬의 기본 모양은 투박합니다. 그래서 그는 이 페이지를 데스크톱과 모바일 브라우저 전부에서 캡처할 계획입니다.

그가 고른 설정은 다음과 같습니다.

- `appearance: none`으로 기본 모양 제거
- 안쪽 여백 `padding: 0.5em 2.25em 0.5em 0.75em`
- `1px solid #c4cbd3` 테두리와 `6px` 둥근 모서리
- 흰 배경 위 인라인 SVG 화살표(data URI)
- 화살표 위치 `no-repeat right 0.75em center / 0.75em`

다만 핵심은 결과 CSS보다 방법입니다. 먼저 AI에게 모든 변형을 담은 일회용 스페시먼(Specimen) 페이지를 만들게 합니다. 이어서 같은 페이지를 여러 브라우저에서 띄워 비교하고, 그다음에 하나를 고릅니다.

이 방식은 버튼과 체크박스, 날짜 입력처럼 편차가 큰 요소에 그대로 응용할 수 있습니다. 프롬프트에 변형마다 이름표와 CSS를 함께 표시하라고 요구하면 비교가 쉬워집니다. 페이지는 버리는 것이 전제이므로 코드 품질에 공을 들일 필요도 없습니다.

프런트엔드 강의에서는 이 방식을 정답 하나를 묻는 대신 선택지를 펼쳐 놓고 고르는 시연으로 쓸 수 있습니다. 수강생에게 AI의 역할이 '결정'이 아니라 '탐색 비용 절감'임을 보여 줄 수 있습니다.

## 3. AI 코드가 잘 돌아갈수록 보안 검사는 더 기계적으로 걸어야 합니다

ITWorld Korea가 예산 없이 90일 안에 AI 생성 코드의 보안을 챙기는 우선순위를 정리했습니다. 대상 도구는 Claude Code와 Cursor, GitHub Copilot, Amazon Q Developer입니다. [출처](https://www.itworld.co.kr/article/4251851/조직이-ai가-생성한-코드의-보안을-어떻게-확보할-수-있.html)

기사가 인용한 SusVibes 벤치마크는 실제 오픈소스 프로젝트의 기능 요청 186건으로 구성됩니다. 보안 지침 없이 기능 설명만 받은 에이전트는 최대 **57%** 확률로 작동하는 코드를 냈습니다. 반면 안전한 코드는 **11.8%**에 그쳤습니다.

Datadog의 Bianca Langford는 AI 출력을 '신뢰할 수 없는 입력'으로 다루라고 권합니다. 코드베이스에 들어오기 전에 스스로 안전함을 입증해야 한다는 뜻입니다. 기사가 제시한 실행 항목은 다음과 같습니다.

- 모든 풀 리퀘스트(Pull Request)에 정적 분석 실행
- 같은 단계에서 시크릿 스캔과 의존성 점검 실행
- 같은 검사를 점차 에디터 단계로 앞당기기
- 승인한 AI 도구만 허용하고 어시스턴트의 접근 범위 제한
- 오래된 라이브러리와 약한 입력 검증을 잡도록 리뷰어 교육
- 과도하게 열린 기본값도 리뷰 점검 항목에 포함

Mimecast의 최고정보보안책임자(CISO)는 한 가지를 더 제안합니다. AI가 관여한 변경마다 책임자 한 명의 이름을 PR 기록에 남기라는 것입니다. Semgrep의 Katie Paxton-Fear는 AI 코드가 충분히 잘 돌아가서 개발자가 비판적으로 보지 않게 된다고 지적합니다.

여기에 데이터베이스 쪽 신호가 겹칩니다. Supabase는 매달 새로 생기는 400만 개 이상의 데이터베이스 중 약 70%가 에이전트나 AI 도구에서 나온다고 밝혔습니다. 그러나 개발 중 운영 데이터를 안전하게 다루는 문제는 아직 풀리지 않았습니다. [출처](https://news.hada.io/topic?id=37687)

따라서 코딩 에이전트에 데이터베이스 권한을 줄 때도 같은 원칙을 적용해야 합니다. 강의에서는 "작동한다"와 "안전하다"를 따로 채점하는 과제로 두 수치의 격차를 체감시킬 수 있습니다.

## 4. Gemini Enterprise는 사내 도구 연결의 참조 구조를 내놓았습니다

구글 개발자 블로그가 **Gemini Enterprise** 연동 가이드 두 편을 공개했습니다. 첫째는 사내 MCP 서버를 외부 노출 없이 붙이는 방법입니다. 둘째는 맞춤 화면을 만들 때 인증을 세 겹으로 나누는 방법입니다.

MCP(Model Context Protocol) 서버는 Cloud Run에서 돌고 StreamableHTTP 전송을 씁니다. 트래픽은 Egress Agent Gateway와 Private Service Connect를 거칩니다. 서버 주소는 FQDN 단위로 범위를 정한 Private Cloud DNS로 찾습니다. [출처](https://developers.googleblog.com/how-to-securely-connect-internal-cloud-run-mcp-servers-to-gemini-enterprise)

인증은 헤더 두 개를 쓰는 OAuth 2.0 방식입니다. 이 구조 덕분에 에이전트는 사내 도구에 닿되, MCP 서버는 공개 인터넷에 드러나지 않습니다.

두 번째 글은 `:streamAssist` API 위에 맞춤 화면을 올리는 경우를 다룹니다. 이때 개발자는 인증 세 겹을 직접 구현해야 합니다. [출처](https://developers.googleblog.com/how-to-handle-user-connector-and-agent-auth-in-gemini-enterprise-with-a-custom-ui)

- 사용자와 워크로드: Google Identity 또는 Identity Federation
- 외부 커넥터: 3자 OAuth(3LO)를 Keystore에서 관리
- 맞춤 ADK 에이전트: 도구별 OAuth를 필요할 때 발급
- 에이전트 설정 위치: Vertex AI Agent Engine과 GCP Auth Manager

세 겹을 처음부터 분리하면 누가, 어떤 커넥터로, 어떤 도구를 썼는지 따로 추적할 수 있습니다. 다만 두 글 모두 요약본에는 단계별 명령이 없으므로 원문을 확인해야 합니다.

오픈 모델 쪽 신호도 있었습니다. 구글은 Tunix와 Gemma 4로 도구를 쓰는 멀티턴 에이전트를 TPU에서 학습하는 안내서를 냈습니다. 학습에는 비동기 vLLM 롤아웃과 에이전트형 GRPO를 씁니다. 다만 수치나 설정값은 요약에 없습니다. [출처](https://developers.googleblog.com/multi-turn-agentic-reinforcement-learning-with-tunix-and-gemma-4-on-google-tpus)

기업 대상 강의라면 MCP 가이드를 참조 구조로 활용할 수 있습니다. 사내 도구를 에이전트에 연결할 때 무엇을 막아야 하는지 설명하는 데 쓸 만합니다.

## 5. 헤드라인은 리만 가설과 상장이었지만, 실속은 하네스에 있었습니다

이번 주 헤드라인은 굵었습니다. 수학자 Levent Alpöge는 Claude와 작업하며 리만 가설 증명을 찾았다고 믿는다고 밝혔습니다. 다만 어떤 모델과 워크플로를 썼는지, 외부 검증을 거쳤는지는 공개되지 않았습니다. [출처](https://simonwillison.net/2026/Nov/20/levent-alpoge)

같은 시기 Ravi Vakil은 Alessandro Masullo의 일반화 리만 가설 증명안을 알렸습니다. 그는 이 작업이 AI 없이 사람만으로 이뤄졌다고 강조했습니다. 정리를 마치기 전의 초안이 앞당겨 공개된 상태입니다. [출처](https://simonwillison.net/2026/Nov/20/ravi-vakil)

도구 관점에서 쓸모 있는 장면은 따로 있었습니다. Masullo 원고를 Lean으로 형식화하는 진행 현황판이 Claude 아티팩트(Artifact) 공개 링크로 공유됐습니다. 장기 프로젝트의 진척을 링크 하나로 보여 주는 방식은 강의 과제 관리에도 응용할 수 있습니다. [출처](https://claude.ai/artifact/CtQyX8qfYAF822bgHJHHE3)

Latent Space도 형식 검증(Formal Verification)을 저품질 AI 코드에 맞설 수단으로 다뤘습니다. AI와 Lean의 결합이 전문가 작업을 자동화하기 시작했다는 진단입니다. [출처](https://latent.space/p/formal-verification)

시장 뉴스는 빛과 그림자가 갈렸습니다. Anthropic은 11월 19일 주당 83달러에 **11억 2,700만 주**의 기업공개(IPO)를 마쳤습니다. 주가는 111.50달러로 시작해 97.17달러로 첫날을 마감했습니다. [출처](https://www.anthropic.com/news/ipo-close)

Latent Space는 기업가치를 1조 5,000억 달러로 전했습니다. 반면 WSJ는 이번 상장을 AI 주식 약 4조 달러 하락의 일부로 묘사했습니다. 어느 해석이든 Claude Code 사용법은 바뀌지 않았습니다. [출처](https://www.wsj.com/finance/stocks/anthropics-ipo-bust-punctuates-4-trillion-ai-wipeout-on-wall-street-f1f1ec90)

Gemini 4 Neon이 Opus 5.5와 겨룬다는 블로그 글도 주목받았습니다. 그러나 근거 자료는 제시되지 않았으므로 자기 작업으로 두 모델을 직접 비교한 뒤 판단해야 합니다. [출처](https://micjm.com/blog/gemini-4-neon-looks-like-a-top-model)

실속은 하네스(Harness)를 다듬는 사람들에게서 나왔습니다. mod_wsgi를 만든 **Graham Dumpleton**은 AI로 Rust 기반 Python 서버 Muru를 만들고 있습니다. 그는 3주 동안 거의 매일 개발 기록을 공개했습니다. [출처](https://simonwillison.net/2026/Nov/21/muru)

그는 무엇이 아직 부족한지 판단하는 일은 여전히 자기 몫이라고 썼습니다. 깊은 도메인 지식이 AI 작업의 방향을 잡는다는 사례입니다. 개발 과정을 공개 기록으로 남기는 방식도 참고할 만합니다.

ClawDOS는 반대편 극단에서 같은 교훈을 줍니다. 4.77MHz 8088과 640KB RAM의 IBM PC XT에서 Claude와 함께 코드를 쓰고 컴파일합니다. 176KB짜리 DOS 하네스가 요청 구성과 도구 실행, 대화 저장을 맡습니다. [출처](https://news.hada.io/topic?id=37604)

TLS 연결은 별도의 최신 PC가 중계합니다. 컴파일할 때는 하네스가 상태를 저장하고 스스로 내려가 Turbo C에 메모리를 내줍니다. 따라서 에이전트 루프의 핵심은 전송 계층과 떼어 낼 수 있고, 아주 작은 환경에도 들어갑니다.

GeekNews의 한 에세이는 이를 한 문장으로 정리합니다. 모델은 두뇌이고, Codex나 Claude Code 같은 하네스는 외골격이라는 비유입니다. [출처](https://news.hada.io/topic?id=37680)

이번 주 도구 흐름은 한 줄로 묶입니다. 모델 경쟁과 시장 소음이 커질수록, 감독 구조와 검증 절차를 손에 쥔 쪽이 실속을 챙겼습니다.
