## 1. 결정 전용 모델: OpenAI Decisions API로 라우팅·필터링 최적화

**OpenAI Decisions API**는 2026년 10월 공개된, "결정 전용" 경량 엔드포인트입니다.  
일반 채팅 모델 대신, **행동 선택과 점수, 이유**를 구조화해서 돌려주는 것이 핵심입니다.  
요금과 지연이 낮아, 프론트엔드 혹은 미들웨어에 붙여 자잘한 결정을 자주 호출하기 좋습니다. [출처](https://openai.com/index/decisions-api)

### 어떻게 쓰는가: 패턴 3개만 잡으면 됩니다

1) **라우팅·필터링**

- 프롬프트에 "상황, 가능한 액션 목록, 출력 포맷"을 짧게 정의합니다.  
- 모델 설정은 `temperature=0`, 짧은 `max_tokens`로 고정성을 높입니다.  

예시 설계:

- 입력 JSON  
  - `context`: 유저 입력, 요청 메타데이터  
  - `options`: `["block", "moderate", "allow"]`  
- 출력 기대  
  - `{"action": "allow", "score": 0.92, "reason": "…"}`  

이 패턴을 **콘텐츠 필터, 라우팅, 스팸 차단, 워크플로 분기**에 그대로 재사용합니다.

2) **피처 플래그·A/B 스위치**

- 프론트엔드나 BFF에서 "어떤 변형을 보여줄지"를 Decisions에 묻습니다.  
- 예: `options`를 `["variant_a","variant_b","control"]`로 주고,  
  유저 세그먼트와 최근 행동을 `context`에 넣습니다.  

응답으로 받은 `action`을 바로 실험 버전 선택에 씁니다.  
실험 결과는 분석 도구에 따로 기록하면 됩니다.

3) **워크플로 단계 선택**

- 에이전트 파이프라인에서 "추가 정보 요청 vs 바로 실행 vs 사람에게 패스"를 결정합니다.  
- `options`에 `["ask_user","auto_execute","escalate_to_human"]`처럼 명시합니다.  

결과는 오케스트레이션 코드에서 `if result.action === "..."` 형태로만 처리하면 됩니다.

### 구현 팁과 강의용 포인트

- **프롬프트를 짧고 규범적으로** 적습니다.  
  "무조건 아래 중 하나만 골라라, JSON만 출력"이라고 분명히 씁니다.
- **로깅을 구조화**합니다.  
  `context`, `options`, `action`, `score`를 모두 로그에 남기면,  
  나중에 규칙 기반으로 되돌리거나 하이브리드 전략을 세우기 쉽습니다.
- 강의에서는 "복잡한 if-else 블록"을 Decisions 호출로 치환하는 예제가 유용합니다.  
  한 시간 안에 "룰 기반 → LLM 기반 결정기" 리팩터링 실습을 만들 수 있습니다.

## 2. 거버넌스 에이전트: Google Project Chrysalis로 운영 자동화 설계

**구글 클라우드 Project Chrysalis**는 Gemini Enterprise Agent Platform과 Agent Development Kit(ADK), BigQuery, 그리고 4단계 보안 스택을 한 번에 묶은 아키텍처입니다.  
목표는 "거버넌스가 붙은, 스스로 진화하는 운영 에이전트"입니다. [출처](https://developers.googleblog.com/architecting-governed-self-evolving-ai-agents-on-gemini-agent-platform)

### 어떻게 쓰는가: 최소 구현 경로

운영·SRE 문맥을 기준으로, 다음 순서가 현실적인 최소 구성입니다.

1) **에이전트 개발**

- **Gemini Enterprise Agent Platform**에 프로젝트를 만듭니다.  
- **ADK**로 에이전트 코드를 작성합니다.  
  - 입력: 모니터링 알람, 로그, 메트릭 요약  
  - 행동: 롤백, 설정 변경 제안, 티켓 생성, 런북 검색  

2) **BigQuery로 텔레메트리 적재**

- 에이전트의 모든 의사결정과 행동을 BigQuery에 기록합니다.  
  - `timestamp, input_summary, chosen_action, confidence, outcome`  
- 이 로그를 나중에 "에이전트 학습 데이터"와 "감사 기록"으로 같이 씁니다.

3) **4단계 보안·거버넌스 스택 적용**

- **Model Armor**  
  - 프롬프트 필터링, 출력 정책을 중앙에서 정의합니다.  
  - 예: 특정 명령어, 특정 리전에 대한 조작 금지 규칙.
- **Cloud KMS**  
  - 크리덴셜과 API 키는 모두 KMS에 저장하고,  
    에이전트는 단기 토큰만 받아 쓰게 합니다.
- **Binary Authorization**  
  - 에이전트 코드와 도구 래퍼에 대한 서명·검증을 켭니다.  
  - 검증된 이미지와 버전만 프로덕션에 배포되게 합니다.
- **OPA(Open Policy Agent)**  
  - "에이전트가 할 수 있는 최대 권한"을 정책으로 정의합니다.  
  - 예: 업무 시간 외 프로덕션 쓰기 금지, 특정 팀만 특정 액션 허용.

### 실전 팁과 교육 포인트

- **모든 행동을 BigQuery에 기록**하는 것이 핵심입니다.  
  한 번 쌓이면, "에이전트 리그레션 테스트"와 "사후 감사" 둘 다 해결됩니다.
- 초기는 "완전 자동 조치" 대신,  
  **제안만 생성하고 SRE가 승인하는 하이브리드 모드**로 두는 것이 안전합니다.
- 강의에서는 기존 "런북 기반 장애 대응"을 예제로 삼고,  
  같은 절차를 Chrysalis 아키텍처로 이전하는 랩을 구성하면 활용도가 높습니다.

## 3. 레거시 코드 리라이트: Claude Code와 VibeTerm 멀티 에이전트 운용

ITWorld는 **Claude Code 코딩 에이전트**가 BASIC 코드를 Go와 WebAssembly로 변환하는 실험을 다뤘습니다.  
동시에 **VibeTerm**은 여러 Claude Code, Codex 인스턴스를 한 화면에서 병렬로 돌리는 무료 윈도우 터미널을 공개했습니다. [출처1](https://www.itworld.co.kr/article/4239373) [출처2](https://news.hada.io/topic?id=35841)

### 어떻게 쓰는가: 레거시 리라이트 워크플로

1) **스펙·테스트부터 정리**

- 레거시 코드의 "기대 동작"을 문서와 테스트로 먼저 고정합니다.  
- 가능하면 간단한 회귀 테스트라도 작성합니다.

2) **Claude Code로 단계별 변환**

- 코드베이스와 목표를 한 번에 설명합니다.  
  - 원본 언어와 타깃 언어, 타깃 플랫폼  
  - 허용·금지 패턴(예: 전역 변수 금지, 동시성 모델 등)  
- 요청은 "한 번에 전체"보다,  
  **모듈 단위·폴더 단위**로 쪼개는 것이 검증과 롤백에 유리합니다.
- 변환이 끝날 때마다 테스트를 돌리고,  
  실패 케이스를 다시 Claude Code에 입력해 수정 루프를 돕습니다.

3) **VibeTerm으로 멀티 에이전트 구성**

VibeTerm에서 창을 나누어 다음처럼 씁니다.

- 왼쪽: "변환 에이전트"  
  - 실제 코드 변환과 리팩터링을 담당합니다.
- 오른쪽 위: "테스트 분석 에이전트"  
  - 실패 테스트 로그를 요약하고 원인 가설을 만듭니다.
- 오른쪽 아래: "문서·주석 에이전트"  
  - 변경된 모듈에 대한 설명과 주석을 정리합니다.

각 창은 서로 다른 Claude Code 서버나 로컬 모델에 붙을 수 있습니다.  
VibeTerm의 "고정 핀" 기능으로 자주 쓰는 에이전트를 고정하면,  
맥락 전환 시간을 줄이고 한 번에 여러 스레드를 진행할 수 있습니다.

### 실전 팁과 강의 아이디어

- 브랜치는 "원본(main) + 변환용(feature/modernize-xxx)" 구조로 단순하게 유지합니다.  
  에이전트가 만든 커밋은 모두 별도 브랜치에 두고 코드 리뷰 후 머지합니다.
- 테스트 실패 로그를 **그대로 붙이지 말고 최소한으로 요약**해서 주십시오.  
  "에러 메시지 + 입력값 + 기대값" 정도가 가장 잘 동작합니다.
- 강의에서는 "작은 레거시 프로젝트 하나"를 정해,  
  학생들이 VibeTerm으로 세 에이전트를 띄우고 각자 역할을 주는  
  "AI 협업 리라이팅" 실습을 만들 수 있습니다.

## 4. CLI와 스킬 표준: OpenAI CLI와 Agent Skills로 자동화·호환성 확보

OpenAI는 **공식 OpenAI CLI**를 제공하고 있습니다.  
또한 Anthropic은 **Agent Skills 표준**을 리눅스 재단 산하 Agentic AI Foundation에 기부해, 벤더 중립 규격이 되었습니다. [출처1](https://news.hada.io/topic?id=35818) [출처2](https://simonwillison.net/2026/Oct/22/donating-agent-skills)

### OpenAI CLI: "스크립트만으로 PoC 끝내기"

1) 설치 후 기본 패턴

- 설치 후 `OPENAI_API_KEY`를 환경 변수로 세팅합니다.  
- 채팅 호출 예  
  - `openai chat.create -m gpt-4.1-mini -i prompt.txt`  
- 이미지 생성 예  
  - `openai images.generate -m gpt-image -p "..." -o img.png`

2) 반복 작업 자동화

- 데이터 파일 여러 개를 배치 요약할 때,  
  쉘 스크립트에서 파일 목록을 돌며 `chat.create`를 호출합니다.
- CI에서 "프롬프트 테스트"를 추가해,  
  특정 입력에 대한 모델 응답이 기준과 크게 달아나면 알람을 보낼 수 있습니다.

### Agent Skills 표준: 에이전트 능력의 "공용 인터페이스"

Agent Skills는 에이전트가 호출할 수 있는 **스킬의 스키마와 매니페스트**를 정의합니다.  
이제 이 규격이 **AAIF**로 넘어가면서, 한 벤더에 묶이지 않는 표준이 됩니다.

실전 적용 방법은 다음과 같습니다.

- 내부 툴을 "스킬"로 정의합니다.  
  - 입력 파라미터, 권한, 예상 부작용을 매니페스트로 적습니다.
- 이 매니페스트를 기준으로  
  **Claude, 다른 에이전트 플랫폼, 자체 에이전트 런타임**이 모두 같은 스킬을 공유하게 합니다.
- 스킬 로더, 권한 체크, 스킬 카탈로그 UI는  
  모두 이 매니페스트만 읽도록 설계합니다.

### 베스트 프랙티스와 교육 포인트

- 지금부터 새 툴을 만들 때는  
  "API 문서 + Agent Skills 매니페스트"를 한 세트로 준비하는 것이 좋습니다.
- OpenAI CLI는 "API 패턴을 설명하기 위한 강의 도구"로 유용합니다.  
  브라우저 없이도 실습실에서 바로 모델 호출 흐름을 보여줄 수 있습니다.
- 강의 하나를 "CLI를 사용해 한 시간 안에 에이전트 스킬 프로토타입 만들기"로 구성하면,  
  개발자들이 API 호출과 스킬 설계를 빨리 몸에 익힐 수 있습니다.

## 5. 보안과 품질: PHP2Shell, Patch the Planet, 형식 검증이 주는 체크리스트

최근 **PHP2Shell**로 명명된 두 개의 원격 코드 실행 취약점이 공개되었고,  
OpenAI의 **Patch the Planet** 프로그램과 GPT-5.6 Sol이 그 발견에 기여했습니다.  
동시에 Anthropic은 "LLM이 형식 검증을 대규모로 가능하게 한다"는 연구를 발표했습니다. [출처1](https://www.latent.space/p/ainews-openais-patch-the-planet-program) [출처2](https://www.itworld.co.kr/article/4239388) [출처3](https://www.anthropic.com/research/formal-verification)

### 오늘 당장 필요한 보안 액션

- **PHP 사용 중인 서비스는 즉시 패치**해야 합니다.  
  배포판 혹은 PHP 그룹의 보안 공지를 확인하고,  
  해당 CVE가 포함된 10월 패치 버전으로 올립니다.
- 패치 전·후로 **웹 서버 로그를 10월 17일 전후부터 스캔**합니다.  
  알려진 공격 패턴과 의심스러운 요청을 확인합니다.
- 즉시 패치가 어려운 경우,  
  WAF나 리버스 프록시에서 임시 규칙을 적용해 공격 패턴을 차단합니다.

Patch the Planet 사례처럼, **AI 보안 연구는 반드시 사람 검증과 조율**이 필요합니다.  
모델이 찾은 취약점은 사람이 재현·분석하고,  
벤더와 협의된 일정 내에서 패치와 공개를 진행해야 합니다.

### 품질 측면: 형식 검증과 아키텍처 부채

Anthropic 연구는 LLM이 **불변식, 보조 정리, 증명 스케치**를 자동으로 생성하면,  
자동 증명기와 결합해 대규모 코드 검증이 가능해진다는 점을 보여줍니다.  
하지만 Armin Ronacher의 지적처럼,  
나쁜 아키텍처와 보안 부채 위에 AI를 얹으면 문제만 증폭됩니다. [출처](https://simonwillison.net/2026/Oct/22/armin-ronacher)

실무자가 가져갈 체크리스트는 다음과 같습니다.

- AI 기능을 붙이기 전,  
  **의존성 정리와 권한 경계 최소화**를 먼저 합니다.
- 중요한 모듈에는  
  "LLM이 만든 검증 보조 자료 → 증명기 검증" 루프를 실험적으로라도 도입합니다.
- 새 AI 기능은 항상  
  **위협 모델링과 롤백 계획**을 포함한 디자인 리뷰를 거칩니다.
