## 1. Claude Dynamic Workflows: 멀티 에이전트 파이프라인 설계

**Anthropic의 Claude Dynamic Workflows**가 공개되면서, "큰 프롬프트 하나" 방식 대신 에이전트 파이프라인을 구성하는 패턴이 제시됐습니다. 각 단계가 역할, 입력, 성공 조건을 명시한 작은 에이전트로 나뉘고, 시스템이 결과를 다음 에이전트로 라우팅합니다. [출처](https://www.latent.space/p/claude-dynamic-workflows)

**기본 설계 패턴은 세 단계로 나누면 이해가 쉽습니다.**  
1) **Planner 에이전트**  
- 입력: 자연어 요구사항, 리포지토리 스냅샷, 제한조건.  
- 출력: 해야 할 작업 목록, 순서, 각 작업의 완료 기준.  
- 프롬프트 핵심:  
  - "출력은 JSON 배열"처럼 구조를 강제합니다.  
  - 각 작업에 `id`, `설명`, `완료조건`을 포함하도록 요구합니다.  

2) **Implementer 에이전트**  
- 입력: 특정 작업 `id`와 해당 작업 설명, 완료조건, 현재 코드 상태.  
- 행동: 코드를 수정하거나 파일을 생성합니다.  
- 출력: 변경된 파일 목록, 변경 설명, 실행한 명령, 테스트 결과 요약.  

3) **Reviewer 에이전트**  
- 입력: 구현 결과, diff, 테스트 로그.  
- 출력: "성공 / 실패" 판정과, 실패 시 재시도 지침 또는 버그 리포트 수준의 피드백.  

**워크플로 정의 요령입니다.**  
- 각 단계는 "입력 스키마, 출력 스키마, 성공 조건" 세 가지로 정의합니다.  
- 성공 조건은 사람이 평가할 필요가 없도록, 가능한 한 자동화합니다.  
  - 예: "테스트 결과에 `FAILED`가 포함되지 않을 것",  
  - "변경된 파일 수가 0이면 실패로 간주할 것" 등.  
- 워크플로 코드에서는 "어느 출력이 어느 에이전트의 입력으로 가는지"를 명시합니다.  
  - 예: `planner.plan` 결과의 각 아이템을 큐에 넣고,  
  - 큐의 항목을 `implementer.run`에 전달한 뒤,  
  - 그 결과를 `reviewer.check`에 전달하는 식입니다.  

**프롬프트와 성공 판정 설계 베스트 프랙티스입니다.**  
- 각 역할 프롬프트는 "역할, 금지사항, 출력 형식, 종료 기준"을 꼭 포함합니다.  
- "성공인지 모르겠으면 질문하고 끝내지 말 것"처럼 불확실성 처리 규칙을 넣습니다.  
- 실패시 재시도 규칙을 시스템 레벨에 두고, 에이전트 프롬프트에서는  
  - "동일 시도는 최대 2번, 이후에는 인간 도움 요청"처럼 상한을 둡니다.  

이 구조는 유닉스 파이프처럼, 작은 에이전트를 조합해 복잡한 과제를 해결합니다. 강의에서는 "단일 거대 프롬프트"와 "역할 분리형 워크플로"를 비교 시연하면, 학습자가 에이전트 설계의 필요성을 바로 체감할 수 있습니다.

## 2. GitHub Copilot app: 코드베이스를 "가르치는" 방법

**GitHub Copilot app**이 초보자용 가이드를 공개하며, 레포지토리별 "지식 주입" 방법을 문서화했습니다. 핵심은 **커스텀 인스트럭션, 스킬, 에이전트/MCP 연동** 세 가지를 조합해 코파일럿을 팀 전용 조수로 만드는 것입니다. [출처](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-how-to-teach-copilot-about-your-codebase)

**1) 스킬(Skills) 파일로 도메인 지식 고정하기**  
- 레포 루트나 `.github` 아래에 스킬 정의 파일을 둡니다.  
  - 예: `copilot-skills.md` 또는 설정 마법사가 안내하는 위치.  
- 포함하면 좋은 내용입니다.  
  - 비즈니스 도메인 용어 정의.  
  - 주요 아키텍처 다이어그램 요약.  
  - 공통 패턴 예시 코드와 "이 패턴을 언제 쓰는가".  
- 작성 팁입니다.  
  - "우리 서비스는 멀티테넌트 SaaS이고, 테넌트 경계는 이 필드로 구분된다"처럼  
    일반 LLM이 모르는 규칙을 명확히 서술합니다.  
  - "신규 서비스는 이 베이스 컨트롤러를 상속하라" 같은 구체 규칙을 넣습니다.  

**2) 커스텀 인스트럭션으로 스타일·정책 강제하기**  
- Copilot app 설정에서 해당 레포지토리 전용 인스트럭션을 등록합니다.  
  - 예: "테스트는 항상 RSpec으로 작성하고, 기존 테스트 패턴을 먼저 확인하라."  
  - "새 엔드포인트는 OpenAPI 스펙에 먼저 추가하라."  
- 자주 반복하는 요구사항은 여기로 올립니다.  
  - PR 템플릿, 커밋 메시지 스타일, 예외 처리 규칙 등입니다.  
- 강의나 팀 온보딩에서는 이 인스트럭션을  
  - "팀 개발 문화의 기계 가이드라인"으로 설명하면 이해가 빠릅니다.  

**3) 커스텀 에이전트와 MCP 서버 연동하기**  
- Copilot app은 **MCP(Model Context Protocol)** 서버와 연동해  
  - **Playwright**, 테스트 러너, 환경 재현 도구를 호출할 수 있습니다.  
- 설정 예시입니다.  
  - Playwright MCP 서버를 등록합니다.  
  - 인스트럭션에 "프론트엔드 변경 시 Playwright 테스트를 실행하라"를 추가합니다.  
- 이렇게 하면, 코파일럿이  
  - "코드 제안 → 테스트 실행 요청 → 결과 보고"까지 한 흐름 안에서 처리합니다.  

**실무 팁입니다.**  
- 반복 설명하는 레포 맥락은 "프롬프트"가 아니라 "스킬 + 인스트럭션"으로 옮깁니다.  
- 신규 기여자 온보딩 시,  
  - "레포 읽기 전 Copilot 스킬 파일 먼저 읽기"를 체크리스트에 넣으면  
  - 사람과 코파일럿이 같은 규칙을 공유하게 됩니다.  

개발 교육에서는 이 흐름을 "사람 문서화 vs 도구 문서화"로 대비해 보여주면 좋습니다. 같은 내용을 스킬과 인스트럭션에 옮겼을 때, 코드 제안 품질이 어떻게 달라지는지 라이브 시연하면 효과가 큽니다.

## 3. Python 3.15 지연 임포트: CLI·플러그인 콜드스타트 줄이기

**Python 3.15**가 **명시적 지연 임포트(lazy import, PEP 810)**를 도입했습니다. 이제 모듈 상단에서 `lazy import`를 쓰면, 실제 사용 시점까지 로딩을 미룹니다. [출처](https://simonwillison.net/2026/Oct/12/python-3-15)

**기본 문법입니다.**  
```python
# 기존
import json
from pathlib import Path

# 3.15 이후
lazy import json
lazy from pathlib import Path
```

- 사용 코드는 바꿀 필요가 없습니다.  
- 모듈이 처음 사용될 때 자동으로 로드됩니다.  

**어디에 적용하면 좋은지입니다.**  
- 시작 속도가 중요한 **CLI 도구**와 **플러그인 시스템**입니다.  
- 예를 들어 다음과 같은 경우입니다.  
  - `sentence_transformers`, `pandas`, `torch`처럼 무거운 패키지.  
  - 특정 서브커맨드에서만 필요하지만, 항상 임포트되던 모듈.  

**적용 절차 예시입니다.**  
1. CLI나 서버의 "메인 엔트리" 모듈에서,  
   - import 시간이 긴 모듈 리스트를 만듭니다.  
2. 이들만 `lazy import`로 바꿉니다.  
3. `time python -m yourtool --help`처럼 콜드스타트 시간을 비교합니다.  
4. 예외적으로 초기화 부작용에 의존하는 모듈은  
   - 지연 임포트에서 제외합니다.  

Simon Willison이 공개한 **`datasette-ports 0.4`**도 이런 최적화와 잘 맞습니다. 이 플러그인은 현재 머신에 떠 있는 **Datasette 인스턴스와 PID**를 보여줍니다. [출처](https://simonwillison.net/2026/Oct/12/datasette-ports)

활용 팁은 다음과 같습니다.  
- `pip install --upgrade datasette-ports`로 업데이트합니다.  
- 플러그인의 인스턴스 목록에서 원하는 PID를 찾습니다.  
- 새 파이썬 3.15 프로파일러나 디버거를,  
  - 해당 PID에 직접 attach해 성능 분석을 합니다.  

강의 현장에서는 "지연 임포트 적용 전/후 CLI 응답 속도"를 비교하는 실습이 효과적입니다. 또 Datasette PID를 기반으로 프로파일러를 붙이는 데모를 곁들이면, 성능 튜닝 흐름 전체를 한 번에 보여줄 수 있습니다.

## 4. Clef·Strands: 에이전트 스택의 의사결정 전용 레이어

**Cloudflare의 Clef/Clef-flash**와 **AWS의 Strands Decider 2B**처럼, **의사결정 전용 모델**이 에이전트 스택의 별도 레이어로 떠오르고 있습니다. 이 모델들은 경량이며, 도구 선택과 작업 라우팅, 다음 행동 결정을 전담합니다. [출처](https://www.itworld.co.kr/article/4234067/ai-%ec%97%90%ec%9d%b4%ec%a0%84%ed%8a%b8%ea%b0%80-%eb%b0%9c%ec%a0%84%ed%95%a8%ec%97%90-%eb%94%b0%eb%9d%bc-%ea%b3%b5%ea%b8%89%ec%97%85%ec%b2%b4%eb%93%a4%ec%9d%80-%ec%9d%98%ec%82%ac%ea%b2%b0%ec%a0%95.html)

**실전 구조는 이렇게 나뉩니다.**  
- 의사결정 모델:  
  - "어떤 도구를 언제 호출할지"를 고릅니다.  
  - 예: "검색 후 코드 수정", "즉시 코드 수정", "인간에게 escalate".  
- 메인 LLM:  
  - 실제 코드 생성, 긴 맥락 추론, 복잡한 대화 응답을 담당합니다.  

**사용 패턴 예시(Cloudflare Workers 기준)입니다.**  
1. 요청이 들어오면,  
   - Clef 같은 의사결정 모델에 "요약된 상태 + 가능한 행동 리스트"를 전달합니다.  
2. 의사결정 모델이 `{action: "run_tests", tool: "playwright"}` 같은 결과를 돌려줍니다.  
3. 워커는 해당 도구를 실행하고, 결과를 다시 의사결정 모델이나 메인 LLM으로 보냅니다.  

**중요한 포인트는 "신뢰도와 임계값 관리"입니다.**  
- 공급업체마다 "confidence score" 의미가 다릅니다.  
- 모델을 바꾸거나 두 개 이상을 병행할 때는,  
  - 자체 로그 데이터를 기반으로 **재캘리브레이션**을 해야 합니다.  
  - 예: 지난 한 달간 "confidence > 0.8일 때 실제 성공률"을 측정합니다.  

**거버넌스와 버전 관리 팁입니다.**  
- 의사결정 정책, 임계값, 질문-응답 예시는  
  - 코드와 별도 YAML이나 JSON 스키마로 분리해 버전 관리합니다.  
- 정책 변경마다 "AB 테스트"나 "점진적 롤아웃"을 적용합니다.  
  - 예: 전체 트래픽의 10%에만 새 임계값 적용.  
- 강의나 사내용 문서에서는 이 레이어를  
  - "LLM 앞단의 트래픽 라우터"로 설명하면 이해가 쉽습니다.  

이 흐름을 도입하면, 메인 LLM 호출 수를 줄이면서도 에이전트 행동이 더 예측 가능해집니다. 멀티 에이전트 실습 과제에 "의사결정 전용 소형 모델 추가"를 옵션으로 붙이면, 학습자들이 비용·속도·정확도 간 트레이드오프를 자연스럽게 체험할 수 있습니다.

## 5. 테스트 에이전트: 무의미한 그린 테스트와 에이전트 실패 패턴 잡기

AI 코딩 에이전트가 늘어나면서, "겉으로만 성공한 작업"과 "의미 없는 테스트"라는 두 가지 문제가 동시에 드러나고 있습니다. 이를 겨냥한 도구와 패턴이 나왔습니다.

먼저 **false-green-detector**는 **무의미한 테스트를 잡아내는 에이전트 스킬**입니다. CI나 코드 리뷰 에이전트 파이프라인에 넣으면, 새 테스트나 수정된 테스트를 검사해 다음을 찾아냅니다. [출처](https://news.hada.io/topic?id=35278)

- 항상 참이 되는 assertion.  
- 실제 입출력 없이 mock만 검증하는 테스트.  
- 조건은 있으나 실제 assert가 없는 케이스.  

**CI 통합 패턴입니다.**  
1. 테스트 실행 후, 변경된 테스트 파일 목록을 수집합니다.  
2. false-green-detector 에이전트에 파일 내용과 diff를 전달합니다.  
3. 에이전트가 "위험도 라벨 + 개선 제안"을 결과로 반환합니다.  
4. 이 결과를 PR 코멘트로 붙이거나,  
   - 위험도 상위일 경우 머지를 막는 규칙을 추가합니다.  

동시에, **Claude Code, Codex, Gemini CLI** 등 에이전트 세팅에서는  
"완료 기준이 모호해 실제 변경이 없는 성공 리포트"가 자주 발생합니다. [출처](https://news.hada.io/topic?id=35266)

**해결을 위해 "증거 기반 완료 조건"을 강제하는 것이 핵심입니다.**  
- 각 작업 템플릿에 다음을 추가합니다.  
  - "실행한 명령 목록".  
  - "실제 결과 증거" 필수 기입.  
- 예시 완료 요건입니다.  
  - 파일 변경 작업:  
    - 변경된 파일명과 변경된 총 행 수를 출력할 것.  
  - 커밋 작업:  
    - 최종 커밋 해시를 명시할 것.  
  - 테스트 실행 작업:  
    - 테스트 요약과 실패 시 전체 스택 트레이스를 포함할 것.  

**프롬프트/설정 예시 문장입니다.**  
- "작업 완료 시, 실행한 명령만 나열하지 말고,  
  - 각 명령이 실제로 남긴 결과를 구체적으로 기술하라."  
- "파일 변경 작업은 항상 `파일명: 변경된 라인 수` 목록을 포함하라."  

이렇게 "실패한 테스트"와 "실패했어야 할 작업"을 조기에 잡으면, 에이전트 기반 개발에 대한 신뢰도가 올라갑니다. 강의에서는 의도적으로 무의미한 테스트를 만들어 false-green-detector를 통과시키고, 이어서 "증거 없는 완료 보고"를 하는 에이전트를 보여준 뒤, 위 규칙을 적용해 다시 시연하는 구성이 대비 효과가 큽니다.
