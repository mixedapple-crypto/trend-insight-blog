## 1. OpenAI 관리형 에이전트: 멀티스텝 자동화

**무엇이 새로웠나**  
OpenAI가 **관리형 에이전트(Managed Agents)**를 공개했습니다.  
콘솔 또는 에이전트 API에서 프롬프트, 툴, 목표를 정의하면, 에이전트가 멀티스텝으로 자율 실행하는 구조입니다.  
주요 출처는 TLDR 요약입니다. [출처](https://tldr.tech/ai/2026-09-08)

### 어떻게 쓰는가: 기본 패턴

실무 기준으로 가장 무난한 구조는 “3층 설계”입니다.

1. **역할·목표 정의 층**
   - 콘솔 또는 API에서:
     - 역할: “B2B 고객지원 티켓 분류·요약 에이전트”
     - 상위 목표: “티켓을 우선순위, 카테고리, 요약, 제안 답변과 함께 JSON으로 반환”
   - 시스템 프롬프트 예:
     - “당신은 고객지원 자동화 에이전트입니다. 티켓 텍스트를 입력받아… JSON 스키마를 만족하는 결과만 출력하십시오.”

2. **툴 정의 층**
   - 연결 예시:
     - 사내 REST API: 고객 정보 조회
     - 웹 브라우징: 관련 문서 검색
     - 파일: 제품 매뉴얼 PDF
   - 콘솔에서 각 툴에 대해:
     - 입력 스키마(필수 필드, 타입)
     - 출력 스키마
     - 호출 제한(초당 n회, 분당 n회)
     를 함께 정의합니다.

3. **실행·스케줄 층**
   - 단발 실행:
     - 에이전트 엔드포인트에 `input`(티켓 내용) 전달
   - 배치 실행:
     - 크론 또는 워크플로 엔진에서 일정 간격 호출
     - 결과를 DB나 큐(Kafka, SQS 등)에 적재

강의에서는 이 3층을 한 슬라이드에 “역할 / 툴 / 오케스트레이션”으로 나누어 설명하면 이해가 빠릅니다.

### 베스트 프랙티스: 폭주 방지·디버깅 설계

관리형 에이전트에서 가장 중요한 것은 “처음부터 디버깅 가능한 상태로 만들기”입니다.

1. **목표를 좁게 시작**
   - 안 좋은 예: “고객지원 전 과정을 자동화하라”
   - 좋은 예:
     - 1단계 에이전트: “티켓 → JSON 구조화”
     - 2단계 에이전트: “JSON → 초안 답변 작성”
     - 3단계 에이전트: “초안 + 정책 → 승인 여부 체크”
   - 에이전트 하나당 “입력 1종, 출력 1종”을 기본으로 설계하면 디버깅이 쉬워집니다.

2. **툴 가드 레일**
   - 입력·출력 스키마를 명시하고, 벗어나면 실패로 처리합니다.
   - 예: 웹 호출 툴
     - 입력: `{ "url": "https://...", "max_bytes": 100000 }`
     - 에이전트 프롬프트에 `"max_bytes는 100000을 초과할 수 없습니다."`를 명시
   - API 키·권한은 최소 권한 원칙:
     - 읽기용 키와 쓰기용 키를 분리
     - 프로덕션과 스테이징 키 분리

3. **로그 패턴**
   - 처음부터 다음을 모두 저장하는 것이 좋습니다.
     - 에이전트 입력
     - 각 툴 호출 로그(입·출력, 소요 시간)
     - 최종 출력 + 에러
   - 강의 과제로 “실패 케이스 5개를 보고 어디서 막혔는지 찾기”를 내면 에이전트 디버깅 감각을 키우기 좋습니다.

4. **강의·개발 응용**
   - 개발자 교육:
     - “Rest API를 직접 호출하는 코드 vs 에이전트가 툴로 호출하는 구조”를 비교 실습.
   - 비개발자 대상:
     - 콘솔에서 툴 없는 에이전트 → 툴 하나 추가한 에이전트로 확장해 보는 단계별 실습이 적합합니다.

## 2. ChatGPT Images 2.5: 레퍼런스·스케치 편집

**무엇이 새로웠나**  
OpenAI가 **ChatGPT Images 2.5**를 공개했습니다.  
API 모델 ID는 **gpt-image-2.5-sunburst**, **gpt-image-2.5-flare**이며, 속도와 멀티턴 지시 이해, 레퍼런스 보존이 개선되었습니다. [출처](https://simonwillison.net/2026/Sep/8/introducing-chatgpt-images-25)  
ChatGPT UI에서는 **Sketch 모드**로 직접 레이아웃을 그릴 수 있습니다. [출처](https://news.hada.io/topic?id=33377)

### API에서 어떻게 쓰는가

CLI 예시는 다음 구조입니다.

```bash
openai_image.py \
  -i https://example.com/reference.png \
  -m gpt-image-2.5-sunburst \
  "add a raccoon scientist studying the chart thoughtfully"
```

실무 자동화 시 패턴은 다음과 같습니다.

1. **레퍼런스 고정 + 텍스트 변경**
   - 상품 사진은 그대로 두고, 배너 문구·요소만 바꾸는 경우:
     - 입력:
       - 참조 이미지 URL
       - “배경과 상품은 유지하고, 상단에 한국어로 ‘가을 세일’ 텍스트 배너를 추가하라.”
   - `sunburst`를 사용하면 피사체 손상 가능성이 줄어듭니다.

2. **여러 레퍼런스 조합**
   - 강의·블로그용 일러스트 생성:
     - 인물 사진 + UI 스크린샷을 함께 넣고
     - “인물이 모니터 속 화면을 설명하는 장면으로 자연스럽게 합성하라.”처럼 지시합니다.

3. **모델 선택 가이드**
   - **gpt-image-2.5-sunburst**
     - 이미지 편집, 레이아웃 유지, 인물·제품 보존이 중요할 때
   - **gpt-image-2.5-flare**
     - 신규 생성, 썸네일·콘셉트 아트, 속도가 중요한 대량 생성 배치

### ChatGPT UI에서 Sketch 활용법

Sketch 모드는 강의·워크숍에서 특히 유용합니다.

1. **구도 먼저, 디테일 나중**
   - 참가자가 직접
     - 대략적인 박스(인물, 텍스트 박스, 차트 위치)를 그립니다.
     - 프롬프트에는 “스케치의 구도를 유지하고, 모던한 교육용 일러스트 스타일로 완성하라.” 정도만 적습니다.
   - 이 구조가 “디자이너의 와이어프레임 → 시안” 과정을 잘 모사합니다.

2. **작게, 자주 수정**
   - “이 부분만 바꿔라” 원칙:
     - 1차: 배경 색상 변경
     - 2차: 인물 표정만 조정
     - 3차: 텍스트 스타일 변경
   - 매번 프롬프트에
     - “다른 부분은 유지하고, 이 요청된 부분만 변경하라.”를 넣으면  
       누적 왜곡이 줄어듭니다.

3. **수업·프로젝트 팁**
   - 디자인 수업:
     - 학생이 Sketch로 레이아웃을 잡고, 글로 “의도”를 설명하게 합니다.
     - 결과물과 의도의 차이를 분석하는 과제로 프롬프트 설계 역량을 기를 수 있습니다.
   - 개발 실습:
     - API로 이미지 버전 히스토리를 저장하고
     - “프롬프트와 이미지 변화 추적” 대시보드를 만들어, 모델 거동을 시각화하는 프로젝트에 활용하기 좋습니다.

## 3. GPT-6 Astra: 스킬·프롬프트 재설계

**무엇이 새로웠나**  
GPT-6 **Astra** 세대 에이전트를 전제로, 기존 긴 프롬프트·스크립트 대신  
짧고 모듈화된 **스킬(Skill) 목록**으로 재설계해야 한다는 논의가 나왔습니다. [출처](https://news.hada.io/topic?id=33404)

핵심은 `Skills/AGENTS.md` 같은 문서를 “에이전트가 읽고 선택할 수 있는 카탈로그”로 바꾸는 것입니다.

### 어떻게 구성하는가: 스킬 원칙 4가지

각 스킬을 다음 4요소로 정리하는 방식이 실무에 가장 잘 맞습니다.

1. **이름**
   - `summarize_customer_email_v2`처럼 기능+버전이 드러나게 작성합니다.

2. **한 줄 설명**
   - “한국어 고객 이메일을 3문장으로 요약하고, 감정 톤을 분석한다.”
   - 자연어지만 **명령문 + 출력 형태**가 포함되도록 작성합니다.

3. **사용 조건(Preconditions)**
   - 예:
     - `input.language == "ko"`
     - `input.length <= 2000 tokens`
   - 에이전트가 “언제 이 스킬을 써야 하는지”를 기계적으로 판단할 수 있게 합니다.

4. **입·출력 명세**
   - 입력 예:
     - `email_text: string`
   - 출력 예:
     ```json
     {
       "summary": "string",
       "sentiment": "positive|neutral|negative"
     }
     ```

이렇게 만들어 두면 Astra가 “어떤 스킬을 조합할지”를 스스로 결정하기 쉬워집니다.

### 겹치는 스킬 정리와 유지보수 전략

1. **중복 스킬 합치기**
   - 나쁜 상태:
     - `summarize_email`, `summarize_ticket`, `summarize_chat_log`처럼  
       비슷한 스킬이 여러 개 존재
   - 좋은 상태:
     - `summarize_text` 하나로 통합하고, `content_type` 파라미터로 분기
   - 강의에서는 “스킬 카탈로그 리팩터링” 실습을 시키면 좋습니다.

2. **작게 쪼개되, 조합 가능하게**
   - 예: 번역 + 톤 조정
     - 스킬1: `translate_text(source_lang, target_lang, text)`
     - 스킬2: `adjust_tone(target_tone, text)`
   - 에이전트가 필요 시
     - 원문 → 번역 → 톤 조정 순으로 조합합니다.
   - 이렇게 하면 향후 톤 조정 로직만 바꾸기도 쉽습니다.

3. **프롬프트를 스크립트가 아닌 “계약”으로 보기**
   - 각 스킬 설명은
     - “에이전트에게 주는 약속 문서”에 가깝습니다.
   - 길게 맥락을 서술하기보다
     - “무엇을 받고 무엇을 돌려주는지”를 한 페이지 안에서 명확히 합니다.

### 강의·실전 응용

- 에이전트 개발 강의:
  - 1차 과제: 기존 거대 프롬프트를 스킬 5개로 분해해 `skills.md`로 재작성.
  - 2차 과제: Astra가 이 스킬을 자동 조합하도록, 상위 매니저 에이전트 프롬프트를 설계.
- 팀 실무:
  - 신규 기능을 추가할 때 “프롬프트부터 쓰기” 대신
    - 먼저 스킬 정의서 한 줄 설명과 입·출력 JSON을 작성한 뒤
    - 실제 구현과 테스트를 진행하면 유지보수가 수월해집니다.

## 4. 연구 협업 전략: Navier–Stokes 논쟁의 교훈

**무엇이 있었나**  
OpenAI의 비공개 모델로 Navier–Stokes 밀레니엄 난제를 다뤘다는 보고,  
그리고 NYU 수학자의 “경력 결정 문제에 OpenAI가 끼어들었다”는 비판이 이어졌습니다. [출처](https://simonwillison.net/2026/Sep/8/on-navier-stokes) [출처](https://techcrunch.com/2026/09/08/openai-fought-dirty-on-career-making-math-problem-says-nyu-mathematician)  

동시에 Terence Tao는 “AI가 공개 연구 문제를 평탄화(flatten) 시킨다”고 경고했습니다.  
누군가 문제를 잡았다는 소문만 나도, 대규모 AI 사용 경쟁이 촉발될 수 있다는 내용입니다. [출처](https://simonwillison.net/2026/Sep/9/terence-tao)

현업·강의 관점에서는 “AI와 함께 일할 때 우선권과 책임을 어떻게 설계할 것인가”가 핵심입니다.

### 개발자·연구자를 위한 실무 원칙

1. **비공개 모델 사용 시, 메타데이터 먼저**
   - 실험 시작 단계에서 다음을 기록합니다.
     - 사용한 모델 이름·버전
     - 모델이 훈련에 사용했을 수 있는 데이터 가정
     - 주요 프롬프트와 세션 기록 보관 위치
   - 논문·보고서 서두에 이 메타데이터를 명시하면  
     사후에 “모델이 사전 초고를 봤는가” 같은 논쟁을 줄일 수 있습니다.

2. **프롬프트·세션 기록 아카이브**
   - 재현 가능성을 위해 다음을 남깁니다.
     - 중요한 결과를 낸 세션의
       - 프롬프트
       - 중간 대화
       - 모델 버전
   - 내부 Git 리포지토리나 노트북에
     - `prompts/2026-09-navier-stokes-*.md` 형태로 저장하는 방식이 실무에 적합합니다.

3. **아이디어 공개는 단계별로**
   - Tao의 경고를 고려하면, 유망한 아이디어는:
     - 비공개 리포지토리·소규모 협업 그룹에서 먼저 검증
     - 외부 공개 시:
       - 세부 증명·알고리즘은 뒤로 미루고
       - 고수준 아이디어·문제 정의 정도만 먼저 공개
   - 스타트업·연구실 모두
     - “공개 레벨 가이드라인”을 팀 규칙으로 만드는 것이 좋습니다.

4. **우선권 확보를 위한 타임스탬프**
   - 외부와 협업하거나, 회사·연구실 간 경계가 있을 때는:
     - arXiv, OSF, DOI 발급 가능한 프리프린트로 초안을 먼저 올립니다.
   - 이후 AI 지원을 받아 세부를 채우더라도
     - 최초 기여와 시점이 명확해집니다.

### 교육 현장에서의 활용

- 연구윤리·AI 활용 강의:
  - Navier–Stokes 사례를 간단히 소개한 뒤
    - “이 상황에서 어떤 문서·타임스탬프가 있었다면 분쟁이 줄었을까”를 토론 주제로 사용합니다.
- 코딩 부트캠프·사내 교육:
  - “AI가 만든 코드·증명에 저작권·우선권을 어떻게 기록할 것인가”를  
    Git 커밋 메시지·PR 템플릿에 반영하는 실습으로 연결하면 효과적입니다.

## 5. 오늘 신호 정리: 에이전트 시대의 설계 과제

오늘 신호의 공통점은 “모델이 아니라 **시스템**을 어떻게 설계하느냐”에 모입니다.  
관리형 에이전트, Astra 스킬 카탈로그, Images 2.5는 모두  
도구 자체보다 **역할 정의 / 스킬 단위 / 가드 레일 / 로그 설계**가 성패를 가르는 구조입니다.

연구·교육 쪽에서는 Navier–Stokes 논쟁과 Tao의 경고가  
“AI와 함께 일할 때, 공개 범위·우선권·책임을 먼저 설계하라”는 대비형 메시지를 던집니다.  

실무 개발자·강사는  
- 에이전트와 이미지 워크플로를 “작게, 명시적으로, 로깅 가능하게” 설계하고  
- 연구·과제에서는 “프롬프트·초고·공개 시점”을 시스템적으로 기록하는 쪽으로  
오늘 도구 흐름을 자신의 환경에 맞게 가져가면 됩니다.
