## 1. PHP 전역 RCE 패치: 즉시 대응 체크리스트

**2026-10-21 기준**, PHP 8.x 전 버전에서 **원격 코드 실행(RCE) 2건**이 공개되어 긴급 보안 릴리스가 배포되었습니다. 해당 취약점은 이미 익스플로잇이 돌고 있어, 패치 지연은 사실상 무방비 상태와 같습니다. PHP-FPM, mod_php, php-cgi, FrankenPHP, LiteSpeed 대부분이 영향을 받습니다. [출처](https://simonwillison.net/2026/Oct/21/php-security-release) [출처](https://www.itworld.co.kr/article/4238838)

### 1) 무엇을 설치해야 하는가

다음 버전 이상으로 **무조건 상향**해야 합니다.

- **PHP 8.5.12**
- **PHP 8.4.27**
- **PHP 8.3.36**
- **PHP 8.2.35**

실무 순서는 이렇게 가져가면 안전합니다.

1. **운영체제 패키지 확인**
   - Debian/Ubuntu: `apt update && apt install php-fpm php-cli ...`
   - RHEL/Alma/Rocky: `dnf update php\*`
   - 컨테이너 기반이면, 베이스 이미지가 위 버전을 포함하는지 Dockerfile에서 확인합니다.

2. **php.net 바이너리 또는 소스 직접 설치**
   - 벤더 저장소에 패치가 아직 없으면,  
     임시로 **php.net 공식 패키지** 또는 소스 빌드를 고려합니다.
   - Remi 저장소 등 서드파티를 쓰는 경우,  
     벤더가 패치를 넣었는지 공지와 체인지를 확인합니다.

3. **버전 검증**
   - `php -v` 또는 `php-fpm -v`로 실제 런타임 버전을 확인합니다.
   - 웹서버와 CLI 버전이 **동일한지**도 같이 봅니다.

### 2) 어디부터 패치해야 하는가

RCE 특성상, **우선순위 정리가 승부처**입니다.

- 1순위: **인터넷에 직접 노출된 PHP 호스트**
  - 퍼블릭 웹서비스, API 게이트웨이 뒤 PHP, 워드프레스 등 CMS
- 2순위: **빌드/CI 서버와 베이스 이미지**
  - GitLab Runner, Jenkins, CI용 PHP 컨테이너 이미지
- 3순위: **백오피스, 사내 툴**

컨테이너를 쓰는 경우에는, **이미지 기반 재배포**가 핵심입니다.

- Dockerfile에서 PHP 버전 상향 후,  
  `docker build` → 새 태그 푸시 → `kubectl rollout restart` 등으로 롤아웃합니다.
- GitHub Actions, GitLab CI 템플릿에서  
  `php:8.x` 태그 대신 **명시 버전 태그**로 고정 후, 이번에 상향합니다.

### 3) “이미 뚫렸을 것”을 가정한 점검 루틴

PHP 재시작으로 끝내지 말고, **침해 전제 점검**을 같이 태워야 합니다.

- 웹 루트, 업로드 디렉터리에 **알 수 없는 php/ico/tmp 파일** 유무 확인
- crontab, systemd 서비스에 **낯선 스크립트 등록 여부** 확인
- WAS 뒤에 붙은 Redis, DB 계정에서  
  의심 쿼리 패턴과 신규 계정 생성 로그를 살펴봅니다.

당장 패치가 곤란하다면, PHP Foundation 가이드에 따라 **임시 완화책**을 적용합니다.

- 공격 표면이 넓은 PHP 엔드포인트를 WAF로 임시 차단 또는 IP 화이트리스트
- 파일 업로드, eval 계열을 쓰는 경로는 우선 비활성화 또는 제한
- CGI, 오래된 embed 모듈을 쓰는 경우 **서비스 일시 차단**도 검토합니다.

강의에서는 이 사례를 **“AI 발견 취약점 → Patch the Planet 5단계”**와 묶어 설명하면 좋습니다. 실무 교육에서는 실제 서비스의 패치 플랜과 침해 가정 체크리스트를 과제로 내면, DevOps와 보안 팀 간 협업 훈련에 도움이 됩니다.

## 2. Claude Duet와 Mods: 실시간 협업과 교육 설계

Anthropic은 **Claude Duet**으로 협업 모드를, Latent Space 쪽에서는 **Claude Mods**로 제어 가능한 주의를 강조했습니다. 둘 다 “에이전트 속을 드러내어 사람에게 맞추는 인터페이스”라는 공통점이 있습니다. [출처](https://claude.com/resources/articles/claude-duet) [출처](https://www.latent.space/p/claude-mods)

### 1) Claude Duet: 다인 실시간 세션 설계

**Claude Duet**은 여러 사용자가 하나의 Claude 세션에 동시에 접속해,  
실시간으로 입력과 커서를 공유하는 모드입니다.

**사용법**

1. Claude 웹 또는 앱에서 **새 Duet 세션 시작**을 선택합니다.
2. 링크 또는 이메일로 동료를 초대합니다.
3. 모두가 같은 채팅창에서 프롬프트를 입력하고,  
   코드 실행 결과와 모델 응답을 같이 봅니다.

**실전 활용 패턴**

- **페어 프로그래밍**
  - 한 명은 “프롬프트 드라이버”, 다른 한 명은 “코드 드라이버”로 역할을 나눕니다.
  - 공통 규칙을 먼저 정합니다.  
    예: 한 사람만 프롬프트 수정, 다른 사람은 IDE에서 실행과 디버그 담당.
- **라이브 강의·워크숍**
  - 강사가 Duet 세션을 열고, 수강생 2~3명을 한 방에 묶습니다.
  - 조별로 프롬프트 설계 → Claude 응답 비교 → 개선점을 토론하게 합니다.

**팁**

- 한 세션에 **역할 역할 라벨**을 붙이면 혼선이 줄어듭니다.  
  예: `[강사]`, `[실습1]`, `[실습2]`를 이름 앞에 붙이도록 안내합니다.
- 코드 예제는 **Git 리포지터리 링크**를 고정 메시지로 올려 두면,  
  프롬프트가 길어져도 맥락 유지가 수월합니다.

### 2) Claude Mods: 제어 가능한 “노출된 에이전트 속”

**Claude Mods**는 Claude 내부 “하네스(harness)”를 바깥으로 뒤집어,  
사용자에게 제어 가능한 모델 설정 패널을 제공하는 실험적 인터페이스입니다. [출처](https://www.latent.space/p/claude-mods)

**사용법**

1. Claude에서 **Mods 메뉴**로 들어가 새 Mod를 생성합니다.
2. 다음 요소를 편집합니다.
   - 프롬프트 프래그먼트(시스템 메시지 역할)
   - 사용할 도구 목록과 체이닝 방식
   - 온도, top-k 등 핵심 하이퍼파라미터
3. 특정 대화에 이 Mod를 적용해,  
   학습자나 팀원이 **노출된 슬라이더와 스위치**로 모델 동작을 조정하게 합니다.

**교육·협업 팁**

- 학습자에게는 **최소한의 노출**만 허용합니다.
  - 온도, 사용할 도구 선택, 응답 길이 정도만 제공하고,  
    프롬프트 핵심은 강사가 고정해 두면 안전합니다.
- 팀 내 디버깅에는 다음 식으로 씁니다.
  - “버그 헌팅 Mod”를 만들어,  
    로그 요약 도구와 테스트 러너만 연결합니다.
  - 개발자는 이 Mod 안에서만 코드를 검사하게 하여,  
    실서버 접근을 차단합니다.

Duet와 Mods를 같이 쓰면, “같은 화면에서 **프롬프트·파라미터·도구 체인**을 함께 조정하는 강의”가 가능합니다. 실무 팀에서는 온보딩 시, 신규 인원이 기존 Mod를 그대로 쓰게 해서 지식 전수를 빠르게 표준화할 수 있습니다.

## 3. DeepInfer와 Raon-1 mini: 저비용 고효율 추론 스택

중국 DeepSeek의 **DeepInfer**와 크래프톤의 **Raon-1 mini(약 30B MoE)**가 모두 “고효율 추론”을 전면에 내세웠습니다. 비용과 처리량을 개선하려는 팀에게 중요한 신호입니다. [출처](https://www.latent.space/p/ainews-deepseek-deepinfer-open-source) [출처](https://news.hada.io/topic?id=35752)

### 1) DeepSeek DeepInfer: 클러스터 단위 SOTA 추론

DeepInfer는 오픈소스 추론 스택으로,  
**클러스터당 1일 155조 토큰 처리** 수준의 처리량을 주장합니다.

**기본 워크플로**

1. DeepSeek 리포지터리 클론 후, 설치 스크립트로 **DeepInfer 런타임**를 배포합니다.
2. README에 따라 GPU 클러스터를 구성합니다.
   - 노드 수, GPU 종류, 네트워크 대역폭를 설정합니다.
3. 제공되는 **모델 레지스트리**에서 사용할 모델을 선택하고 로딩합니다.
4. REST 또는 gRPC 엔드포인트를 호출해,  
   배치 인퍼런스를 수행합니다.

**핵심 튜닝 포인트**

- **배치 크기(batch size)**: GPU 메모리가 허용하는 선까지 키워서  
  토큰당 비용을 낮춥니다.
- **시퀀스 패킹(sequence packing)**:
  - 길이가 비슷한 요청끼리 묶어 “빈 토큰 낭비”를 줄입니다.
- **레플리카 샤딩(replica sharding)**:
  - 긴 컨텍스트나 대형 모델은 여러 GPU에 분산해 로딩합니다.

실무 팁은 “**자신의 실제 워크로드**로 벤치마크”입니다. 공개된 수치는 극단적으로 최적화된 시나리오 기준인 경우가 많아,  
실제 트래픽 패턴, 평균 컨텍스트 길이, 지연 허용치를 반영해 재측정해야 합니다.

### 2) 크래프톤 Raon-1 mini: MoE + 선형 어텐션

**Raon-1 mini**는 약 30B 파라미터급이지만,  
**Mixture-of-Experts(MoE)**와 자체 **선형 어텐션**으로 효율을 노립니다.  
한국어·영어 대화, 추론, 에이전트 작업이 1차 목표입니다. [출처](https://news.hada.io/topic?id=35752)

**사용법**

1. 공개된 오픈웨이트를 Hugging Face나 자체 호스팅 프레임워크에 로딩합니다.
   - 정확히 어떤 프레임워크를 지원하는지는 프리뷰 공지를 확인합니다.
2. 기존 30B급 **dense 모델 자리에 drop-in** 교체를 시도합니다.
3. 에이전트 또는 도구 호출 파이프라인에서,  
   Raon-1 mini를 **“추론·결정 전담 모델”**로 배치합니다.

**튜닝·운영 팁**

- MoE 특성상, “전문가 라우팅”이 있어  
  하나의 요청마다 활성화되는 파라미터 수가 제한됩니다.
  - 토큰당 FLOP가 줄어드니,  
    GPU 메모리와 처리량 관점에서 dense 30B보다 유리할 수 있습니다.
- **선형 어텐션 모드**는 긴 컨텍스트나  
  에이전트 실행 로그를 전부 넣는 작업에 적합합니다.
  - 멀티스텝 에이전트 로그를 그대로 컨텍스트에 둔 채로  
    의사결정을 시키는 실험에 활용할 수 있습니다.

강의에서는 두 도구를 비교해,  
“CPU/GPU, 배치, MoE 구조별 토큰당 비용”을 직접 계산하는 실습으로 연결하면 좋습니다. 실무 팀은 사내용 모델 비교 벤치마크에 둘 다를 올려, **성능/비용 곡선**을 시각화한 후 채택을 결정하는 것이 안전합니다.

## 4. OpenAI × Google Cloud: 엔터프라이즈 통합 전략

**OpenAI 모델이 Google Cloud Model Garden에 공식 입점**하면서,  
엔터프라이즈 환경에서 OpenAI와 Gemini를 나란히 쓰기 쉬워졌습니다. 국내 기사에서는 **GPT-6 시리즈와 Codex 통합**도 부각되었습니다. [출처](https://openai.com/index/openai-models-google-cloud) [출처](https://news.hada.io/topic?id=35775)

### 1) Model Garden에서 OpenAI 모델 호출하기

**작업 순서**

1. Google Cloud 콘솔에서 **Marketplace**로 들어갑니다.
2. **OpenAI** 상품을 구독하고,  
   사용할 프로젝트를 선택합니다.
3. Model Garden에서 원하는 모델  
   (예: GPT 계열, 코드 특화 모델)을 선택합니다.
4. Vertex AI / Model Garden API를 통해  
   기존 Gemini 호출 코드와 거의 동일한 방식으로 요청을 보냅니다.

**실무 팁**

- **같은 입력 프롬프트**를 Gemini와 OpenAI 모델에 모두 보내  
  응답 품질과 지연을 비교합니다.
- 과금과 IAM은 **Google Cloud 프로젝트 단위**로 통합 관리되므로,  
  기존 감사지표, 비용 알림 정책을 그대로 활용할 수 있습니다.

### 2) Codex CLI·데스크톱 앱 연동

국내 기사 기준으로는, **로컬 Codex CLI/데스크톱 앱을  
Google Cloud 계정에 연동해 원격 모델을 사용**하는 흐름입니다. [출처](https://news.hada.io/topic?id=35775)

**실전 설정**

1. Codex CLI 설치 후, `codex login` 등 명령으로  
   Google Cloud 자격 증명을 연결합니다.
2. 지역(region)과 프로젝트 ID를 기본값으로 설정합니다.
3. 로컬에서 실험한 프롬프트와 코드 생성 패턴을  
   그대로 서버 측 API 호출 코드에 옮깁니다.

**팁**

- 강사 입장에서는, 학생들 로컬에서  
  Codex 앱으로 실험하게 한 뒤,  
  같은 프롬프트를 Cloud API 예제로 옮겨보게 하면 학습 전이가 빠릅니다.
- 실무에서는 “**로컬 실험 → 노트북 스니펫 → 서비스 코드**”의  
  계단형 템플릿을 만들어 두면, 프롬프트와 파라미터가 흐트러지지 않습니다.

### 3) 정책·거버넌스: Broad Access와 기업 활용

OpenAI는 **“Broad access through consistent standards”** 문서로,  
파트너가 따라야 할 안전 가이드를 구체화했습니다. [출처](https://openai.com/index/broad-access-through-consistent-standards)

핵심 요구사항은 다음과 같습니다.

- OpenAI가 제공하는 **콘텐츠 필터**를 파트너 앱에도 동일하게 적용
- **오남용 신고 채널**을 앱에서 직접 제공하고,  
  이를 OpenAI 측 인입 엔드포인트와 연결
- 모델 출력이 보이는 화면에 **정책 고지**를 노출

실무에서는 “요구사항 → 기술 통제”를 이렇게 매핑하는 것이 좋습니다.

- 필터: **Classifier 호출 래퍼 서비스**를 만들어,  
  모든 응답이 이 래퍼를 거치도록 강제
- 신고: 앱 내 신고 버튼 → 내부 티켓 시스템 →  
  필요 시 OpenAI 신고 API로 연동
- 감사: 누가 언제 어떤 프롬프트/응답을 봤는지,  
  로그 스키마를 미리 설계

AT&T의 **LegalEdge** 사례처럼,  
법무팀에 ChatGPT 기반 비서를 붙일 때는  
**출처 링크와 human-in-the-loop**를 기본값으로 넣어야 합니다. [출처](https://openai.com/index/att-legal)

## 5. LLM이 복제하는 소프트웨어: 과장과 실속 사이

한쪽에서는 AI가 PHP 취약점을 찾아내고,  
다른 한쪽에서는 사용자가 **어도비 포토샵 상당 부분을 러스트로 재현**했다고 주장하는 사례까지 등장했습니다. LLM이 상용 소프트웨어 기능을 복제하는 속도가 빨라지는 흐름입니다. [출처](https://www.itworld.co.kr/article/4235573)

### 1) “기능 복제” 워크플로의 실제 모습

기사 사례에서 사용자는 다음과 같은 흐름을 썼습니다.

1. 제품 설명서와 요구사항을  
   프론티어 또는 오픈 모델(예: Claude Opus, Qwen 계열)에 입력합니다.
2. 모델에게 **컴포넌트 단위 설계와 코드 생성을 병행**하게 합니다.
3. Git 리포지터리에 생성 코드를 올리고,  
   커뮤니티에서 풀 리퀘스트와 버그 리포트로 빠르게 개선합니다.

비슷한 워크플로는 상용 SaaS나 개발툴 “클론”을 만들 때에도  
바로 재현이 가능합니다.

### 2) 실무자가 챙겨야 할 현실적인 한계와 팁

관건은 “**초속도 복제** vs **품질·보안 리스크**”의 대비입니다.

- LLM이 생성한 초기 코드는  
  동작은 비슷해 보여도, 구조와 보안이 허술한 경우가 많습니다.
- 외부 라이브러리와 공개 API 의존성이  
  그대로 섞여 들어오면서 **공급망 공격 표면**이 넓어집니다.

실전 팁은 다음과 같습니다.

1. **코드 신뢰 금지, PR 중심 검증**
   - 생성 코드는 무조건 별 브랜치로 올리고,  
     리뷰와 테스트를 통과한 변경만 메인에 병합합니다.
2. **보안 리뷰를 워크플로에 강제 포함**
   - SAST, SBOM 생성, 의존성 취약점 스캐너를  
     CI 단계에 기본으로 붙입니다.
3. **스펙 우선, 구현 후행**
   - Tenex의 AI-native SDLC처럼,  
     먼저 “측정 가능한 결과와 테스트”부터 정의합니다. [출처](https://www.latent.space/p/tenex)
   - 스펙 → 코드 → 테스트 → 배포를  
     에이전트 오케스트레이션으로 자동화하되,  
     검증 게이트만큼은 사람이 설계합니다.

Panache가 Battle Drones를 **자산만 교체한 포크**로 낸 것처럼,  
게임이나 툴을 복제할 때는 엔진과 자산을 분리해 포크하는 것이 좋습니다. [출처](https://simonwillison.net/2026/Oct/21/panache)

- 코드는 원 프로젝트와 동기화하기 쉽게 유지하고,  
  아트와 음원 등 자산만 별 커밋으로 교체하면,
  - 라이선스 준수, 버그 픽스 상류 반영,  
    장기 유지보수가 모두 수월합니다.

오늘 흐름을 요약하면, **AI가 취약점을 찾고 기능을 복제하는 시대**에는 “패치를 미루지 않는 운영”과 “검증을 전제로 한 복제”가 핵심입니다. 에이전트와 고효율 추론 스택, 클라우드 통합은 모두 이 전제를 만족할 때에만, 강의와 실무에서 진짜 생산성 향상으로 이어집니다.
