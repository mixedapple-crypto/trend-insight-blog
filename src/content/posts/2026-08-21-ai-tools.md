## 1. ChatGPT 검색: site: 연산자 내부 적용 급증과 개발자 영향

**Promptwatch** 추적 데이터에 따르면, GPT-5.6이 공개된 8월 초 이후 ChatGPT 검색의 "팬아웃 쿼리(fanout query)" 중 16~17%가 도메인 특정 검색을 사용합니다.

이전 수치는 0.3~0.5%였습니다. 한 달 만에 40배 이상 늘었습니다.

내부 구현은 `site:` 연산자를 사용자에게 직접 노출하지 않습니다. 대신 `search(query, recency, domains)` 형태의 함수를 통해 OpenAI가 도메인을 직접 제어합니다.

이 변화의 실질적 목적은 Reddit 의존도 축소입니다. 특정 커뮤니티 글이 과도하게 인용되는 문제를 OpenAI가 내부에서 직접 억제하기 시작한 것입니다.

**개발자 실전 팁 세 가지:**

- ChatGPT 검색을 RAG 파이프라인이나 리서치 자동화에 활용 중이라면, 답변 소스 분포가 달라질 수 있으므로 출처 검증 단계를 별도로 두십시오.
- 특정 도메인 결과를 기대하는 프롬프트는 명시적으로 출처 유형을 요청하는 방향으로 조정하십시오.
- 강의에서 "ChatGPT는 왜 이 사이트를 더 자주 인용하나"를 설명할 때, 이 내부 함수 구조가 좋은 실증 사례가 됩니다. [출처](https://simonwillison.net/2026/Aug/20/chatgpt-search-now-uses-the-siteoperator-at-scale)

## 2. /wayfinder 스킬: 그린필드 프로젝트 방향 설정을 구조화하는 법

Matt Pocock이 공개한 `/wayfinder` 스킬은 AI에게 코드 작성 전에 아키텍처 결정·의존성·단계별 로드맵을 먼저 정리하도록 유도합니다.

사용 방법은 간단합니다. 프로젝트 시작 시점 또는 다음 단계가 불명확할 때, 클로드(Claude)나 **Cursor** 같은 에이전트 환경에서 `/wayfinder`를 호출하고 현재 컨텍스트를 전달합니다.

에이전트는 즉시 구현으로 뛰어들지 않고, 숨겨진 전제(hidden assumption)와 의존 관계를 먼저 표면화합니다. 이 과정이 이후 비용이 큰 재작업을 줄이는 핵심 단계입니다.

**실전 워크플로:**
1. 프로젝트 목표와 기술 스택을 한 문단으로 요약해 전달합니다.
2. `/wayfinder` 스킬이 생성한 로드맵을 팀 전체가 검토합니다.
3. 합의된 아키텍처 결정을 `CLAUDE.md` 또는 프로젝트 규칙 파일에 기록합니다.
4. 이후 코드 생성 단계에서 이 파일을 컨텍스트로 주입합니다.

강의 실습에서는 "AI에게 바로 코드 짜달라고 하기 전에 설계를 먼저 협의하는 패턴"을 보여주는 데 이 스킬이 유용합니다. [출처](https://www.latent.space/p/wayfinder-skill)

## 3. Bun 1.4 WebView: 외부 의존 없는 서버사이드 브라우저 자동화

**Bun 1.4**가 `Bun.WebView`를 도입했습니다. macOS WebKit 또는 Chrome DevTools Protocol을 사용하는 네이티브 헤드리스 브라우저 자동화 기능입니다.

Simon Willison은 이를 활용해 URL과 JS 코드를 받아 렌더링 결과를 JSON으로 반환하는 API를 프로토타입으로 구현했습니다. Puppeteer나 Playwright 같은 별도 프로세스 없이 작동합니다.

실행 메모리는 192~256MB 컨테이너 수준입니다. 프로덕션 서비스에 올려도 부담이 적습니다.

**실전 적용 시나리오:**

- 자바스크립트 렌더링이 필요한 페이지 스크래핑을 마이크로서비스 하나로 처리할 때
- AI 에이전트가 웹 페이지를 실시간으로 읽어야 하는 파이프라인에서 브라우저 자동화 레이어를 가볍게 구성할 때
- 기존 `shot-scraper` 워크플로를 Bun 기반으로 마이그레이션할 때

```ts
// 기본 사용 예시 (Bun 1.4)
const view = new Bun.WebView({ headless: true });
await view.load("https://example.com");
const result = await view.evaluate(() => document.title);
```

강의에서는 "AI 에이전트가 웹을 직접 읽는 아키텍처"를 설명할 때 이 구현이 구체적인 참조 사례가 됩니다. [출처](https://simonwillison.net/2026/Aug/20/bun-webview-json-api)

## 4. AI 추론 아키텍처: 파일럿 단계에서 결정해야 하는 이유

AI 추론(Inference) 아키텍처 선택을 프로덕션 직전으로 미루면 재작업과 프로세스 재시작이 발생합니다. ITWorld가 정리한 5가지 원칙의 핵심은 "파일럿 단계에서 결정하라"입니다.

훈련 아키텍처와 추론 아키텍처는 요구사항이 다릅니다. 훈련은 처리량과 유연성이 우선이고, 추론은 낮은 지연·높은 안정성·자율 운영이 기준입니다.

레거시 시스템은 사람이 개입해 장애를 가려왔습니다. AI 추론 환경에서는 이 완충재가 없습니다. 통합·오케스트레이션(Orchestration) 레이어를 이벤트 기반 저지연 구조로 현대화한 뒤 AI를 올려야 합니다.

**체크리스트 (파일럿 단계용):**
- 지연 요구사항을 SLA로 명시했는가?
- 데이터 주권 제약에 따라 클라우드·온프레미스·엣지 라우팅 정책을 정의했는가?
- 기존 QA·모니터링 파이프라인이 AI 추론 출력을 커버하는가?

개발팀이 AI 도입 검토를 할 때 이 원칙들이 초기 아키텍처 결정의 구체적 근거가 됩니다. [출처](https://www.itworld.co.kr/article/4211748/ai-%ec%b6%94%eb%a1%a0-%ec%95%84%ed%82%a4%ed%85%8d%ec%b2%98-%ed%8c%8c%ec%9d%bc%eb%9f%bf-%eb.html)

## 5. AI 답변 붙여넣기 vs 편집 후 공유: 실무 기준선 다시 긋기

오늘 두 가지 대비되는 시각이 나란히 등장했습니다. 하나는 "AI 답변을 그대로 붙여넣지 마라"는 실무 원칙이고, 다른 하나는 "실수하는 AI 개발자라도 채용해야 한다"는 팀 운영 논리입니다.

두 주장을 겹쳐보면 공통 전제가 보입니다. AI 출력은 버전 관리·코드 리뷰·QA처럼 기존 오류 포착 인프라 안에서 다루어야 한다는 것입니다.

**실무 기준선:**
- AI 초안을 공유하기 전, 자신의 맥락과 판단을 반영해 편집합니다. 수신자가 동일한 도구로 동일한 출력을 얻을 수 있다면, 편집 없는 공유는 부가가치가 없습니다.
- AI 코딩 에이전트를 팀에 도입할 때는 "완벽한 코드를 기대"하기보다, 풀 리퀘스트·QA 게이트 안에서 다른 기여자와 동일하게 검토합니다.

오늘 신호들이 한 방향을 가리킵니다. 도구가 빨라지고 내부 동작이 정교해질수록, 사람의 판단과 편집 역할이 도구 선택보다 더 구분선이 됩니다. [출처1](https://news.hada.io/topic?id=32699) [출처2](https://www.itworld.co.kr/article/4211725)
