## 1. LLM 0.32.1 + llm-openrouter 0.7: 설치 오류 수정 & 서버 측 도구 추가

**LLM 0.32.1**은 신규 설치가 깨지던 문제를 수정한 긴급 패치입니다.

원인은 OpenAI Python 라이브러리가 httpx를 제거하면서, LLM이 의존하던 전이 의존성(transitive dependency) 체인이 끊긴 것입니다. 임시 조치로 `openai<3`을 고정하였으며, 0.33에서 httpx2로 마이그레이션 예정입니다.

설치 오류가 발생한다면 아래 중 하나를 적용합니다.

```bash
pip install llm==0.32.1        # 최신 패치로 올리기
pip install openai==2.*        # openai를 2.x대로 내리기
```

같은 날 공개된 **llm-openrouter 0.7**은 LLM 0.32 + OpenRouter의 응답(Responses) API를 통합하였습니다.

추가된 서버 측 도구 세 가지—Shell, WebFetch, **WebSearch**—는 클라이언트 왕복 없이 모델이 직접 실행합니다. 사용법은 단순합니다.

```bash
llm -m openrouter/claude-opus-4-5 -T WebSearch "최신 Python 보안 패치 요약"
```

`-T` 플래그로 도구를 선택하면, 추론 모델이 검색 결과를 받아 응답까지 한 번에 처리합니다.

강의에서 OpenRouter 연동 예제를 보여줄 때, 이 버전부터 "서버 측 도구"와 "클라이언트 도구"의 차이를 설명하는 실습 소재로 쓸 수 있습니다. [출처](https://simonwillison.net/2026/Aug/21/llm-openrouter)

## 2. Claude Computer Use + Skills/Files API: 프로덕션 에이전트 전환 패턴

Anthropic이 컴퓨터 사용(Computer Use), 스킬스(Skills) API, 파일스(Files) API를 결합한 프로덕션 에이전트 구성 방식을 공개하였습니다.

핵심 구조는 세 단계입니다.

1. **Computer Use**로 화면 읽기·입력 자동화 실행
2. Skills API로 조직 고유 지식(내부 문서·절차)을 에이전트에 주입
3. Files API로 완성된 파일을 단일 워크플로에서 반환

새로 추가된 브라우저 사용 도구(Browser Use Tool)는 DOM 셀렉터 대신 페이지 구조를 의미 단위로 읽어 특정 필드와 버튼을 식별합니다.

취약한 CSS 셀렉터 기반 자동화가 사이트 변경마다 깨지던 문제를 구조적으로 줄입니다.

실전 팁은 이렇습니다. 데이터 입력·양식 처리·문서 생성처럼 "파일 인·아웃이 있는 반복 업무"를 먼저 선정하고, Skills API에 검증된 절차를 문서화한 다음 Computer Use로 UI 동작을 연결합니다.

개발 강의라면 "에이전트 오케스트레이션의 세 레이어"를 이 사례로 설명할 수 있습니다. [출처](https://news.hada.io/topic?id=32754)

## 3. 코딩 에이전트로 TUI 대신 네이티브 앱 만들기: 개발 습관 전환

Simon Willison이 "개인 도구에 TUI를 더 이상 만들지 말라"는 논거를 정리하였습니다.

핵심 주장은 단순합니다. 코딩 에이전트가 네이티브 앱 스캐폴딩에 드는 시간을 이미 TUI 제작 수준까지 낮추었으므로, 일회용 스크립트도 네이티브 UI로 만드는 것이 합리적이라는 것입니다.

실제로 그는 Claude Code로 제작한 macOS 상태 표시줄 앱을 수개월째 매일 사용 중이라고 밝혔습니다.

실전 전환 방법은 다음 순서를 따릅니다.

- 기존 CLI 스크립트의 입력·출력 인터페이스를 먼저 정리
- 에이전트에게 "이 스크립트를 macOS 상태 표시줄 앱(또는 웹 앱)으로 감싸라"고 지시
- 에이전트가 생성한 코드를 검토하고 주요 동작만 확인

강의 실습에서 "동일 기능을 CLI → 네이티브 앱으로 에이전트가 변환하는 과정"을 보여주면, 에이전트 코딩의 체감 범위를 직관적으로 전달할 수 있습니다. [출처](https://simonwillison.net/2026/Aug/21/stop-making-tuis)

## 4. 데모 에이전트 → 배포 에이전트: 5개 장벽과 실전 대응

엔터프라이즈 환경에서 에이전트가 막히는 지점은 모델 능력이 아니라 인프라입니다.

가장 앞선 장벽은 **인증(Authentication)**입니다. 공유 API 키로 동작하던 데모 에이전트는 프로덕션에서 사용자별 역할 기반 접근 제어(RBAC)를 요구합니다.

모델 컨텍스트 프로토콜(MCP, Model Context Protocol)은 에이전트 능력과 사용자 신원을 분리한 뒤, 신뢰 인프라가 요청 헤더에 사용자 자격을 주입하고 하위 서버가 재검증합니다.

두 번째 장벽은 데이터 규모입니다. 수천 개 테이블이 있는 기업 데이터 웨어하우스는 컨텍스트 창을 초과합니다. 스키마 전체를 프롬프트에 주입하는 대신, 의미 기반 인덱싱과 점진적 필터링으로 관련 스키마만 선별해야 합니다.

이 두 문제 외에도 에이전트 상태 전달, 승인 게이트, 감사 추적이 추가 장벽으로 꼽힙니다.

실전 체크리스트로는 이렇게 정리됩니다.

- 배포 전: 사용자 신원 전파 경로 설계 → MCP로 자격 분리
- 데이터 접근: 전체 스키마 대신 시맨틱 인덱스 + 필터 레이어
- 승인 게이트: 사람이 검토할 지점을 워크플로 초기에 명시

## 5. Huzzah·Proliferate·ChatGPT 튜터링: 주변 신호 정리

오늘 주변 신호에는 구조적 대비가 뚜렷한 세 가지가 있습니다.

**Huzzah**는 채팅 프롬프트 대신 의도 기반 의사코드(pseudocode)를 지속적으로 저장해 코드를 재생성합니다. 대화가 끊길 때마다 맥락을 다시 설명해야 하는 문제를 실행 가능한 사양서 형태로 해결하는 접근입니다. [출처](https://news.hada.io/topic?id=32735)

**Proliferate**는 Claude Code·Codex·Cursor·Grok 등 여러 코딩 에이전트를 단일 인터페이스에서 연결하는 오픈소스 자체 호스팅 IDE입니다. 에이전트 간 위임·조율, 재사용 가능한 워크플로 체인, 사람 승인 게이트를 지원합니다. 특정 에이전트에 종속되지 않으면서 각각의 강점을 병행 활용하려는 팀에 적합합니다. [출처](https://github.com/proliferate-ai/proliferate)

Matt Webb의 ChatGPT 활용 사례는 반대 방향의 신호입니다. 코드 생성 대신 "퀘터니언(quaternion) 수학 개념을 단계별로 설명해 달라"는 방식으로 학습 파트너로 활용하였습니다. 특정 도메인(그래픽스·물리·암호화)에 처음 진입할 때, 코드를 복사하기 전에 개념부터 질문하는 습관은 나중에 유지·확장을 훨씬 쉽게 만든다는 것이 핵심입니다. [출처](https://simonwillison.net/2026/Aug/21/matt-webb)

오늘 신호 전체를 관통하는 흐름은 하나입니다. 에이전트 도구는 빠르게 늘고 있지만, 실제로 쓸 수 있는 상태로 만드는 작업—인증·데이터 필터링·맥락 지속성·승인 구조—은 여전히 사람이 설계해야 합니다.
