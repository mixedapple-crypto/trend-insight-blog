## 1. Datasette 플러그인: 백그라운드 작업과 보안 패치

**Datasette 1.0a40(2026-09-16)**에서는 플러그인에서 **백그라운드 작업**을 직접 등록할 수 있고, 내부 HTTP 클라이언트가 **httpx2**로 교체되었습니다. 동시에 **0.65.5**는 테이블 이름 끝 공백과 개행으로 권한 우회를 할 수 있던 취약점(GHSA-h547-rmjf-5m2m)을 수정했습니다. 장기 실행 작업과 보안이라는, 실무에서 바로 부딪히는 두 축이 동시에 나온 셈입니다.

**새 백그라운드 작업 API 사용법입니다.**

```python
# plugin.py
from datasette import hookimpl

async def long_running_job(ds, table_name):
    # I/O가 많은 작업 예시
    db = ds.get_database()
    await db.execute_write("VACUUM")  # 또는 외부 API 호출
    await ds.add_message(f"{table_name} 최적화 완료", type="notice")

@hookimpl
def register_routes(datasette):
    async def trigger_job(scope, receive, send):
        # 요청 처리와 분리하고 싶은 작업을 등록
        datasette.add_background_task(long_running_job, datasette, "my_table")
        # 즉시 응답
        await datasette._send_html(send, "<p>작업을 시작했습니다.</p>")
    return [
        (r"^/optimize$", trigger_job),
    ]
```

핵심은 **`add_background_task`에 “코루틴 함수 + 인자”를 넘기고, HTTP 응답은 바로 돌려보내는 것**입니다. 이렇게 하면 플러그인에서 리포트 생성, 외부 API 수집, 대용량 인덱싱 같은 작업을 UI를 막지 않고 돌릴 수 있습니다.

내부 요청에는 새 HTTP 클라이언트가 쓰입니다.

```python
async def example_internal_call(datasette):
    # 내부적으로는 httpx2 기반
    response = await datasette.client.get("/-/metadata.json")
    data = response.json()
    return data
```

테스트 코드에서도 `datasette.client`를 그대로 쓰면, 최신 async HTTP 동작과 맞춰진 환경에서 시나리오 테스트를 할 수 있습니다.

**보안 패치 적용은 단순합니다.**

```bash
pip install -U datasette==0.65.5
# 또는 requirements.txt / 이미지 버전 갱신
```

다만 패치만 믿지 말고, 앱 코드에서도 **사용자 입력 테이블 이름을 정규화**해야 합니다.

```python
import re

ALLOWED_TABLE = re.compile(r"^[a-zA-Z0-9_]+$")

def sanitize_table(name: str) -> str:
    name = name.strip()  # 공백, 개행 제거
    if not ALLOWED_TABLE.match(name):
        raise ValueError("허용되지 않는 테이블 이름입니다.")
    return name
```

테이블 이름, 뷰 이름, 플러그인 이름처럼 “식별자”는 모두 **검증 후 권한 체크**를 거치게 하는 것이 좋습니다. 강의나 사내 교육에서는 이 패치를 **“AI·웹 도구에서 식별자 역시 사용자 입력으로 간주해야 한다”**는 예제로 쓰기 좋습니다. 에이전트를 얹은 Datasette 플러그인이라면, 장기 작업은 모두 `add_background_task`로 넘기는 패턴을 표준으로 잡으면 온보딩이 한층 수월해집니다.

## 2. Claude 통합: 하나의 작업 공간과 세션 브로커

Anthropic은 **Claude Cowork와 Claude Chat을 하나의 “Claude”로 통합**했습니다. 웹, 데스크톱, 모바일 앱의 Pro와 Max 요금제에서 순차 적용 중이며, 한국 커뮤니티에도 이미 안내가 올라왔습니다. 이제 별도의 Cowork 공간으로 이동하지 않고, **하나의 대화창에서 문서, 슬라이드, 디자인과 코드 작업**을 모두 이어갈 수 있습니다.

실무에서 바로 쓸 수 있는 워크플로는 다음과 같습니다.

1. **하나의 대화에서 프로젝트를 시작**합니다.  
   - 요구사항 정리 → Claude Docs로 사양 작성  
   - Claude Slides로 초안 슬라이드 생성  
   - Claude Design으로 간단 와이어프레임 생성  

2. 같은 대화에 **GitHub, Notion, Google Drive 같은 커넥터**를 연결합니다.  
   - “이 레포의 `api` 디렉터리 구조를 요약해 주세요.”  
   - “위 요구사항 문서를 기준으로 테스트 케이스 목록을 만들어 주세요.”

3. 강의에서는 **세션 하나를 “수업 스레드”로 유지**하면서,  
   - 수업 자료, 예제 코드, 과제 설명을 모두 같은 스레드에 붙여 두고  
   - 학생 질문마다 “이전에 만든 요구사항 문서를 참고해서 답변해 주세요.”처럼 맥락을 재사용합니다.

여기에 **Claude Code Channels를 활용한 “세션 간 Q&A 브로커”** 패턴이 결합되면, 조직 내에 “레포 담당 Claude”를 둘 수 있습니다. 개략 구조는 다음과 같습니다.

- 각 Claude Code 세션마다 **Channel 엔드포인트**를 만듭니다.  
- “질문 세션”이 **“답변 세션”의 Channel로 메시지 POST** → 답변 세션이 처리 후 자기 Channel에 응답 POST → 브로커가 이를 받아 질문 세션에 전달합니다.  
- 간단한 **`request_id`를 헤더나 메시지 바디에 넣어 상관관계**를 유지합니다.

실전 팁은 세 가지입니다.

1. **브로커 레이어를 따로 둡니다.**  
   - 사내 작은 서비스로 Channels를 감싸고,  
   - ACL, 레이트 리밋, 팀별 네임스페이스를 이 레이어에서 처리합니다.  
   이렇게 하면 서로 다른 팀 레포의 맥락이 섞이지 않습니다.

2. **각 Claude 세션을 “도메인별 에이전트”로 고정**합니다.  
   - 예: `infra-claude`, `ml-claude`, `frontend-claude`  
   - 세션 첫 메시지에 역할, 접근 가능한 레포, 허용/금지 작업을 명시합니다.  
   문의는 항상 브로커를 통해 “알맞은 세션”으로 라우팅합니다.

3. 강의에서는 **“질문 라우팅” 과제를 설계**하기 좋습니다.  
   - 학생들에게 간단한 Channels 브로커를 짜게 하고,  
   - 서로 다른 Claude 세션에 질문을 라우팅해 보게 하면  
   멀티 에이전트 구조와 메시지 상관관계의 핵심 개념을 자연스럽게 익힐 수 있습니다.

이렇게 하나의 Claude 인터페이스를 “여러 전문 세션으로 나뉜 에이전트 네트워크의 프론트”로 쓰면, 사용자 입장에서는 단일 창을 유지하면서도 에이전트 아키텍처를 운영 측면에서 관리할 수 있습니다.

## 3. Jev와 Gemini: LLM 앞단의 초경량 판단 모델과 이상 탐지

**Jev(TypeSafe)**는 텍스트 생성 없이 **결정, 분류, 라우팅, 스코어링만 수행하는 “System One Model”**입니다. 소개에 따르면 작은 프런티어 LLM 대비 **100배 이상 빠르고, 200배 이상 저렴한** 것을 목표로 합니다. 동시에 구글의 **Gemini Enterprise Agent Platform**에는 **Agent Anomaly Detection**이 프라이빗 프리뷰로 추가되어, 에이전트의 행동을 LLM 바깥에서 감시합니다.

Jev는 구조적으로 **LLM 앞단 또는 사이드카**로 붙이는 것이 좋습니다.

- 입력을 **구조화된 피처나 임베딩** 형태로 보내고,  
- “이 요청을 어떤 도구로 라우팅할지”, “승인/거절”, “카테고리 레이블” 같은 **작은 의사결정만 수행**하게 둡니다.  
- 기존에 작은 LLM으로 구현하던  
  - 콘텐츠 필터링  
  - 인텐트 분류  
  - 여러 에이전트 중 라우팅 선택  
  같은 부분을 Jev로 교체하면, 특히 **대량 실시간 트래픽**에서 비용과 지연을 줄이기 좋습니다.

적용 패턴 예시는 다음과 같습니다.

1. **엔드포인트 앞의 프록시 계층에 Jev를 배치**합니다.  
   - 요청 메타데이터, 사용자 속성, 간단한 텍스트 요약을 피처로 만들어 Jev에 보냅니다.  
   - Jev가 `ROUTE=KNOWLEDGE_BASE`처럼 결정값을 주면,  
     - LLM 호출,  
     - 캐시된 FAQ 응답,  
     - 사람 상담사 등으로 라우팅합니다.

2. **배치 처리에 적극 활용**합니다.  
   - 콜센터 요약 분류, 대량 스팸 판별, 피드 랭킹 선별 단계 등에서  
   - Jev 요청을 **묶음(batch)**으로 보내 처리량을 극대화합니다.

여기서 구글의 **Agent Anomaly Detection**이 “감시 레이어” 역할을 합니다.

- 에이전트 실행에서 발생하는 **OpenTelemetry 트레이스와 툴 호출 로그**를 수집하고,  
- 별도의 파이프라인에서 **논리적 이상, OWASP Agentic Top 10 위반 가능성**을 분석합니다.  
- 중요한 점은 **메인 요청 경로에 지연을 추가하지 않는 아웃오브밴드 방식**이라는 점입니다.

실전에서 활용하는 기본 순서는 다음과 같습니다.

1. Gemini Enterprise Agent Platform에서 **Agent Anomaly Detection을 활성화**합니다.  
2. 에이전트가 이미 **OpenTelemetry로 추적 정보를 내보내도록 계측**합니다.  
3. 탐지 결과를  
   - Google Security Command Center, 또는  
   - 제공되는 API로 수신합니다.  
4. 이 결과를 기준으로  
   - 특정 사용자, 세션, 도구 조합의 **향후 호출을 차단**하거나,  
   - 사람이 검토해야 하는 케이스를 큐에 올립니다.

팁은 **“알림-only”에 머물지 말고, 최소 한 가지는 자동 집행 로직을 추가하는 것**입니다.

- 예: “재무 시스템에 대해 비정상적으로 많은 `DELETE` 시도가 감지되면, 해당 에이전트의 이 도구 사용을 10분간 차단한다.”  
- 예: “OWASP Agentic Top 10 룰 중 2개 이상을 동시에 건드리면, 해당 세션을 즉시 사람 검토 큐로 올린다.”

강의나 내부 교육에서는 Jev를 **“System 1 필터·라우터”**, Gemini 이상 탐지를 **“System 2 안전 감시자”**로 소개하면 개념 구분이 명확해집니다. 모델 크기나 파라미터보다, **어디에 어떤 모델을 꽂고 어떤 로그로 관리하느냐**가 설계 포인트가 됩니다.

## 4. AI 코드·에이전트 거버넌스: “빠른 자동화”와 품질 관리의 긴장

오늘 흐름의 마지막 축은, **속도**와 **거버넌스**의 대비입니다. GitHub Copilot, OpenAI, Microsoft, 그리고 국내 기사까지 모두 같은 방향을 가리킵니다. “AI가 도와주는 속도”는 이미 기정사실이고, 이제는 **코드 품질과 책임, 모델 복지 논쟁을 어떻게 다룰 것인가**가 남았습니다.

### Copilot로 Copilot 런타임를 Rust로 옮긴 사례

GitHub는 Copilot 에이전트 런타임 약 **80만 줄을 Rust로 마이그레이션**하면서, Copilot 자체를 활용했습니다. 중요한 점은 “한 번에 번역”이 아니라 **작은 단위의 반복 루프**에 초점을 뒀다는 점입니다.

실무 복제 패턴은 다음과 같습니다.

1. **작은 모듈 단위로 리팩터링 범위를 고정**합니다.  
2. Copilot에게 “이 Go/TypeScript 모듈을 Rust/Java로 옮기되, 아래 테스트를 통과해야 한다”고 프롬프트합니다.  
3. 생성된 코드를 바로 **컴파일하고 해당 모듈의 테스트만 실행**합니다.  
4. 실패 로그를 다시 Copilot에 넣어 수정안을 받습니다.

강의에서는 이를 “AI 리라이트 스프린트”로 구성해,  
- 학생들이 작은 레거시 모듈을 새 언어로 옮기게 하고,  
- 테스트 기반 개발과 AI 도구 협업의 중요성을 동시에 체험하게 할 수 있습니다.

### AI 생성 코드 품질 관리: “빠를수록 쌓이는 기술 부채”

국내 기사에서는 **엔터프라이즈 DevOps에서 AI 코드 생성기를 쓸 때의 역설**을 짚습니다. 속도는 빨라지는데, **아키텍처 원칙, 보안 규칙, 라이브러리 정책, 테스트 기준**이 프롬프트에만 느슨하게 담기면 기술 부채가 폭발합니다.

권장 패턴은 명확합니다.

1. **엔지니어링 표준을 기계가 읽을 수 있는 형태로 고정**합니다.  
   - 아키텍처 가이드 → ADR 문서 + 리포 내 `architecture.md`  
   - 승인 라이브러리 목록 → 코드 모드용 정책 파일  
   - 보안 규칙 → SAST 룰, 시크릿 스캔  
   - 네이밍, 포맷팅 → 린터, 포매터 설정  
   - 논기능 요구사항(NFR) → 로드 테스트, 헬스 체크, 알람 룰

2. AI 코드 생성 프롬프트에는 항상  
   - “이 리포의 `guidelines/*.md`와 `.eslintrc`, `security-policy.yaml`을 준수해 주세요.”  
   를 포함합니다. 가능하면 **에디터 확장이나 사내 프록시**가 이를 자동으로 덧붙이게 합니다.

3. 생성된 코드는 **기존 CI/CD 게이트를 100% 통과해야만 머지**합니다.  
   - 린터, 포매터, 유닛·통합 테스트, 보안 스캔, 라이선스 체크까지 동일하게 적용합니다.  
   - “사람이 썼으니 믿을 수 있다”는 예외를 AI 코드에 두지 않습니다.

핵심 팁은 한 줄입니다. **“AI가 쓴 코드는, 사람이 쓴 코드보다 더 불신하라.”**  
도구는 속도를 주지만, **표준과 검증 로직을 코드로 고정하지 않으면** 그 속도가 그대로 기술 부채의 속도가 됩니다.

### 모델 안전·책임: 오픈AI 사례와 “모델 복지” 논쟁

OpenAI는 **모델 미스얼라인먼트 보고 프레임워크**와, **6건의 우려 사례**를 공개했습니다. 동시에 뉴욕타임즈 보도에서는 실제 서비스에서 **환각과 정책 실패가 반복된다**는 점을 다시 상기시켰습니다. 여기에 Microsoft AI CEO **무스타파 술레이만**은 “모델 복지” 논의를 경계하면서, **모델에 자아와 권리를 학습시키는 프롬프트·훈련이 통제를 흐릴 수 있다**고 지적했습니다.

실무자에게 바로 적용할 포인트는 세 가지입니다.

1. **모델 출력은 기본적으로 “불신” 상태에서 출발**합니다.  
   - 코드: 유닛 테스트, 타입 체크, 린터, SAST를 통과해야 배포  
   - 사실 주장: 외부 API, 데이터베이스, 신뢰 가능한 문서로 검증  
   - 안전성: 금지된 주제, PII 노출 여부를 별도 필터와 룰로 확인  

2. **사고 보고 템플릿을 도입**합니다.  
   - 재현 가능한 프롬프트와 출력, 영향을 받은 사용자 범위, 심각도, 근본 원인, 완화 조치를 한 번에 수집하는 템플릿을 사내 표준으로 둡니다.  
   - 이는 OpenAI의 프레임워크를 축소 복제하는 방식으로 설계할 수 있습니다.

3. **프롬프트와 교육에서 의도적인 비-의인화 전략**을 씁니다.  
   - “너는 권리가 있다, 감정이 있다”는 역할극을 반복적으로 학습시키지 않습니다.  
   - 가이드라인과 헌법은 “어떤 행동을 하면 안 된다 / 해야 한다” 수준에 두고,  
     - “너의 감정이 상한다” 같은 표현은 피합니다.  
   - 강의와 문서에서는 “모델 행동”과 “내적 경험”을 명확히 구분해 설명합니다.

오늘 신호들을 한 줄로 묶으면, **에이전트와 코드 생성의 “속도 경쟁”이 이미 끝난 자리에서, 남은 승부는 거버넌스와 책임 설계**입니다. Datasette의 백그라운드 작업, Claude 통합, Jev와 Gemini의 감시 레이어, Copilot와 OpenAI의 사례 모두, “에이전트는 더 많이 움직이게 두되, **행동과 결과는 사람의 규칙과 로그 안에 가둔다**”는 같은 방향을 가리키고 있습니다.
