## 1. eMudhra CA 유출 대응: 파이썬과 서버 즉시 패치

2026-10-20 기준, **eMudhra 중간 CA 8개 인증서의 개인키가 유출**되었습니다. 이 중간 CA들이 **Mozilla, Microsoft, Apple, Chrome 신뢰 루트**에 연결되어 있어, 업데이트하지 않은 환경은 공격자가 만든 인증서를 정상으로 믿을 수 있습니다. 개발·강의 환경 모두 **신뢰 저장소(trust store) 업데이트**를 바로 진행해야 합니다. [출처](https://simonwillison.net/2026/Oct/20/emudhra-certificates)

실무용 체크리스트는 다음과 같습니다.  
1) **운영체제 CA 번들 업데이트**  
- Ubuntu/Debian:  
  ```bash
  sudo apt update
  sudo apt install --only-upgrade ca-certificates
  ```  
- RHEL/CentOS/Amazon Linux:  
  ```bash
  sudo yum update ca-certificates
  ```  
- macOS 개발용: Homebrew 사용 시  
  ```bash
  brew update
  brew upgrade ca-certificates
  ```  

2) **파이썬 신뢰 번들 업데이트**  
강의 환경, 노트북, CI에서 공통으로 적용합니다.  
- 패키지 버전 최소 기준:
  - **uv 0.13.4 이상**
  - **pip 26.2.2 이상**
  - **certifi 2026.10.19 이상**
- 예시 스크립트:
  ```bash
  python -m pip install --upgrade \
    uv==0.13.4 \
    pip==26.2.2 \
    certifi==2026.10.19
  ```

3) **CI와 이미지 자동 업데이트**  
도커 이미지나 교육용 VM을 쓰는 경우, **빌드 단계에 CA·파이썬 번들 업데이트를 고정**하는 것이 중요합니다.  
- Dockerfile 예시:
  ```dockerfile
  FROM python:3.12-slim

  RUN apt-get update && \
      apt-get install -y --no-install-recommends ca-certificates && \
      update-ca-certificates && \
      rm -rf /var/lib/apt/lists/*

  RUN python -m pip install --upgrade \
      uv==0.13.4 \
      pip==26.2.2 \
      certifi==2026.10.19
  ```  
- CI에는 “**주기적 보안 업데이트 잡**”을 따로 두고, 주 1회 정도 `apt upgrade ca-certificates`, `pip install --upgrade certifi`를 실행하게 설정하면 좋습니다.

4) **직접 운영하는 CA·인증서 재발급**  
수업용 내부 서비스, 사내 툴에서 자체 CA를 쓰고 있다면, 이번 사건을 계기로 다음 과정을 정례화하는 편이 안전합니다.  
- 중간 CA 키에 대한 **정기 교체 주기** 설정  
- 인증서 폐기(OCSP/CRL)와 재발급 자동화 스크립트 정비  
- 애플리케이션이 **폐기된 중간 CA 체인**을 거부하는지 통합 테스트 추가

보안 강의와 실무 개발 모두에서 “**신뢰 저장소 업데이트**”가 왜 필수인지 보여줄 수 있는 실제 사례입니다. 오늘 중 실습 서버와 학생 노트북까지 모두 점검하는 체크리스트로 활용하기 좋습니다.

## 2. Anthropic 5.5 삼총사: Haiku·Sonnet·Opus 전환 전략

Anthropic이 **Claude Haiku 5.5, Sonnet 5.5, Opus 5.5**를 공개했습니다. 공통된 메시지는 “동일 혹은 더 좋은 품질을 **더 싸고 빠르게**” 제공하겠다는 것으로, 기존 5.x 사용자라면 기본 모델 교체를 검토할 시점입니다. [Haiku](https://www.anthropic.com/claude-haiku-5-5), [Sonnet](https://www.anthropic.com/claude-sonnet-5-5), [Opus](https://www.anthropic.com/claude-opus-5-5)

### 2-1. Haiku 5.5: 서브에이전트와 대량 요청용

**Claude Haiku 5.5**는 소형·저비용 모델로, 다음에 적합합니다.  
- 문서 수천 건 **일괄 요약**  
- 여러 서브에이전트를 띄우는 **멀티 에이전트 오케스트레이션**  
- 브라우저 내 추론, 서버리스 함수처럼 **짧고 잦은 호출**

API 예시(가상 파이썬 코드):

```python
from anthropic import Anthropic

client = Anthropic()

resp = client.messages.create(
    model="claude-3-5-haiku-2026-10-xx",  # 실제 모델 ID 확인 필요
    max_tokens=512,
    messages=[{"role": "user", "content": "이 문서 요약해줘"}],
)
```

실전 팁:  
- 많은 작업을 할 때는 “한 번에 길게”보다 **짧은 호출을 여러 번** 나누는 것이 Haiku 5.5에서 비용·지연 모두 유리합니다.  
- 에이전트 프레임워크를 쓰는 경우, “요약/정리/후처리” 같은 단계는 기본 모델을 Haiku 5.5로 지정하고, 복잡한 추론만 Sonnet/Opus로 올리는 구성이 좋습니다.

### 2-2. Sonnet 5.5: 기본 모델로 갈아탈 타이밍

**Claude Sonnet 5.5**는 기존 Sonnet 5 대비 **30% 이상 빠르고, 최대 30% 저렴**하다고 밝혔습니다. 엔드포인트는 동일하므로, 단순히 모델 이름만 바꾸고 회귀 테스트를 돌리면 됩니다.

- API 예시:
  ```python
  client.messages.create(
      model="claude-3-5-sonnet-2026-10-xx",
      ...
  )
  ```

실전 마이그레이션 절차:  
1) 스테이징 환경에서 **동일 입력에 대한 A/B 테스트** 실행  
2) 품질 평가는 다음 중심으로 비교
   - 코드 생성 정확도  
   - 시스템 프롬프트를 지키는지 여부  
   - 도메인 문서(사내 규정, 매뉴얼) 준수 정도  
3) 품질이 동등 이상이면, **기본 모델을 Sonnet 5.5로 전환**하고 비용·지연을 모니터링합니다.

강의용 샘플 코드, 튜토리얼 리포지토리도 Sonnet 5.5 기준으로 업데이트해 두면, 수강생이 최신 비용 구조를 그대로 체험할 수 있습니다.

### 2-3. Opus 5.5: 장시간 에이전트용 비용 절감 카드

**Claude Opus 5.5**는 대형·에이전트 특화 모델이며, **Opus 5 대비 약 40% 비용 절감**이 목표입니다. 적합한 사용처는 다음과 같습니다.  
- 수십 단계로 이어지는 **리팩터링 에이전트**  
- CI에 붙여 코드 리뷰, 테스트 계획까지 맡기는 **장시간 세션**  
- 수십 페이지 리포트, 리서치 요약 등 **긴 컨텍스트 지식 작업**

도입 팁:  
- 기존 Opus 5 기반 에이전트 워크플로에 대해, **동일 세션을 10~20개 표본** 잡고 Opus 5.5와 결과를 비교합니다.  
- 차이가 있는 경우, 우선순위는 다음 순서로 조정합니다.
  1) 시스템 프롬프트에서 **역할과 제약을 더 구체화**  
  2) 단계 수를 줄이는 대신, 각 단계 입력을 더 구조화  
  3) 필요한 경우, 마지막 검증 단계만 Sonnet 5.5 또는 Opus 5로 유지

교육 측면에서는 “소형(Haiku)–중형(Sonnet)–대형(Opus)” 3단계 구조로, **태스크별 모델 선택 전략**을 실습으로 보여주기 좋은 시점입니다.

## 3. SF Compute: GPU 랙을 코드로 예약·프로비저닝하기

SF Compute가 **“프로그래머블 데이터 센터” API**를 공개했습니다. 이제 GPU를 개별 인스턴스가 아니라 **랙 단위로 예약**하고, 랙 구성과 네트워크 토폴로지를 코드로 지정할 수 있습니다. [출처](https://www.latent.space/p/sfcompute2)

기본 사용 패턴은 다음과 같습니다.  
1) **가용 랙 조회**  
   - REST API `GET /racks`로 GPU 타입, 수량, 네트워크 옵션을 확인  
2) **예약 생성**  
   - `POST /reservations`에 원하는 GPU 모델, 수량, 인피니밴드 여부, 노드 간 토폴로지를 포함  
3) **프로비저닝 매니페스트 제출**  
   - OS 이미지, 드라이버 버전, 컨테이너 런타임, 필수 패키지 목록을 담은 매니페스트를 업로드  
4) 예약 시간에 맞춰 랙이 지정된 상태로 부팅되고, 이후에 잡을 제출

실전 팁: **“에페메럴 인프라”**로 생각하는 것이 핵심입니다.  
- 매니페스트를 Git에 버전 관리하고, CI에서 유효성 검사를 돌립니다.  
- 예를 들면 다음 정보를 YAML로 묶어 둡니다.
  - CUDA, cuDNN, 드라이버 버전  
  - 도커 런타임 버전  
  - 필수 시스템 패키지와 파이썬 환경  
- 이렇게 해 두면 랙 구성이 바뀌거나, 다른 리전에 랙을 예약해도 **완전히 동일한 소프트웨어 스택**을 재현할 수 있습니다.

강의나 워크샵에서는 “노트북에서 돌아가던 코드가 왜 클러스터에서 느려지거나 깨지는지”를 설명할 때, **토폴로지·드라이버 차이까지 포함한 재현 가능한 인프라** 개념을 SF Compute 예제로 보여줄 수 있습니다.

## 4. Java용 GitHub Copilot: 챔피언들이 쓰는 프롬프트 습관

GitHub가 **“3명의 Java 챔피언이 Copilot을 어떻게 쓰는가”**를 공개했습니다. 공통 패턴은 “코드는 Copilot이 초안을 쓰고, **최종 책임은 개발자가 진다**”는 구조입니다. [출처](https://github.blog/ai-and-ml/github-copilot/how-3-java-champions-are-using-github-copilot-for-increased-productivity)

핵심 사용법은 다음 세 가지로 정리됩니다.  
1) **메서드 시그니처와 Javadoc을 먼저 작성**  
   - 예를 들어, 입력·출력, 예외, 성능 제약을 Javadoc에 명시한 뒤 Copilot을 호출합니다.  
   - 이렇게 하면 메서드 본문 초안이 의도에 더 근접합니다.  
2) **테스트 우선 생성**  
   - 테스트 클래스와 메서드 이름, 시나리오 설명까지 작성한 뒤 Copilot에게 테스트 본문 생성을 맡깁니다.  
   - 특히 파라미터 조합이 많은 경우, 경계값 테스트를 빠르게 생성할 수 있습니다.  
3) **리팩터링 초안으로 활용**  
   - “이 메서드를 두 개로 나누자”, “스트림 API로 바꾸자”처럼 **구체적 refactor 목표**를 코멘트에 쓰고, 제안 코드를 받아 검토합니다.

실전 베스트 프랙티스:  
- Copilot이 생성한 코드는 **기존 단위 테스트와 정적 분석·보안 스캔을 반드시 통과**시키는 워크플로를 CI에 강제합니다.  
- PR 리뷰 가이드에 “Copilot 생성 코드라면, **리뷰어가 논리적 설명을 요청**한다”는 항목을 넣으면, 무비판적인 수용을 줄일 수 있습니다.  
- 수업에서는 한 번은 “Copilot 도움 없이 구현”, 한 번은 “Copilot 초안 후 리팩터링”을 비교 실습하면, 도구 의존도가 아니라 **설계와 리뷰 역량**에 초점을 맞출 수 있습니다.

## 5. 오늘 정리: 모델 갈아타기 전에 토대부터 점검하기

오늘 흐름을 관통하는 대비 구도는 뚜렷합니다. 한쪽에서는 **Anthropic 5.5 라인업**과 같은 모델 업그레이드가 비용과 성능을 끌어내리고, SF Compute처럼 GPU 인프라를 코드로 제어할 수 있는 선택지가 늘어났습니다. 다른 한쪽에서는 eMudhra CA 유출, 소프트웨어 공급망 공격 증가 같은 **토대 수준의 취약점**이, 개발자와 강의 환경을 동시에 위협하고 있습니다.

실무자와 강사에게 필요한 우선순위는 명확합니다.  
1) 오늘 당장 할 일: **CA·신뢰 저장소와 의존성 업데이트를 자동화**해, 실습 환경과 프로덕션 모두에서 기본 보안선을 맞춥니다.  
2) 그다음 할 일: Anthropic 5.5, Copilot 워크플로, SF Compute 같은 새 도구를 **스테이징에서 실험하고, 비용·품질 벤치마크를 쌓은 뒤** 모델·인프라를 교체합니다.

이 순서를 지키면, “새 모델·새 인프라를 먼저 도입하고, 나중에 보안과 재현성을 맞추느라 고생하는” 전형적인 실수에서 한 발 비켜설 수 있습니다.
